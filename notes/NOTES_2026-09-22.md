## Brackets go wherever they enclose text; a `<…>` pair of two math signs stays (2026-09-22 00:43, issue #127)

Fish takes a square-bracketed group inside the text as an instruction: the
reply's `content` loses the words, the word timings skip them and the audio
is shorter (the issue's measurements, `s2.1-pro-free`). The rule of #94,
#96 and #101 removed brackets only when nothing but punctuation, symbols or
whitespace stood outside the groups, so a sentence with one word outside
reached Fish as written. That rule existed to protect comparisons.

`prepareSpeechText` now keeps the unpaired opening positions of each
configured pair; a closing symbol takes the nearest unpaired opening one of
its own pair, whatever lies between. Nested groups lose every layer, since
Fish would swallow an inner pair, and crossing groups (`<[Hello>]`) lose
both pairs. A symbol that closes several pairs closes the one opened last.
Unpaired symbols stay. The removed positions are sorted before they are
returned: `restoreSpeechOffsets` counts them in ascending order, and a
crossing group records them out of order. An opening symbol configured for
two pairs still leaves a segment that contains it unchanged, and an invalid
list still changes nothing.

The `<>` pair alone gets a math-sign test, the owner's choice over literal
removal, which turned `x <= 5 and y >= 3` into `x = 5 and y = 3` and
`aged < 65 years and BMI > 30` into two bare numbers. A `<` or `>` reads as
a sign when whitespace stands on both sides, an ASCII letter or digit on
both sides, `=` touches it, or `-` stands before a `>`. A sign-like `>`
pairs only with a sign-like `<`, and that pair stays as written; a plain
`>` takes the nearest plain `<` and falls back to the nearest sign-like one.
The fallback is for the owner's LitRPG stats, whose segments read
`< 100 exp>` and `< 2/50 HP >` (#98): their `<` is spaced, and without it
`You gained < 100 exp> today.` would keep its signs. Letters and digits are
ASCII on purpose — Chinese has no spaces, and `他获得了<火球术>技能` must
still lose its pair. #94's single wrapper `<a < b>` now falls out of the
rule without its special case, as does `<Warning: HP < 10%>`. Accepted
misreads: `You have < 2/50 HP > left.` stays (both signs spaced),
`List<String>` loses its pair, `P<.001 and Q>.05` loses both signs.

The cache is keyed by the prepared text, so a sentence whose preparation
changed is synthesized once more, and the entry under its old text is
never hit again. On the old scan 31 new or rewritten expectations failed.
The bracket fixture gained four paragraphs — the issue's two sentences, a
spaced angle label and a comparison — for case 3g item 10. Live results
are recorded separately.

## Adoption needed a named document, and naming needed a native position (2026-09-22 02:05, issue #129)

The Positions File's desktop side takes an item from the file only for a document this machine has *named* — a `documents` row mapping `{lib, key}` to a Document Id (`adopt`, `src/read-aloud/document-positions.ts`) — and 1.14.0 named one only when a sentence of it was read here (`recorded`), when a native row from before the file was derived on open (`deriveSharedFromNative`), or in the upgrade's backfill of EPUB rows. Opening a book named nothing. So a book read on the phone alone was never adopted on a computer that had not read it: Shift+Space found neither a row nor an item and let the key fall through to Zotero's own start, the player's play skipped the pull for want of a Document Id, and the first sentence read here — stamped now, newer than the phone's — replaced the phone's item in the file at the next sync, so the phone then adopted the computer's place. #126's crossing run never met it: its fixture had been read on the desktop first. Found by reading the code while recording #128; the live reproduction is #129's verification run.

Spec 6.9 said "for an attachment it holds"; the code's `holders` map meant "named". The word is now defined in the spec's glossary paragraph (*Named*: a device has computed the document's id — OpenReader on add, the plugin on open), and 1.14.2 names every EPUB when its reader opens: `watchReader` awaits `name()` (the old `ensureId`, exposed) before it pokes the Positions File's transport, so the `reader-open` sync has a holder, and the resume paths await it again inside the two-second pull budget — `pullBeforeResume` now takes the attachment, names an EPUB, and flushes the Positions File only once the name is there (the plugin's own file comes down regardless, as before, since a PDF's Shift+Space still resumes from the newest native row). Shift+Space takes the key for an EPUB under sync even with nothing held (`canPullShared`), because the pull may bring something; when it brings nothing, `resumeAfterPull` falls through to Zotero's own start, exactly what returning false did. The player's play takes the async path for every EPUB and stays immediate for a PDF and with the switch off. The cost per opened EPUB is one whole-file read, the first time only (34 MB in 11 ms, #126's run); the log line `document named on open: <lib>/<key>` is the run's proof, written only when the id was not in the store before.

Weighed and rejected on the issue: naming only at resume (the open's `1 adopted` would vanish and every naming would sit inside the resume budget); adopting every item regardless of holder (resume still needs `{lib, key}` → id, the store would hold the phone's own books, 6.9 and the counts change meaning); naming on library add with a whole-library backfill (a read per import and a scan at first start, which #126 declined). A place this computer starts from by hand — a click, "Read Aloud from Here", Zotero's own play — still outranks the phone's item once a sentence is read here: newest wins, and the owner chose the place.

## Zotero asks for its voice list only signed in, and every plugin voice rode that request (2026-09-22 02:46, issue #130)

Reported from outside: signed out of Zotero, no plugin voice reached the
player — not System's, not a local Fish Speech server's — while Test
connection passed, the voice browser listed the voices and nothing was
logged. Read in the installed 10.0.3 (rj = `resource/reader/reader.js`,
xr = `chrome/content/zotero/xpcom/reader.js`):

- `ReadAloudManager.loadVoices(loadRemote)` (rj:82310-82322) calls the
  remote interface's `getVoices()` only when `loadRemote` is true, and
  `_prepareReadAloud` (rj:84270-84271), on every popup open, passes
  `this._state.loggedIn`. That flag is `Zotero.Sync.Runner.enabled` at
  `_open()` (xr:270), refreshed on every `api-key` notification
  (xr:2879-2882); `enabled` is `_apiKey || Zotero.Sync.Data.Local.
  hasCredentials()` (`xpcom/sync/syncRunner.js` 36-40), and `setAPIKey`
  saves or removes the login before it notifies (`syncLocal.js` 135-157).
  The only other listener of `api-key` is Zotero's streamer (`streamer.js`
  41), which re-reads its key.
- The plugin's `loadVoices` hook (#121) passed Zotero's flag through, so
  the composite `getVoices` — Zotero's two tiers and every provider in one
  answer — never ran signed out. The 2026-09-15 notes had it as Still
  open, unverified; #110 had taken every user of plugin voices to be
  signed in.
- Zotero's first-run and Manage voices windows get their interface from
  the reader's own method with their own window (xr:1897-1935) and load
  the remote list without asking `loggedIn` (`useVoiceData`,
  `resource/reader/read-aloud-first-run.js` 3647, the reader bundle's copy
  at rj:40600), so they listed the plugin's voices signed out all along;
  only the player did not.
- Signed out, `TierSelect` (rj:38827-38875) pushes Local alone and, with
  one option, draws the "Log in to access Zotero Voices." row instead of
  the select, so #110's option rewrite never met an element.

The fix: the hook asks for the remote list whatever the flag on a reader
the hijack patched (`ownsInterface`, `diagnostics.liveVoiceList()` shows
`asked` beside `remote`); the composite skips Zotero's `getVoices` — and
does not build Zotero's interface, which opens its audio cache — while the
reader's own `_state.loggedIn` is false, and the credit calls answer none;
the dropdown wrapper hands `TierSelect`, known by its props (a boolean
`loggedIn`, a `tiers` Set, `onChange`, `onLogIn`; the popup's element has
no `tiers`), `loggedIn: true` while the manager lists any plugin voice
(`loginRowReplaced` in `providerTiers()`). The tab's flag rather than the
global one, because a live check can then set it on a fixture tab with
Zotero's own `setLoggedIn(false)` while the owner stays signed in:
Zotero's voices missing from that tab alone is the proof the skip ran.

The owner added one behavior: signed out, the Zotero section's Enable is
greyed, the reason on its line (`blocked` in `ui/provider-rows.ts`, a tier
already on keeps its Disable), and the pane follows a sign-in at once
through its own `api-key` observer. The reason,
`ztts-zotero-not-signed-in`, lost its `Edit →`: it now shows inside the
settings window on every platform, and macOS has no Edit → Settings.
`Zotero.Sync.Data.Local.hasCredentials` is an own property of that object,
so a live check can stand in for a sign-out by replacing it and firing the
notification (`cases/zotero-tiers.md` items 10-11).

## Verified live, issue #130: the tab's own flag proves the skip, and a tab open across a reinstall keeps the previous instance's `loadVoices` hook (2026-09-22 03:30, issue #130)

zotero-tester ran `cases/signed-out-voices.md` 1-5 and `cases/zotero-tiers.md`
10-11 on 1.14.1-beta2 (Zotero 10.0.3-beta.3), the owner signed in with
only Fish Audio on: every item passed. With the fixture tab's
`setLoggedIn(false)` the open read `asked: false, remote: true`, `tiers`
`["fish"]` (339 voices, none Standard or Premium) while
`zoteroTiers().signedIn` stayed true with both switches on, the
`not asked for` line was in the debug output, and a sentence played from
Fish with 10 word timestamps. Zotero's original player drew the provider
select (`loginRowReplaced: true`, no `.row.log-in`); its options panel is
open from the popup's first render (`showOptions` starts true), so a click
on Options collapses it — the kit's first version read a collapsed panel
and reported a false negative. The pane greyed Standard's Enable at the
`api-key` notification with `hasCredentials` replaced, let a raw
`command` at it do nothing, and came back at the second notification.

Found on the way, and older than #130: a reader tab open across an
in-place reinstall is left with the previous instance's `loadVoices`
hook under the new one. The new instance attaches before the old one's
shutdown tail runs (#28, #64), so `live-voice-list.ts` `attach()` takes
the old hook, still an own property of the manager, for `original`; the
old `detach()` then finds a hook that is not its own on top and restores
nothing. Every later load — a popup open, a settings change's refresh,
the redelivery's `loadVoices(true)` (#38) — runs the old, disposed
`load()`, which returns without touching the new stage, and the new one
throws `can't access property "length", list is undefined` at
`stage._allVoices` (caught, logged). Such a tab keeps the voice list it
had before the reinstall until it is closed; playback is unaffected.
Seen on both builds the run installed. Proposed to the owner as an issue
of its own.

## The 03:30 entry had the order wrong: every clean shutdown carries a leftover `loadVoices` hook forward, and none makes one (2026-09-22 10:05, issue #131)

The 03:30 entry put the leftover hook on a new instance attaching before
the old one's shutdown tail. That cannot be the cause: the bootstrap has
held a new `startup()` back until a pending shutdown ends since #28, and
every logged upgrade shows `stopped` before `started`. The error console,
which reaches back to 02:21, shows no failed shutdown either, while the
owner's tab logged the error after each of three clean installs.

What carries it is `detach()` itself: it puts back the own-property
descriptor `attach()` found (`live-voice-list.ts` 100, 144). Once a
manager holds a hook that its own instance never removed, every later
shutdown writes that hook back and the next version keeps it as
`original` again, so the tab stays broken through every update until it
is closed. Zotero leaves a replaced plugin's scope callable
(`xpcom/plugins.js` 305-307), which is why the old hook still runs. What
left the first hook, and whether it still rebuilds the list with an older
build's code, are open on #131.

## Empty plugin preferences enable OpenAI, and native voice memory repopulates the cleared branch (2026-09-22 22:18, issue #132)

Removing a user value is not the same as switching a provider off. Both
`addon/prefs.js` and `core/settings.ts` enable OpenAI by default, with an
empty API key. The owner had disabled it; clearing the plugin branch
removed that override, and reinstalling 1.14.2 exposed the default. An
offline harness using the real settings loader, provider factory, catalog
and browser grouping reproduced `OpenAI (0)` from no saved preferences,
with one intercepted discovery request. Switching only OpenAI off removed
the row and the request. No migration or sync was needed, and no live
request or profile mutation was made during diagnosis. The research
harness remains under `.tmp/first-install-openai/`; no fix was applied.

A settings reset also has a second boundary: Zotero's own
`extensions.zotero.reader.readAloudVoices` survives clearing
`extensions.zotero.zotero-tts.*`. The memory-sync constructor seeds empty
plugin memory from that native preference. The pre-reset backup and the
post-reinstall file both retained the screenshot's Fish voice and 2.15
speed in the native preference, and the new plugin memory held them too.
The prior reset removed 32 plugin preferences but did not create a fresh
profile. Preserve the native preference for an ordinary plugin settings
reset; account for it explicitly when reproducing a first-use environment.

## OpenAI now requires an enable choice on a fresh installation (2026-09-22 22:31, issue #132)

Both installed and fallback defaults now switch OpenAI off. Explicit user
values still win; no migration or preference deletion is involved. Copies
that relied only on the old enabled default now require an Enable action.
The regression drives real settings, provider construction, catalog listing
and browser grouping with installed defaults and an empty backend. It
failed before the change in both modes and passes afterwards, with no
OpenAI entry or request. Explicit true keeps the provider and its failure
feedback, and explicit false keeps it absent. Existing catalog fixtures
now enable OpenAI explicitly instead of inheriting the old default.

The owner waived live zotero-tester verification and requested a direct
commit and 1.14.3 release. The focused live case records expected behavior
for a future run, not a claimed pass. Native voice memory remains intact.

The owner also requested two default-only changes for 1.14.3: expanded
player opening starts on, and Fish Audio starts with Official voices only
(Your voices and Manual voices off). Explicit saved choices still override
these defaults, and manual Model IDs are not erased. Backup coverage now
checks an explicit opt-out from expanded opening; Fish source round-trip
coverage continues to check independent saved choices. The README and
Fish Audio tutorial describe the new defaults in both languages.
