## A bug hunt over the released 1.10.9, through the bridge on Windows: seven runs, three issues, and what Zotero showed (2026-09-05 12:24, issues #48, #49, #51)

The second full pass of `test/zotero-dev.md` (the first was 1.10.1 on
2026-08-31), over the release asset of 1.10.9 installed in place, on the
Windows machine — Zotero 10.0.2-beta.5+72e8b7be3, Firefox 140, in a remote
desktop session. Seven verification briefs to the tester agent, one per
section (sections 1–6, then the audio halves of 3 with the reload and
section 7 last), plus one research follow-up to the section-3 agent. Every
listed behavior PASS except the ones that became issues; every pref
byte-identical at the end of every run (`readAloud.memory` written last,
`reader.readAloudVoices` restored as a string, since Zotero reorders
`en.tierVoices` on its own persist); Zotero's credits untouched — the one
Premium segment of item 3.9 was fetched and never spoken, since the pause
check drives the boundaries through the controller's own
`_handleSegmentEnd`. The one deliberate change to the user's state: the
paused session in the EPUB tab was closed in section 1, because the reading
guard (#11) refuses every provider switch, the favorites-only switch and a
♥ while any session is open, paused included, and most of the checklist
sits behind one of those. The position survived in all three copies
(Zotero's `savedPosition`, the item's own, the plugin's row) and
`diagnostics.smartKey()` predicted `resume at the stored position` for that
tab afterwards. What came out: #48 the voice browser's sample player
swallowing a playback error, #49 the player's language dropdown persisting
Zotero's fallback and the plugin making it the default everywhere, #51 a
permanently deleted attachment's bookmark re-uploaded to the shared
positions file. The issues hold the evidence; this entry holds the Zotero
facts, all from the 10.0.2-beta.5 bundle (`resource/reader/reader.js`
unless said).

- **The player renders only on `readAloudState.lang`, and that field has
  one writer that runs once.** The render gate is
  `popupOpen && readAloudState.lang && !readAloudFirstRunPopup` (42586).
  `_prepareReadAloud` (83983-83995) writes the UI's `lang` inside
  `if (sdt && !this._readAloudManager.lang)` — only while the manager has
  no language yet — and `_updateReadAloudUIState` returns early while the
  popup is closed (83565-83569). So a bare `_prepareReadAloud()` on a tab
  before its first popup open sets `manager.lang`, drops the UI write, and
  the next `toggleReadAloudPopup(true)` skips the block: a session
  `active` and reading with no player on screen, for the tab's life, until
  `_updateReadAloudUIState({ lang })` is written with the popup open (113 ms
  to render, measured). The checklist's own item 3.1 used to do exactly
  that on a fresh fixture, which is how the section-3 run found it. No user
  path reaches it: the view's `lang` output comes back only while the popup
  is open (the helper's `setState`, 53217-53221),
  `startReadAloudAtPosition` — the plugin's resume and plain start — opens
  the popup before `_prepareReadAloud` (83952-83979), and memory-sync moves
  no lane while the document language is unknown (`planSync` returns
  `lang: null` without a `docLang`). Fixed in the checklist and the
  rulebook, no issue.
- **A language switch in the popup resolves against the previous
  language's memory.** `_persistedVoices` is written by
  `_syncPersistedVoicesToManager` alone (83883-83892), for the manager's
  language at that moment; the dropdown's `handleLangChange` (38593-38599)
  calls `setLanguage(base, { region, persist: true })`, which resolves at
  once (82040-82057) with that entry still loaded. `_findFallbackVoice`
  (82173-82213) then fails branches 1 and 2 on availability, computes
  branch 3's region from the old entry, and `_resolveVoice` takes
  `voicesForLang[0]` (82165-82166) — or, coming back to a regional
  language, the first voice of that region (82205-82211). `_pendingSetVoice`
  makes it persist (82167-82171), over the entry the user had for that
  language. Measured both ways through the real dropdown: English →
  Multiple languages landed on `azure::ja-JP-MasaruMultilingualNeural`
  (index 0 of the 87 `mul` voices, every one with `getVoiceRegion` null)
  over the `mul` entry's AlloyTurbo; back to English (United States) landed
  on `azure::en-US-AIGenerate1Neural` (the pool's first `US` voice) over
  Andrew. The counterfactual: `_syncPersistedVoicesToManager()` after the
  switch, or the entry rewritten by pref, put the lane's own voice back —
  the entry is honored whenever it is the one loaded. Zotero's bug at the
  root, for its own users too; the plugin's part is `setLanguage` with
  `persist` counted as a pick (`memory-sync.ts:526`) and spread. That is
  issue #49 — fixed the next day, in 1.10.11, by handing the hook the
  right entry first ([2026-09-06](NOTES_2026-09-06.md)).
- **Read Aloud's audio is a Web Audio graph, and a dead output device is a
  silent hang.** `_initAudioContext` (39933-39955) builds
  highpass → peaking → compressor → destination; `_playAudioBuffer`
  (40010-40041) plays a time-stretched buffer through a source node and
  advances on `source.onended`. With no output device — a remote desktop
  session without audio redirection — the context is `suspended` at
  `currentTime` 0, `resume()` neither resolves nor rejects (race it against
  a timer in a bridge script, or the eval times out to bare `undefined`),
  `onended` never fires, and the controller sits `_isPlaying: true`,
  `_error: null`, `_position` frozen, buffers full: the #42 silent-stop
  shape, from the device side, with nothing in the UI. The sink is per
  content process and does not recover in place — pause/resume and a new
  controller keep the suspended context; a newly opened reader tab gets a
  fresh one, while the device is up — and `_handleDeviceChange`
  (39926-39931, 39957-39985) probes a stall only on `devicechange`. The
  device flapped three times in one day here (absent in section 3, present
  in 5, absent then present then absent in the last run). Synthesis,
  timestamps, highlight, prefetch and every state check run regardless, so
  the mechanism half of every playback item is testable without sound, and
  the checklist now says to probe first. A plain `<audio>` element on the
  same machine decodes, fires `playing`, then `error` with
  `MediaError.code` 3 / `OnMediaSinkAudioError` a few ms later — which is
  what the voice browser's sample player swallows (issue #48).
- **The option rows of the player's CustomSelect select on `pointerup`**
  (37954-37958), not `click`: `element.click()` on a row does nothing;
  `row.dispatchEvent(new win.PointerEvent('pointerup', { bubbles: true, cancelable: true, pointerId: 1, isPrimary: true }))`
  is the dropdown's own path. The trigger opens on `click` (37860-37869).
- **A language key is whatever a file says.** `getBaseLanguage` is
  `lang.replace(/-.+$/g, '')` (38002-38004), and `sdt_segments_getSDTLang`
  hands `setLanguage` a document's raw `language` / `Language` /
  `dc:language` property with only that applied (71241-71250) — no BCP-47
  check, no display-name mapping. The profile's `reader.readAloudVoices`
  carries a key `"English"` holding `{ speed: 1.7 }` and nothing else: that
  shape is the plugin's `persistSpeed` "no matching key" branch
  (`src/core/read-aloud-speed.ts:143-144`), created verbatim as #26 intends
  and as Zotero's own `_persistCurrentVoice` would key it. Which document
  said `English` is open — not the EPUB that was open (its OPF and its SDT
  both say `en`), and no item's `language` field in the library. The key
  self-perpetuates: `resolveVoiceLang('English')` resolves into it.
- **Prefetch's steady state is `position + count`.** `prefetchAfter`
  (`remote-interface.ts:334-359`) warms exactly the setting's count after
  the segment just requested, one chain at a time, skipping what is pending
  or cached; Zotero's own window is three wide. Measured with the setting at
  5: 5, 7 and 11 segments ahead in three states, all inside
  `[position + count, position + 3 + count]`, the "+3" being the upper bound
  the checklist recorded on 2026-08-31 as if it were the value. Amended.
- **The in-place upgrade under a session, again clean.** `stopped` before
  `started` with the database closed in between, no dead object, the tab
  handed the new instance's interface (`redelivered … rebuilt 1 voice
  list(s)`), the System voices working from the rebuilt list, the pane once
  — as 5.6 says, on a session paused at segment 11. The audio cache is per
  plugin instance, so every auto-update re-synthesizes the document
  (`(cached)` gone after the reinstall): design, worth knowing. Zotero's
  own restore on that tab's popup reopen landed one segment early (10 for a
  session paused at 11), the plugin's Shift+Space resume on the exact
  sentence — the documented rect-to-segment behavior, seen in both
  directions in one run.
- **Deleting an attachment does not reach the sync layer.** The deletion
  observer (`src/index.ts:1121-1146`) calls `positionStore.remove` only;
  `PositionSync` (`position-sync.ts:92-118`) has no removal and its `list()`
  is the transport's local side; the merge is a union (`position-file.ts:
  83-93`). A clean 45-entry file put on the server came back at 46 after one
  sync, with the erased fixture's key and without the crafted one — the
  in-memory map is the whole difference. Eight such orphans were already in
  the file, every one a fixture of this checklist. Issue #51.
- **The transport counts before it checks.** With the positions switch off,
  `syncs` and `lastTrigger` still move and `lastOutcome` reads `skipped`
  (`position-transport.ts:109-120`); `remoteEntries`, `adopted`, `uploaded`
  and the file's `lastModified` do not. The back-off gates on time alone
  (`SYNC_RETRY_MS`, 60 s): a URL fixed inside the window still waits, with
  the stale error as the last thing recorded. Every flip of either sync
  switch is a settings change and uploads the full 50-setting backup, keys
  included — fourteen uploads in the section-6 run. A rename leaves the old
  machine's file forever (this profile has `zotero-tts-settings_xujialiu-
  win11.json` from an earlier id, plus the pre-1.11 shared file). All by
  design; recorded so nobody chases them.
- **The reading guard's remedy is heavier than it needs to be.** The dialog
  and the README both say to close the tab; closing the player is enough —
  `toggleReadAloudPopup(false)` is `deactivate()` (83906-83931), and the
  guard reads `active`. Left as is; a wording refinement if wanted.
- **Small things seen, no issue:** `_readAloudPositionLocked` is already
  true when a session starts, so a lock check must force it false first;
  `diagnostics.playerOptions(true)` presses the Options button of every
  reader with a player; `#ztts-notice`'s `textContent` opens with its own
  `<style>` rule; `Zotero.Debug.storing` may already be on; reading a
  `MediaError.message` from chrome logs Gecko's `resistFingerprinting`
  warning; `windowUtils.notifyUserGestureActivation` does not exist in this
  Firefox — the reader document's does; a first visit to the *Other* server
  preset writes nothing, so the fields keep the previous preset's values;
  the OpenAI Test connection says nothing about the model when the server
  lists no models (Chatterbox), the synthesis probe covering it; the memory
  observer re-derives `readAloud.memory` when `reader.readAloudVoices` is
  written back; `store.loaded` is the count at open and does not follow an
  erase; `patches().highlight` counts views and `readAloudMemory` counts
  methods, so both run above the reader count. Issue #39's first half —
  `highlight()` logging an error per call on a popup-less tab — did not
  reproduce on 10.0.2-beta.5 (six calls, nothing logged); commented there.
  Two fixture attachments of an earlier pass, capital-F titles, were in the
  library before the session started, most likely through Zotero sync from
  the macOS pass of the night before; left alone, reported. Issue #50, a
  user's request for chat-completions TTS servers, arrived during the pass.
- **Driving, for the rulebook (updated today):** the bare
