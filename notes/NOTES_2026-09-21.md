## The pane's blank check kept its own list of attributes (2026-09-21 14:30, issue #103)

`diagnostics.l10n()` counts a settings pane element as translated when
Fluent has put its text or a string attribute on it. The attributes it
read were a list typed at #30 against what the pane's messages set then
— `label`, `placeholder`, `tooltiptext`, `help`, a `value` other than
`?` — and nothing tied that list to the Fluent file. #101's bracket pairs
field brought the first message carrying only an `aria-label` (a field
with no text of its own), which Fluent does set: the probe of the live
pass of 2026-09-14 read it on the element. That pass found
`ztts-bracket-pairs` under `blank` on every healthy pane, while every
unit test was green.

The rule is now `paneElementBlank` in `src/core/l10n.ts`, `aria-label`
added, and `test/l10n.test.ts` renders every message of every shipped
locale through `@fluent/bundle` the way Fluent leaves an element — its
value as the text, each attribute set — and requires none to read as
blank, so a message whose only attribute is a kind the rule does not read
fails `npm test` instead of a live pass. The kinds `en-US/zotero-tts.ftl`
uses on 2026-09-21: `value`, `help`, `label`, `placeholder`,
`tooltiptext`, `aria-label`, and `bold`, which never stands alone (the
same test file pins it inside its `.label`). Of the pane's 202
`data-l10n-id` elements the old rule missed only this one.

## Zotero's settings window keeps a radio's end margin on Linux only (2026-09-21 14:44, issue #102)

The two `?` after the auto-scroll options sat 0 px from their text on
Windows (the issue's evidence) and on macOS (measured on Zotero
10.0.3-beta.3 with 1.13.2-beta3: the text's end and the circle's edge
both at 469.72 and at 509.67 px), while every other `?` in the pane
sits 3–9 px after what precedes it. A XUL radio's inline margins in the
settings window depend on the platform:

- the toolkit gives `radio { margin: 2px 4px }`
  (`chrome/toolkit/skin/classic/global/radio.css:13-15`, in the GRE
  `omni.ja`), plus `padding-inline: 4px 2px` on Windows;
- Zotero's `chrome://zotero/skin/preferences.css` zeroes both on
  Windows for a radio in a vertical `radiogroup`
  (`radiogroup:not([orient=horizontal]) radio { padding-inline: 0;
  margin-inline: 0 }`), and every radio's and checkbox's margin on
  macOS (`radio, checkbox { margin: 0; gap: 6px }`);
- on Linux neither rule applies and the toolkit's 4 px end margin
  stands (read from the sheets, not measured).

The checkbox splits the same way: the toolkit's `checkbox { margin: 4px
2px }` leaves it 2 px at its end on Windows and Linux, Zotero's macOS
rule 0, so the `?` after a checkbox measures 6 px on Windows and 4 on
macOS. A gap in this pane that rests on a control's own end margin
therefore differs by platform. The pane's rule for a `?` after text now
lists the radio and zeroes the radio's end margin itself, so a `?`
after a radio is 4 px everywhere.

A CSS fix can be tried on the live pane before any build: find the
plugin's sheet in the settings window's `document.styleSheets` by its
`jar:…/content/preferences.css` href, `insertRule` the candidate at the
end, measure, then `deleteRule` it. The rule applies as it would from
the xpi (the `-moz-platform` finding of issue #56 came from the same
move). Here it moved the two icons from 0 to 4 px and none of the other
50.

### Architecture note that changes the picture (new since the plugin's notes)

Read Aloud no longer segments the live DOM. The reader pulls an **SDT pack** ("structured document
text") through `options.getSDTPack` (X:269 `getSDTPack: this._createGetSDTPack(this._iframeWindow)`;
X:1164-1187 → `Zotero.SDT.getPack(this.itemID, …)`; SDT:278-281 generates it with
`Zotero.PDFWorker.getStructuredDocumentText(item.id, …)` in the document worker and caches it as
`.zotero-sdt-cache` in the attachment's storage directory, SDT:26, SDT:299-300, keyed by the file's
MD5 `item.attachmentHash`, SDT:428-448 / IT:4130-4146). The reader materialises it
(R:84024-84046 `_loadSDT` → `reader.materialize()` → `{ structure, mapper: createPositionMapper(structure) }`,
mapper = `EPUBPositionMapper`, R:62474 / R:63278). Every block and text node in the structure carries
an **anchor** with a precomputed CFI path (`anchor.selectorMap`) and an NFC delta map
(`anchor.deltaMap`); all EPUB positions used by Read Aloud are produced and consumed by
**string operations on those paths**, not by resolving a DOM Range.

So Zotero has two EPUB CFI generators with different text-step conventions:

- **A. DOM generator** — bundled epub.js `EpubCFI.fromRange` (R:46529), used by the EPUB view's
  `toSelector` for selections, annotations and the context menu (Q2).
- **B. Worker generator** — `src/dom/epub/cfi.ts` in W (W:164838-164923), used for the SDT anchors and
  therefore for every Read Aloud `sourcePosition`, i.e. for what `savedPosition` holds (Q1/Q4).

The **resolver** (`EpubCFI.toRange`/`findNode`, R:46973/R:46898) follows A's convention; B follows the
spec. That is the generator/resolver disagreement the plugin brute-forces (issues #3/#4).

`_captureReadAloudStart` (R:84076-84092): live selection (`view.getSelectionPosition()`) > explicit
target (`consumeTargetPosition()`) > `savedPosition` only if
`this._activePrimaryView?.isPositionNearView?.(saved)` (DOM view: R:53745-53751,
±3/+4 viewport heights; **an unresolvable selector counts as near**: "Don't discard a position we
can't resolve", R:53747-53748).

A `null` index reaches the controller as `this._position = backwardStopIndex ?? 0;` (R:39399), i.e.
an unmappable position **starts from segment 0** on the idle path.

**Position → segment** (R:84117-84127):

```js

  let sdtPosition;
  if (isSDTPosition(targetPosition)) { sdtPosition = targetPosition; }            // {start:[…], end:[…]} R:79494
  else { sdtPosition = this._sdt?.mapper.sourceToSDTPosition(targetPosition); }
  if (!sdtPosition) { return null; }
  return findSegmentIndexForSDTPosition(segments, sdtPosition);
}
```

`findSegmentIndexForSDTPosition` (R:71303-71320): *"Find the index of the first segment whose end is
at or past the given position's start"* — `if (compareRefs(segments[i].position.end, position.start) >= 0) return i;`
with a fallback to the **last** segment (`exact = false`). **Only the range START is used**; the end of
a range CFI is parsed but never consulted for the segment choice.

**CFI → SDT point** — `EPUBPositionMapper.sourceToSDTPosition` (R:62506-62521): requires
`position.type === 'FragmentSelector'` (`conformsTo` is **not** checked on this path); `parseCFIRange(value)`
(R:62633-62663) splits `epubcfi(…)` on top-level commas (1 part → start = end = whole path; 3 parts →
`parent+start`, `parent+end`) and `splitOffset` (R:62690-62700, regex `^(.*?):(\d+)(?:\[[^\]]*\])?$`,
offset `null` when absent). Then `_pointToContentPoint(path, offset, isEnd)` (R:62528-62549):

```js
let strippedPath = stripAssertions(path);                     // removes every [..]  R:62617
for (let entry of this._pathEntries) {                        // text-node paths (exact match)
  if (strippedPath !== entry.path) continue;
  // CFI offsets are in original (DOM) space; SDT text is NFC
  let localOffset = offset === null ? (isEnd ? entry.length : 0)
                  : localOriginalToNFC(entry.deltaMap, entry.nodeCharStart, offset, entry.length);
  return [...entry.ref, entry.nodeCharStart + localOffset];
}
for (let entry of this._blockEntries) {                       // leaf-block paths (prefix match)
  if (!cfiPathStartsWith(strippedPath, entry.path)) continue;
  return isEnd ? getBlockEndBoundary(entry.ref) : [...entry.ref];
}
return null;
```

`cfiPathStartsWith` (R:62624-62631) accepts an exact match or a continuation at `/`, `:`, `!`.
`_buildIndex` (R:62560-62615) indexes **leaf blocks only** (`walkContentRangeLeafBlocks`, R:59970) —
`path: stripAssertions(blockAnchor.selectorMap)` — and their text nodes
(`expandSelectorMap(block.selectorMap, text.selectorMap)`, R:62233-62240).

**Consequences for the two shapes in question**

- **ELEMENT CFI, no text step, no offsets** (`epubcfi(/6/34!/4/2/4/2/4)`): it *does* resolve, without
  any DOM access, when its path **equals a leaf block's path or lies inside one** (e.g. a `<span>` inside
  the `<p>`): start → block start ref `[blockIndex]`, end → next block boundary; the chosen segment is
  the **first segment of that block** (first segment whose end ≥ block start; for a block without text
  segments, e.g. an image, the next text segment). If the path is an **ancestor** of leaf blocks (the
  body, a `<div>`/`<section>` wrapper that has block children, a `<blockquote>`, `<ul>`, an `<li>` with
  block children, a `<table>`) nothing matches → `null` → segment 0 (idle) or no-op (active).
  Leaf blocks are what the worker emits (W:164991-165118): `h1-h6`, `p`, `figcaption`, `pre`; a
  transparent/unknown element (`div`, `section`, `span`, … W:165056-165060) **without block children**
  becomes a paragraph anchored at that element (W:165108-165116); a bare text node directly inside a
  container becomes a paragraph anchored at the **text node** (W:164992-165000, so that block path ends
  in a text step); `li`/notes are container blocks whose leaves are inside.
- **RANGE CFI with text steps and offsets** (`epubcfi(/6/34!/4/2/4/2/4/1,:0,:94)`): the start point
  `…/4/1:0` must match a text-node entry **exactly** (path string, after assertion stripping); the NFC
  delta map translates the DOM offset into SDT (NFC) space; the segment is the one containing that
  character (first segment whose end ≥ it). If the text step does not match any entry (e.g. the other
  text-step convention), the block prefix loop still catches it (`…/4/1` starts with `…/4`) and the
  position degrades to the **block start**, i.e. the paragraph's first sentence — not a failure.
  The end point is computed but unused for the segment choice.

Idle path timing: with `startReadAloudAtPosition(pos)` on an idle reader the target is consumed only
once a voice resolves and `activate()` runs (`_onReadAloudEngineStateChanged` auto-activates,
R:83874-83878).

### Q3. Which epub.js, and how a CFI resolves

- Fork of **epub.js 0.3** (R:48382), `class EpubCFI` at R:46042, with Zotero changes: `pathTo` stops at
  `.cfi-stop`/fragments (R:46471-46474); `walkToNode(steps, _doc, ignoreClass, root)` (R:46861-46896);
  `findNode(steps, _doc, ignoreClass, root)` (R:46898-46926) resolves by **XPath** when no ignoreClass:
  `stepsToXpath` (R:46792-46810) builds `./*` + `*[index+1]` per element step and `text()[index+1]` per
  text step (`*[position()=n and @id='x']` when an assertion is present, R:46800-46802);
  `toRange(_doc, ignoreClass, root, options)` (R:46973-47040) with `fixMiss(…, calibreCompat)` (R:46928).
- The view resolves against the **section container**: `getRange(cfi)` (R:57717-57750):
  `let view = this._sectionRenderers[cfi.spinePos]; … cfi.toRange(view.container.ownerDocument, undefined, view.container)`
  with `spinePos = cfi.base.steps[1].index` (R:46156). `./*` under the container is `replaced-html`, so
  the path after `!` is addressed exactly as under a document element.
- **Element-step rule** — `parseStep` (R:46188-46215):

  ```js
  if (num % 2 === 0) { type = "element"; index = num / 2 - 1; } else { type = "text"; index = (num - 1) / 2; }
  ```

  and XPath `*[index+1]` counts **element** children only → element index = 2 × (1-based index among
  element siblings): **upstream's rule, unchanged**. Text steps: `text()[index+1]` = index among the
  parent's **text-node children** (`walkToNode` equivalently `this.textNodes(container)[step.index]`,
  R:46849-46859) — upstream's convention, whereas the worker generator uses the spec's
  `1 + 2 * elementsBefore` (W:164897-164907). Hence issues #3/#4; irrelevant to a text-step-less CFI.
- **Spine component**: identical on both sides — upstream `(spineNodeIndex+1)*2` / `(index+1)*2` over all
  itemrefs (R:47056-47066, R:49040, R:49139-49170); worker `spineStep = 2 * (elementIndex + 1)` among
  `<package>` element children, default 6 (W:164654-164668), `itemStep = 2 * (spineIndex + 1)` over all
  itemrefs including `linear="no"` and ones lacking a manifest entry (W:164672-164678, W:166067-166087).
  So OpenReader's `/6/N` (N = 2·(i+1)) matches unless the OPF orders `<spine>` unusually — and then both
  compute the same non-6 value.
- **What can make an upstream-generated element CFI land elsewhere in Zotero**:
  1. **Sanitiser removals.** `sanitizeAndRender` (R:55499-55577) parses the XHTML with
     `DOMParser … 'application/xhtml+xml'` (R:55508) and removes `<style>` (R:55518-55521),
     `<link rel~=stylesheet>` (R:55522-55533), `<title>` (R:55534-55536); the worker skips the same three
     (`SANITIZER_REMOVED_TAGS = new Set(['style', 'title'])` + stylesheet links, W:164852-164866,
     comment "CFI step indices must skip these so paths match the post-sanitization DOM"). Upstream
     epub.js in a WebView counts them. Inside `<head>` this is harmless; a `<style>`/`<link>`/`<title>`
     inside `<body>` shifts every later sibling by one element (step −2) in Zotero relative to
     OpenReader.
  2. `html/head/body/base/meta` are **replaced** by `replaced-*` custom elements in place
     (R:55502, R:55566-55573) and `<object data type=image/*>` by `<img>` (R:55538-55550): same count and
     position, no shift.
  3. `renderMath` runs only when a `script[type="text/x-mathjax-config"]` exists (R:53172-53184) and
     lives in a lazy chunk not read here; it may add elements (unverified).
  4. Parsing model: Zotero DOM and worker both parse as XML (worker: htmlparser2 `xmlMode: true` with
     an HTML-mode fallback on parse failure, W:164422-164435), so no HTML tree fix-ups (e.g. implicit
     `<tbody>`). Whether OpenReader's WebView parses the section as XHTML or HTML was not checked here.
  5. Assertions: the SDT mapper strips `[…]` (R:62617-62619) and Zotero emits none (`toString(true)`),
     but the DOM resolver's XPath requires a present `[id]` to match (`@id='…'`, R:46800-46802) —
     a wrong assertion breaks `toDisplayedRange`; omit them.
  6. `conformsTo` is not checked by the mapper (R:62507) but `toDisplayedRange` throws on anything but
     `http://www.idpf.org/epub/linking/cfi/epub-cfi.html` (R:57787-57789; constant
     `FragmentSelectorConformsTo.EPUB3`, R:51735; mapper `CONFORMSTO`, R:62223).

### Q5. Reading a file's bytes by range from the plugin sandbox

`IOUtils.webidl` is **not** in omni.ja (the only "webidl" entries are two devtools allowlist files); it
is compiled into libxul. Read from the ESR 140 source instead
(`https://hg-edge.mozilla.org/releases/mozilla-esr140/raw-file/tip/dom/chrome-webidl/IOUtils.webidl`):

```webidl
dictionary ReadUTF8Options { boolean decompress = false; };
dictionary ReadOptions : ReadUTF8Options {
  /** The offset into the file to read from. If unspecified, the file will be read from the start. */
  unsigned long long offset = 0;
  /** The max bytes to read from the file at path. If unspecified, the entire file will be read.
      This option is incompatible with |decompress|. */
  unsigned long? maxBytes = null;
};
/** Reads up to |opts.maxBytes| of the file at |path| according to |opts|. NB: The maximum file size that can be read is UINT32_MAX. */
[NewObject] Promise<Uint8Array> read(DOMString path, optional ReadOptions opts = {});
```

So a byte range is one call: `await IOUtils.read(path, { offset, maxBytes })`; the whole file is
`await IOUtils.read(await item.getFilePathAsync())` (Zotero does exactly that for the reader, X:862).
The sandbox (PL `_loadScope`) gets `IOUtils`, `PathUtils`, `ChromeWorker`, `Worker` via `Object.assign`
and `crypto`, `TextEncoder`, `Blob`, `File`, `FileReader`, `fetch` via `wantGlobalProperties`
(PL, the `wantGlobalProperties:` array and the `Object.assign(scope, {…})` after it). SHA-256 would be
`crypto.subtle.digest('SHA-256', bytes)`; that `crypto.subtle` is present in the sandbox is what
MEMORY.md records, not something this static read proves. Note Zotero's own file identity is MD5:
`item.attachmentHash` → `Zotero.Utilities.Internal.md5Async(path)` (IT:4130-4146), used by the SDT cache
(SDT:428-448) and file sync.

### Q6. NFC normalisation

The reader bundle never calls `normalize('NFC')` — its uses are NFD/NFKC/NFKD for search
(R:73512, R:73575, R:73599, R:74479). NFC happens in the **document worker** when the SDT pack is built,
per DOM text node, after whitespace collapsing (W:165308-165312 `collapseWhitespace(raw)`):

```js
function createTextNode(text, node, ctx, collapseMap = '') {
    let nfc = text.normalize('NFC');                                   // W:165366
    let tn = { text: nfc };
    …
    let nfcMap = nfc !== text ? computeDeltaMap(text, nfc) : '';        // W:165371
    let deltaMap = composeDeltaMaps(nfcMap, collapseMap, nfc.length);   // W:165372
    if (deltaMap) { anchor.deltaMap = deltaMap; }
```

So **segment text** (`chain.text`, `segment.text`, what the TTS provider receives) is NFC and
whitespace-collapsed; the **DOM text is untouched**, and CFI offsets stay in original DOM space — the
`deltaMap` translates both ways (R:62076-62135 "DeltaMap utilities for NFC normalization position mapping",
`nfcToOriginal` R:62130, `localOriginalToNFC` R:62446; comment at R:62533 "CFI offsets are in original
(DOM) space; SDT text is NFC"). The other NFC call in the worker (W:157335) is the PDF extractor
(`./src/pdf/index.js`); W:2899/2902 are pdf.js internals. Adjacent DOM text nodes with equal style are
merged into one SDT text node with a multi-entry selectorMap `"len path\nlen path"`
(W:144680-144750 `mergeNodesWithSelectorMap`).

### Implications for a shared position (not asked, but what the reading shows)

- An OpenReader **element CFI of a paragraph block** hands Zotero the paragraph's first sentence with no
  DOM involvement, provided it names a Zotero *leaf* block (a `<p>`/heading/`pre`/`figcaption`, a
  block-less `<div>`, …) or a descendant of one, and does not name a container (`<li>` with blocks,
  `<blockquote>`, `<div>` with block children) — those yield segment 0.
- To land on the exact sentence the plugin can hand `startReadAloudAtPosition` a Zotero-style range
  CFI built from the **SDT anchors** (block `selectorMap` + text `selectorMap`, via
  `_sdt.mapper.textNodeSpansToSourcePosition` or `resolveSelectorMap`) — the same generator Zotero uses —
  rather than epub.js `fromRange`, whose text-step convention Zotero's own mapper does not index; or
  hand an **SDT position** `{ start: [block, node, char], end: […] }` directly (`isSDTPosition`,
  R:84119). The text anchor's `exact` should be compared against `segment.text` after the same
  `\s+ → ' '` + trim, both sides NFC.
- The plugin's text-step brute force is needed only for **display** (`toDisplayedRange`), never for
  the resume path, which never resolves the DOM.

## An element CFI from upstream epub.js names the same block in the SDT mapper, measured on four books (2026-09-21 17:18)

The round trip issue #126 asked for, run by a delegated agent through the zotero-dev bridge on this Zotero (10.0.3-beta.3) against the exact epub.js bundle `@epubjs-react-native/core@1.4.8` embeds (fingerprints match npm `epubjs@0.3.93`; run under jsdom). The full report, with every (b) case and the live tables, is in the OpenReader repo's log, `notes/NOTES_2026-09-21.md` at 17:11. What concerns Zotero:

- **Where the mapper's list is.** The pack is not loaded when a reader opens: `await reader._internalReader._loadSDT()` (R:84024), then `reader._internalReader._sdt` = `{structure, mapper}`; `mapper._blockEntries` (`{ref, path, block}`, `path` = the assertion-stripped `block.anchor.selectorMap`, spine component included) is exactly the array `_pointToContentPoint` scans (R:62541); `mapper._pathEntries` holds the text-node paths. Serialising 仙逆's 124,908 blocks inside the reader compartment (`new reader._iframeWindow.Function(...)` + `IOUtils.writeUTF8`) took 122 ms.
- **Element CFIs resolve exactly in `.xhtml` books.** 621/621 (El Akkad) and 120,755 + 2,061 whitespace-only (仙逆, `<br/>` inside `<h2>`) of 122,816 upstream Blocks named the identical Zotero leaf block through the mapper and through `view.toDisplayedRange`; the spine step `/6/N` agreed on all 2,096 sections. - **The mapper strips `[id]` assertions (R:62617); `toDisplayedRange` does not.** True assertions (`/6/8[cop]!…`, `…/40[release_identifier_line]`) resolve identically either way; a **wrong** one makes `toDisplayedRange` return null (`@id='nope'` in the XPath, R:46800-46802) while the mapper still resolves.

The DOM resolver still finds the element.
- **`<dl>` definition lists (processor v2):** the worker emits the whole `<dl>` as one paragraph whose text is only the `<dt>` terms; the `<dd>` paragraphs are **absent from the SDT** — 572 upstream Blocks in one book land on the dt-words block, and Read Aloud never speaks that text.
- **Text-node-anchored leaf paths (odd last step) do not survive the trip out.** 430 of the leaf blocks in two O'Reilly books are anchored at text nodes with the spec's `1 + 2·elementsBefore` numbering (W:164897-164907); upstream's resolver counts `text()[n]` (R:46849-46859) and resolved 81 of them correctly, 114 to the wrong node, 235 not at all. Element-anchored paths resolved 125,533/125,533 in the two novels. So anything written for another reader must be the **block's** element path, never the text-node path.
- **The seam is the other side's parser, not Zotero's.** Zotero parses every member as XHTML (`DOMParser … 'application/xhtml+xml'`, R:55508; worker htmlparser2 `xmlMode: true`, W:164422); epub.js in a WebView delivers sections through `srcdoc` and HTML-parses them, so `.html` members with self-closing `<a …/>` index anchors (Wickham, *R Packages*) put every later sibling off by one — 50 same-path-different-text paragraphs and 1,645 of 2,422 CFIs unresolvable — and a `<table>` without `<tbody>` gains a step. ## The hooks the Positions File rides on, and what is read where (2026-09-21 17:58, issue #126)

What 1.13.2's plugin side of the shared positions (docs/spec/SYNC-FORMAT.md) reaches into Zotero for, verified against the unpacked 10.0.3 bundle (R = `resource/reader/reader.js`); every read is a read, nothing in the reader is patched, and every value that crosses is copied.

- **Capture reads two things per sentence**, from the sandbox, on the sampler's tick: `_internalReader._readAloudManager.activeSegment` — `{ text, position: { start: [...blockRef, node, char], end } }` (`addSegment`, R:71233-71244; getter R:82220; the NFC, whitespace-collapsed segment text) — and `_internalReader._sdt.structure`, the materialised SDT (`_loadSDT`, R:84024-84046; set once Read Aloud has requested segments, R:84048-84061). The block is reached by walking `structure.content[ref[0]].content[ref[1]]…` — as many property reads as the ref is deep — so a 124,908-block novel costs nothing per tick; its text is the concatenation of its text nodes' `text`, its path `anchor.selectorMap` with `[…]` stripped, exactly what `EPUBPositionMapper._buildIndex` indexes (R:62560-62615). A leaf block is one whose `content` holds only text nodes (`isLeafBlock`, R:59961-59969); a segment's ref always names one.
- **No CFI is generated**, in either direction. The locator written is the block's own path with a trailing odd (text-node) step dropped (`elementLocator`); the position handed back to Zotero is an **SDT position**, `{ start: [...ref, node, char], end }`, which `startReadAloudAtPosition` takes as it stands: `isSDTPosition` (R:79494) short-circuits `_findReadAloudStartIndex` (R:84117-84127) on both the idle path (`setTargetPosition`, R:84256; consumed in `_captureReadAloudStart`, R:84076-84092) and the active one (`jumpTo` → `onComputeRepositionIndex`, R:82607-82615, 82926-82930). The segment that starts is the first whose end is at or past the point (`findSegmentIndexForSDTPosition`, R:71303-71320), so a point at the sentence's first character lands on that sentence.
- **Resume walks the SDT inside the reader window.** The snapshot of every leaf block (`{ ref, path, text, starts }`) is produced by `walkSnapshot`'s own source handed to `waived(reader._iframeWindow).Function` and called with the structure — the walk that took 122 ms for 仙逆 from chrome in the round-trip run (17:18) — with a sandbox walk over the wrappers as the fallback. Two passes: the blocks related to the locator's path first, every block only when the anchor is not there. **From the sandbox this has not been timed yet**; the live run measures it.
- **A row from before this build is derived on open.** `renderToolbar` (the event `watchReader` already rides on) fires with `_internalReader` present; `_loadSDT()` then `mapper.sourceToSDTPosition(cloneInto(pos, win))` (R:62506-62521) turns the native FragmentSelector into the SDT point. When the row's text step is one the mapper does not index, the point degrades to the block's boundaries — a bare ref, no node, no char (R:62543-62546) — and the item's quotation becomes the whole paragraph; the stamp is the row's own `ts`, never now, so a place read before the update cannot outrank one a phone reached since.

Whole-file because the copied core is synchronous and `IOUtils` is not (`ReadOptions.offset`/`maxBytes` exist in ESR 140, 17:16, and are not used). Each id logs `document id for <lib>/<key>: <bytes> bytes read, <ms> ms`; the number for 仙逆 is owed by the live run.
- **A pause is seen by the sampler**: `managerOf(reader)` already yields `{ active, paused }`; the tick that sees speaking → not speaking (paused, closed, or the reader gone) calls back once, and index.ts pokes both transports after ten quiet seconds.
- **The reader-realm rules held throughout**: arrays from the reader are walked by index (a sandbox callback handed to their `some`/`forEach` never runs, 2026-09-08 and 2026-09-15), objects handed in go through `Components.utils.cloneInto(value, reader._iframeWindow)`, and the snapshot comes back as a JSON string because a string is the one thing that crosses without a wrapper.

## The player's play resumes through toggleReadAloudPaused, and a jump un-pauses by itself (2026-09-21 18:12, issue #126)

The pull before a resume (spec 6.8) had reached Shift+Space only; the player's play button goes another way, and its facts are these, from the 10.0.3 bundle (R = `resource/reader/reader.js`):

- **Every play/pause goes through `reader._internalReader.toggleReadAloudPaused(paused = undefined)`** (R:84220-84238): the player button, the reader's Space key (R:82089) and the plugin's own `togglePlayerPaused`. It returns early for a disabled Read Aloud or an inactive manager; with no argument it flips `manager.paused`; un-pausing calls `_lockPositionToReadAloud()` then `manager.play()` (R:82558), pausing `manager.pause()` (R:82569). So the one wrap `resume-guard.ts` already keeps on this method (#93) is where a resume can be held: the wrapper returns at once and runs the original later, or not at all.
- **`repositionTo` un-pauses by itself** (R:82616-82628): `_paused = false`, a new controller, `_stateChanged()`. `startReadAloudAtPosition(sdtPosition)` on an active session takes `jumpTo` → `repositionTo` (R:84239-84266, 82607-82615), so after a resolved shared resume the original un-pause must **not** run: it would read `paused` as false, compute `paused = true`, and pause the sentence it just started. The guard's `control.release()` is that case; `control.resume()` the others. A `jumpTo` whose position does not map is a silent no-op (`onComputeRepositionIndex` null, R:82611-82614) and leaves the manager paused — index.ts reads `manager.paused` after the jump and runs the original un-pause when it is still true.
- A second press while the pull is pending is ignored (the guard's `pending` flag); a pause, an idle reader, `toggleReadAloudPaused(true)`, sync off, and an attachment without a Document Id all run the original at once. The whole thing is bounded by the same `RESUME_PULL_MS` as Shift+Space, and the press is settled in a `finally`, so a throw anywhere still lets the original run.

## `_sdt.mapper` is an Xray wrapper in the sandbox; `_internalReader` and `_readAloudManager` are not (2026-09-21 18:25, issue #126)

Found by the live run of 1.13.2-beta5 (zotero-tester, build 679460d): item 8 failed with `sdt.mapper.sourceToSDTPosition is not a function`, once per already-open EPUB reader with a row, so `documents.items` stayed 0 after the backfill had named 12 documents. Measured on three EPUBs from the sandbox: `Components.utils.isXrayWrapper(sdt.mapper) === true`; its `ownKeys` are `["_structure","_pathEntries","_blockEntries"]` and `typeof sdt.mapper.sourceToSDTPosition` is `"undefined"`, while `typeof Cu.waiveXrays(sdt.mapper).sourceToSDTPosition` is `"function"` — an Xray of a class instance replaces the prototype with `Object.prototype`, so own data properties show and prototype methods do not. `_internalReader` and `_readAloudManager` are **not** Xrays, which is why `_loadSDT()`, `activeSegment`, `startReadAloudAtPosition` and every other path worked; `_sdt` itself and `_sdt.structure` are plain data reached through the same view — the structure walk (`blockAtRef` in the capture path, item 3) works unwaived because data properties are exactly what an Xray shows.
