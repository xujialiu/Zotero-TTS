## Positions travel as one shared WebDAV file, merged by recency (2026-09-01 00:26, issue #40)

The reading-position store now syncs between computers through the user's
own WebDAV folder — `zotero-tts-positions.json` beside the settings backup,
the union of every machine's bookmarks. The parts worth keeping:

- **Settings and positions split on mergeability.** Positions are one row
  per attachment with a timestamp, so every machine can write one shared
  file through download → merge (newest `ts` per `lib/key` wins) →
  conditional upload, and a lost concurrent write self-heals from the local
  store on the next sync. Settings are one unmergeable blob, which is why
  the settings side (#41) gets one file per machine instead. Getting this
  asymmetry right was most of the design discussion.
- **Canonical serialization is what makes "upload only when changed"
  work.** Entries sorted by `lib` then `key`, fields in one order; the
  transport compares the serialized merge against the downloaded text and
  skips the PUT on byte equality. Verified live in the strongest form by
  accident: the tester PUT a file it had rebuilt by hand from parsed
  items, and the plugin still judged it byte-equal (652 chars both ways).
- **The store filter and the file union are different sets.** Merged
  entries are offered to the sampler only when
  `Zotero.Libraries.exists` + `Items.getIDFromLibraryAndKey` resolve them
  on this machine; everything stays in the file for the machines that do
  have those documents. A crafted `ZZFAKE01` entry survived four merges in
  the file and never entered the local store.
- **A newer build's file is refused, a broken one is healed.** The parser
  throws with a `kind`: `newer` aborts the sync (a downgrade must not eat
  what a newer format holds), `malformed` is treated as an absent file and
  the next upload overwrites it.
- **The sampler outbids adopted clocks.** `adopt()` takes a remote entry
  only when strictly newer; and a real sentence change now stamps
  `max(now, previous.ts + 1)` instead of plain `now` — otherwise a machine
  with a fast clock pins a document against real listening everywhere
  until wall time catches up with its stamp.
- Event-driven only: pokes at startup, reader open, tab close, the pref
  observer (so ticking the checkbox syncs at once — verified: the observer
  fires the sync synchronously enough that the first poll already saw it
  running), and one bounded flush at shutdown. Single-flight with one
  trailing run; a burst of tabs is one request. An unreachable server
  failed in 422 ms, logged exactly once, backed off for its 60 s window,
  recovered when the URL came back.

The switch is `webdav.syncPositions` — in DEFAULTS deliberately, so the
backup carries it (with the credentials it needs) to a restored machine,
while the position *data* stays out of backups as before.

## One tab close fires both close hooks, so anything riding a close must dedupe (2026-09-01 00:29, issue #40)

Live verification caught the transport syncing **twice per ordinary tab
close**: `tab.onClose` fires first and `reader.uninit` follows (the
2026-08-27 sequence), each capture was followed by a poke, and single-flight
does not swallow the second — a trailing poke is a full sync of its own.
The captures themselves were always safe (the first one freezes the
attachment, so the second reads nothing); it was the *pokes* that doubled,
and with the switch on every closed tab cost two GET round trips.

Fix: `tab.onClose` marks the reader in a `closePoked` WeakSet before its
poke; the `uninit` backstop pokes only unmarked readers — which keeps it
covering the one path that has no tab, a separate reader window. Verified
on 1.11.0-beta2 with the sequence `startup → switch-on → open → close →
open → close` producing syncs 1..6 exactly, **with both hook maps
observed live at 1 before the close and 0 after** — so `uninit` did fire
and the WeakSet suppressed its poke; a bare +1 count could not have told
that apart from a backstop that silently failed to install.

The general lesson: the tab hook and the uninit hook are a pair everywhere
(capture already rides both), and any *side effect* attached to "a reader
closed" needs this dedupe, while the capture-style reads stay idempotent
and can keep riding both.

## Settings sync splits machine by machine, and a multistatus needs no DOM (2026-09-01 00:55, issue #41)

The settings side of the sync split shipped: manual backup is two files
(settings snapshot + positions export/import, the import running the same
merge as #40's transport), and with WebDAV configured each machine keeps
`zotero-tts-settings_<id>.json` fresh on the server by itself — upload
only, applying stays a button. What the work taught:

- **The machine id must live outside DEFAULTS.** The backup set is exactly
  DEFAULTS, so an identity pref inside it would be hijacked by restoring
  another machine's backup — machine B would silently start writing
  machine A's file. `webdav.machineId` is therefore undeclared, created on
  first use (verified live: the pane load created it), defaulting to the
  sanitized hostname — "Xujia's MacBook Pro 5" came out
  `Xujias-MacBook-Pro-5`, apostrophe and spaces collapsed to dashes.
- **A PROPFIND multistatus parses fine without a DOM.** The sandbox has
  DOMParser but the tests' Node 22 does not; injecting a parser would have
  left the actual parsing untested. `parseMultistatus` (core/webdav.ts) is
  a prefix-agnostic string extractor — Nextcloud's `d:`, Apache's `D:` +
  `lp1:`, unprefixed, entities, percent-encoded CJK paths all fixtured —
  and against the real server the listed `lastModified` matched the
  upload's own `exportedAt` to the second.
- **Auto-upload gating, measured**: with the switch off a change is not
  queued at all (24.8 s later: nothing pending, file 404). Flipping the
  switch on is itself an observed settings change, so the first upload
  follows ~10 s later with no further action. A two-change burst collapsed
  to one upload carrying the settled value — the transient never reached
  the server. A `config`-kind failure arms no retry timer (a blank URL
  would otherwise log an error a minute forever); the next change tries
  again.
- **`pending` clears before the PUT lands.** `run()` drops the flag before
  awaiting the upload — correct, or a change arriving mid-upload would be
  swallowed — so `pending: false` is not "done": completion is
  `uploads`/`lastAt`. It cost the verification a polling round; any pane
  indicator or future check must read the counters.
- **The pre-1.11 shared file is not orphaned.** The user's real folder
  held a `zotero-tts-settings.json` from the manual era;
  `SETTINGS_FILE_PATTERN`'s optional `_<id>` group lists it, and the
  Restore picker offers it as "shared file (before 1.11)". Consequence on
  such a profile: with two files present the picker always opens — the
  silent single-file path only runs on a clean folder.

## Modal dialogs cannot be driven through the bridge (2026-09-01 00:57)

`Services.prompt.select` / `confirm` and the FilePicker block the calling
JS and the extension's event loop — the same reason the browser tooling
warns never to trigger alerts. So the Restore-from-server click and the
positions Export/Import buttons cannot be exercised end to end from a
verification agent; the pass proves the listing headlessly instead
(`diagnostics.settingsFiles()` runs the very `client.list()` the button
runs) and leaves the dialog flows to unit tests plus a human's one look.
General rule for future briefs: name the modal-bearing buttons up front as
do-not-click, and give the diagnostic that proves their substrate.

## The bridge's zotero_set_pref cannot write false to a bool pref (2026-09-01 00:31)

`zotero_set_pref` with value `false` echoes `Set … = "false"` and leaves a
declared bool pref at **true**: the value arrives stringified, and
`Zotero.Prefs.set` writes through the declared type, so `setBoolPref` gets
a truthy non-empty string. Caught during #40's verification because the
"end state" check read `enabled: true` after the supposed switch-off. The
reliable route from the bridge is `zotero_execute_js` with
`Zotero.Prefs.set(name, false, true)` and a read-back of
`typeof Zotero.Prefs.get(name, true)`. No future run should trust
`zotero_set_pref` for a boolean in either direction without reading the
pref back.
