# zotero-tts — engineering notes, 2026-09-07

[← 2026-09-06](NOTES_2026-09-06.md) · [index](NOTES.md)

## The plugin carries its own copy of its strings in the registry, since Zotero's reload deletes the shared one after the successor has started (2026-09-07 00:02, issue #64)

Issue #64 holds the incident, the plugins.js citations and the plan;
this entry holds what a plugin can and cannot do about Zotero's Fluent
registration, what the loss actually costs, and what the fix measured.

- **The registration and its removal are Zotero's, and on a reload the
  removal runs last.** `xpcom/plugins.js` reads every plugin's
  `locale/<locale>/*.ftl` into one closure-private map and rebuilds one
  `L10nFileSource.createMock` source named `zotero-plugins` from it
  (`registerLocales` 584–653, async over the file reads;
  `rebuildUnifiedPluginSource` 660–688); `unregisterLocales` (690–694)
  deletes the plugin's entry and rebuilds, synchronously. `onDisabled`
  (911–919) awaits the bootstrap's `shutdown` and *then* unregisters;
  `onEnabling` (900–909) registers and then calls `startup`; the
  AddonManager fires the two 1–2 ms apart and nothing sequences them —
  the issue #28 shape, one layer further out. A plugin cannot reach the
  map, `Zotero.Plugins` exposes nothing that re-registers, and the
  `Zotero.Plugins.addObserver` `shutdown` hook fires *before* the tail
  (`_callMethod` 224–285 notifies observers after the bootstrap promise,
  and `onDisabled` continues after `_callMethod`), so the only moves are
  a timing guess or a source of one's own. An in-place install is not
  affected: `onInstalling` awaits the old `shutdown` before anything.
- **A resource missing from a Localization empties the whole
  Localization, so the settings window goes, not the pane.** The
  preferences window translates every pane through one `document.l10n`
  (`preferences/preferences.js` 353–361, the `translateFragment() failed
  -- invalid data-l10n-id` line is its catch), and the pane's `<linkset>`
  adds `zotero-tts.ftl` to that window's resources — six on this build:
  `branding/brand.ftl`, `zotero.ftl`, `preferences.ftl`,
  `toolkit/global/textActions.ftl`, `toolkit/global/arrowscrollbox.ftl`,
  ours. `L10nRegistry.getInstance().generateBundlesSync(['en-US'], list)`
  yields 4 bundles with that list and 0 with our file missing, and a
  Localization over it then formats Zotero's `general-remove` as `null`:
  every pane loaded after ours in that window would render blank, Zotero's
  own included (panes already translated keep their text; the window
  loads panes lazily, `_loadPane`). Fluent's `{ path, optional: true }`
  resource form survives a missing file (3 bundles beside `zotero.ftl`),
  but a `<link rel="localization">` cannot say it and plugins.js 44–48
  declines it for the shared source. Gecko is not silent either: a
  resource missing at format time logs `Missing resource in locale
  en-US: <file>` to the error console.
- **The sandbox reaches the registry through Zotero's global.** Zotero's
  xpcom scripts are `loadSubScript`ed into a plain object of
  `zotero.mjs`'s module scope, so their global is the shared system
  global, where `L10nRegistry` and `L10nFileSource` are WebIDL
  constructors; `Components.utils.getGlobalForObject(Zotero)` hands the
  sandbox that global (measured from a sandbox shaped like `_loadScope`'s
  and from the live plugin scope: both `function`; the bare name is
  `undefined`, and so is `L10nRegistry.getInstance().sourceNames` —
  `hasSource` and `getSource(name).hasFile(locale, path)` are the readings
  that exist). `Services.appShell.hiddenDOMWindow.L10nRegistry` and the
  main window's are the same object.
- **The fix is a second source, built the way Zotero builds the shared
  one** (`core/l10n-source.ts`): `createMock('zotero-tts', 'app',
  Services.locale.availableLocales, 'zotero-tts:{locale}/', files)` with
  one entry per Zotero locale — 46 here — holding the closest shipped
  file (`Zotero.Utilities.Internal.resolveLocale` with `silent`, then
  the first `en*`, then the first shipped: `registerLocales`' own
  fallback, without which a locale the plugin lacks would lose the
  window's bundle wholesale). The two files are read from the xpi with
  `Zotero.File.getResourceAsync(rootURI + 'locale/<locale>/zotero-tts.ftl')`
  in the `own strings source` startup step, right after `strings`; the
  source leaves in `shutdown` before `setMessageSource(null)`, on the
  serialized chain the bootstrap keeps, so a reload's successor finds it
  gone and registers (`registered` in the log; `replaced` would mean the
  previous instance had not removed it). Two sources holding the same
  file id coexist: the bundles for `['zotero-tts.ftl']` go 1 → 2, the
  later-registered source wins where it defines a message and falls
  through where it does not, Zotero's strings and other plugins' files
  are untouched. The cost is 46 copies of a ~20 KB string in Rust
  memory, what Zotero's source already holds for the same file.
  `diagnostics.l10n().registry` reports `hasFile` of both sources and
  the bundle count.
- **Measured** (1.11.2-beta2 over 1.11.2-beta, macOS, Zotero
  10.0.2-beta.7, 2026-09-06 23:50–23:55). The install path: `stopped
  (reason 7)` → `Installed plugin` → `own strings source registered:
  en-US, zh-CN for 46 Zotero locales` (+4 ms) → `started`; `startup()`
  16 of 16; `registry` `{locale: "en-US", shared: "present", own:
  "present", bundles: 2}`; the pane 110 of 110 filled, Advanced 0 blank.
  The reload: `stopped (reason 4)` logged *after* `Calling bootstrap
  method 'startup' … ADDON_ENABLE` (the race, reproduced), then
  `registered`, then `started`; `sample` `Voice browser`, `registry`
  `{shared: "missing", own: "present", bundles: 1}` — Zotero's copy did
  go (the shared source's `zoteroif_preferences.ftl` stayed `present`,
  the bug's signature) and ours carried; chrome-scope
  `formatValueSync('ztts-heading-sync')` `Sync`; 0 errors naming
  `zotero-tts.ftl`, `translateFragment` or `[zotero-tts]`. `shared` stays
  `missing` for the rest of the session, until a restart or an in-place
  install. After the user's restart (00:0x) the cold start registered
  the source too — 16 of 16, `{present, present, 2}` — and a second
  reload reproduced the race again (2 of 2 on macOS); the settings
  window opened on the pane afterwards read 110 of 110 filled, the four
  provider switches `Disable / Enable / Enable / Enable` (their `label`,
  painted by `t()`), the 24 `?` icons intact, and Zotero's Advanced (16
  `data-l10n-id` elements) and Cite (9), loaded in that same window
  after ours, 0 blank each — the blast radius closed. A live
  `requestedLocales` switch to zh-CN read `语音浏览器` with the pane
  retranslated (110, none blank) and our source's zh-CN entry `present`
  while Zotero's was `missing`; a second in-place install put `shared`
  back to `present` and `bundles` to 2, `registered` again. In beta2
  `registry.locale` read `Zotero.locale`, which is fixed at startup and
  did not follow the switch (the tester's one correction); beta3 reads
  `Services.locale.appLocalesAsBCP47[0]`, the locale the registry
  resolves the file by, and the checklist expects `zh-CN` there.
- **Driving notes.** The debug store was off on this profile
  (`Zotero.Debug.enabled` 0, `storing` false); `Zotero.Debug.setStore(true)`
  turns it on for the session and writes no pref. The pane's four
  provider switches carry no `data-l10n-id` — `ui/provider-rows.ts`
  paints their `label` through `t()` — so a blank-count over
  `[data-l10n-id]` never sees them; read the `label`. Zotero quit on its
  own at 23:55:52, an orderly quit (`prefs.js` rewritten, no crash
  record), about a minute after the reload and with nothing but reads
  in between; the bridge was gone until the user started it again.
