## The Engine behind Read Aloud's manager: four hooks, and what the manager does around them (2026-09-23 17:20, issue #133)

Built on `xujialiu/engine` (ADR 0005, 0006). Read in the installed Zotero
10.0.3 (`Info.plist` 10.0.3, `application.ini` 10.0.3-beta.3, build
20260917121732); R = `resource/reader/reader.js`.

**The hooks.** The Engine answers the manager through four shadows, each
per tab (every tab has its own bundle and classes):

- `RemoteReadAloudVoice.prototype.getController` (R 40476): every voice of
  the Player is one, and `_createController` asks it (R 82664). The
  prototype is reachable from a live voice only.
- `ReadAloudManager.prototype.activeTimestamp` (R 82229-82235): null
  unless `this._controller instanceof RemoteReadAloudController` (82230);
  the shadow answers the same lookup without the test, and passes Read
  Aloud's own controllers to the original getter. The plugin's own
  `highlight-style.ts` reads the word through this getter too (its
  stand-in check, `start === 0 && end === 86400`).
- `ReadAloudManager.prototype.setSegments` (R 82543): only to patch the
  voice prototype in time. On a tab's first open there is no voice before
  the list lands, and from there to the first `getController` nothing of
  the plugin runs: `loadVoices` (82310) assigns `_allVoices`, runs
  `_resolveVoice` and `_stateChanged` (a microtask); the reader's
  `_onReadAloudEngineStateChanged` activates the manager (83871-83876),
  `_requestReadAloudSegments` awaits `_loadSDT()` and calls `setSegments`
  (84048-84075), which builds the controller. A `setTimeout` from the
  voices answer would lose that race whenever the structure is already
  loaded. `setSegments` is public, and precedes every first controller of
  a session: `_applyVoice` and `repositionTo` build one only with segments
  in place.
- `ReadAloudManager.prototype.repositionTo` (R 82621): sets a flag around
  the call, so the controller it builds starts where it was told.

**Why the jump flag.** `_createController` starts a new controller from the
active segment when it is still in the list, else from `_backwardStopIndex`
(82659-82663). Between two sentences `_activeSegment` is null
(`_handleSegmentEnd` sends `ActiveSegmentChange(null)`, 39490-39491), so a
voice list landing in the gap asks for a controller at the run's start —
the index a jump to the run's start would ask for too. Only the call that
made the rebuild tells the two apart.

**The rebuild pattern.** `_createController` calls `_destroyController()`
and then `getController` synchronously (82653-82664), so the old
controller's `destroy` is followed by the new request within the task.
The Engine ends a session only when a microtask after a `destroy` finds
no successor; `deactivate`, `clearSegments` and a tab's `destroy` leave
none. `_destroyController` also drops the manager's word
(`_activeTimestampIndex = null`, 82726), and nothing restates it until
the next word event, so a carried-on session restates its word a
microtask later, before the manager's own `_stateChanged` microtask
renders (the rebuild's caller queues that one after `getController`
returns).

**What the manager does on its own, kept as it is:**

- An `Error` event pauses the manager and not the controller
  (82703-82707): Read Aloud's controller stays unpaused, so a skip after
  an error plays on while the manager says paused. The Engine's session
  does the same.
- `_createController` sets `speed` before wiring its listeners and
  `paused` after (82670-82717), and Read Aloud's `paused` setter always
  speaks (39316-39323): a `play()` on a playing manager restarts the
  sentence. The Engine swallows only the first `paused` of a carried-on
  controller, which restates what already plays.

**What Read Aloud's engine does that is easy to get wrong in a copy:**

- `keepFetching` (40302-40327) asks for the second of a pair before the
  first: the first call starts the second before it awaits its own fetch.
  A server that answers one request at a time sees the next-but-one
  segment first. Kept (core/engine/read-ahead.ts `runReadAhead`).
- The next segment's head start in the read-ahead order is 10,000 ms of
  risk (40292-40295): a far slower segment after it can still go first.
- `_prefetchFrom`'s time left of the clip playing is in unstretched
  seconds, while each later segment's estimate is divided by the speed
  (40268, 40386-40390). Kept.
- Word timers fire in arming order when their delays are equal, so of
  several timings already under way at a resume the last one armed
  wins, not the latest start (40087-40103). The audio-clock word keeps that
  choice (core/engine/words.ts).

**Found on the way, not decided:** Zotero's own player popup plays its
voice samples through `RemoteSampleReadAloudController` (40404-40441),
whose chain `read-aloud/volume.ts` used to gain as well (it patched the
shared base). The Engine leaves samples to Read Aloud (ADR 0005), so with
*Use plugin player* off, a sample in Zotero's popup now plays at Zotero's
own level whatever the plugin's volume says. The voice browser's samples
set their element's volume themselves and are unaffected.
