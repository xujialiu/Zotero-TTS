## Player voice changes share preparation and paused resume (2026-09-15 00:15, issue #108)

The player and the shortcut previously had different transitions. Native
`selectVoice`, `selectTier` and persistent `setLanguage` resolve and apply
the new voice synchronously (`resource/reader/reader.js:82328–82364` in the
installed Zotero bundle). `_applyVoice` recreates the controller at the
current segment (`82507–82535`); native `play` unpauses that controller
(`82558–82568`). The shortcut's separate prepared handoff bypassed that
restart, but its paused branch selected immediately without fetching.

`voice-switch.ts` now attaches to those three manager operations. A
synchronous preview runs native choice resolution and the memory layer's
locale staging while `_applyVoice`, persistence and state notifications are
suppressed. The choice fields are restored before returning to the caller.
The memory layer excludes previews from its pick observer. At handoff the
resolved fields are applied and the native selection adopts the prepared
controller; the native selection still owns persistence and shared-voice
propagation. Picking the original voice cancels without recreating it, but
still passes through the native pick so an unchanged preference can be
learned by memory-sync's existing observer.

Pause keeps preparation alive and disarms any scheduled old-source stop.
The old controller and its offset remain the resume fallback. A prepared
resume uses a single identifiable paused word and the next word's actual
target timestamp. A grouped timestamp cannot identify that paused word:
the original voice finishes the sentence instead. With target audio still
pending, native playback resumes first and the usual prepared handoff
follows. A suspended target AudioContext can decode while paused; its
output is resumed only after Play. Skip, speed, stop, close and disposal
invalidate pending work, including delayed output startup.

Native `_getAudioData` retains in-flight promises and `destroy` clears its
maps without an abort API (`40329–40406`). Destroying a prepared controller
alone therefore did not cancel synthesis. Each pending switch now owns an
injected AbortController, and the composite interface captures its signal
by requested voice ID. Preparation requests deduplicate within that
signal, separately from ordinary playback, so cancelling one cannot stop
another caller. Cancelled results are not cached and preparation does not
launch the plugin's ahead-of-playback warmer. Zotero's official remote
interface exposes no request cancellation: its late result is discarded,
but no claim is made that an already submitted official request is stopped
or its quota returned.

The first paused-preparation regression failed with no requested segment.
The paused-resume and grouped-timestamp regressions independently reproduced
the old-voice resume and unsafe grouped-word jump. The initial full suite
passed 2,334 tests; the final original-voice re-pick check and correction
passed the 34-test handoff suite, typecheck and build. The live run uses
`1.12.10-beta`; its results belong on #108, with executed methods retained
in the voice-switch kit. Automated results do not establish listening
continuity or real-provider timestamp accuracy.

## What can be separated from Read Aloud (2026-09-15 14:31, issue #109)

The owner has decided to move the plugin off Zotero's Read Aloud step by
step while Zotero keeps the document analysis
([docs/PHILOSOPHY.md](../docs/PHILOSOPHY.md)). Before that end was chosen,
a research run put a cost on each piece, read in the installed
10.0.3-beta.1; its `reader.js` is byte-identical to the 2026-09-14 copy in
`.tmp`, so earlier line numbers hold. rj = `resource/reader/reader.js`,
wk = `resource/document-worker/worker.js`, xr = chrome `xpcom/reader.js`,
api = `xpcom/sync/syncAPIClient.js`. Facts were read in source unless
marked *inferred*.

- **Document analysis** runs in the document worker, started from chrome
  by `Zotero.SDT.getPack` (`sdt.js:81`) and cached as `.zotero-sdt-cache`
  beside the attachment (`sdt.js:26`); every reader open requests it
  (rj:83041). An ONNX clusterer cuts a PDF's blocks (wk:143973), an ONNX
  classifier labels them body, auxiliary or excluded (wk:144026), text
  repeated in the page's edge band on three or more pages is excluded
  (wk:156173), and a paragraph continues only through a part link
  (wk:155896). Size: 15.7k lines of PDF structure analysis over 126.7k of
  pdf.js core, a 13.5 MB ONNX runtime and 9 MB of models. Zotero does not
  keep it for Read Aloud alone.
- **The analysis is reachable without Read Aloud.** Chrome's
  `Zotero.SDT.getReader(itemID)` offers `materialize`, `getBlocks` and
  `getPageBlocks` (`structured-document-text.js:326-398`) with no tab open,
  generating the pack when it is missing; the sandbox can call it as it
  calls the sync API client (*inferred*). Inside a reader,
  `_internalReader._loadSDT()` returns `{structure, mapper}` (rj:84024),
  which the plugin already shadows (#87, #104). The position mapper
  converts both ways for PDF, EPUB and snapshot (rj:61874, 62484, 63053)
  and lives in the reader realm.
- **Segmentation is not reachable.** `buildSDTReadAloudSegments`
  (rj:71256), sentencex (rj:71596) and the mapper factory are private to
  the bundle, which exports only `window.createReader` (rj:85740);
  `View.getReadAloudSegments` is dead code (rj:72773). The only caller,
  `_requestReadAloudSegments` (rj:84048), returns unless the manager is
  active, and then builds a controller through `setSegments` (rj:82543).
  The builder itself needs only the structure, a granularity and a
  language: a port is about 870 lines, plus sentencex (7.6k lines) and eld
  (737 lines and 2 MB of data). Zotero and the plugin are both AGPL-3.0.
- **The highlight belongs to the player.** Zotero re-pushes its own
  highlight on every Read Aloud state change (rj:83388-83390, 83923), and
  the PDF view clears it unless the popup is open (rj:76434): a player of
  our own draws its own, or shadows that snapshot.
- **The player and its engine** are about 1,855 and 1,908 lines: the popup
  (rj:38480), a controller reading 3 segments ahead with 2 fetches at once
  (rj:40258-40260), a WSOLA time-stretch (rj:39755), an AudioContext chain
  (rj:39944) and the gap timer (rj:39405).
- **Zotero's Standard and Premium voices** stay reachable from a player of
  our own. `Zotero.Sync.Runner.getAPIClient({ apiKey })` speaks
  `tts/speak` (api:690, 854-856; a 402 is quota or daily limit,
  api:719-727) but bypasses Zotero's audio cache, so repeated text is
  billed again unless we cache it and honor `noStore` (*inferred*).
  `ReaderInstance.prototype._getReadAloudRemoteInterface` keeps that cache
  and needs an open reader window (xr:1749). Either way a replacement
  rebuilds the low-balance warning under 3 minutes (rj:82160), the
  purchase link and the first-run notice that Premium text goes to outside
  providers (`reader.ftl:249-258`).
- **The plugin today:** `src/read-aloud` is 9,509 of 25,237 lines —
  follow and highlight 2,476, analysis and segmentation patches 966,
  positions 1,225.

Not verified, and listed under Still open in NOTES.md:
`loadVoices(this._state.loggedIn)` (rj:84271, 82317) takes
`loggedIn = Zotero.Sync.Runner.enabled` (xr:270) and skips the remote
interface when it is false. The plugin's voices come through that
interface, and `src/` never reads `loggedIn`, so a user not signed in to
Zotero sync may see none of them.

## Provider entries built: a second shadow on _resolveVoice, a createElement wrapper, and the keys the memory follows (2026-09-15 17:05, issue #110)

Built in the `provider` worktree on `feat/provider-tiers`, test build
1.12.10-beta3, verification pending. What the build settled beyond the
plan comment, and what it turned up:

- **Two prototype shadows of one method from two undo logs.**
  provider-tiers.ts shadows `_resolveVoice` on the same prototype
  system-voices.ts does, through its own `createProtoPatches` log (the
  logs dedup per log, so both hold the pair). Attach order decides which
  is outer: the hiding attaches first everywhere (`onVoicesRequested`,
  `watchReader`), so the re-tag runs first and hands to the splice, and
  dispose runs the other way round (`stopProviderTiers` before
  `stopSystemVoiceHiding`) so the outer wrapper is unwound first and no
  zombie stays — the #38 shape memory-sync's move hook avoided by an own
  property. The re-tag's "tiers with voices" leaves every `local` voice
  that is not ours out, so the stranded rule is right whichever shadow
  runs first.
- **The tier of a plugin voice is read off its id, never off a list.**
  The response still says `local` (the parser's one key), and only the
  manager's objects say the provider after the re-tag, so memory-sync
  (`planSync`'s `tierVoices` key, `stageLanguagePick`'s pool) derives
  the key from the id through `pluginVoiceTier`, with the local engine's
  name from a new `localEngine` dep; the response's half of a list keeps
  `tier: 'local'` in every fixture. `PLUGIN_TIER` is `PUBLISHED_TIER`
  now, the response's key only.
- **The keys.** The provider id, except `local` → the engine's name
  lower-cased (`kokoro`); an unknown engine files under `local-engine`,
  never `local`. The OpenAI section's key is `openai` whatever the Server
  preset — only the entry's label follows the preset (`Xiaomi MiMo`,
  `Chatterbox-TTS-Server`; the "other" preset reads `OpenAI`), so the
  memory kept under `openai` survives a switch of server. The plan
  comment had left the OpenAI key open; noted on the issue.
- **When the stranded rule actually fires.** On every popup open Zotero's
  `applyPersistedVoices` clears `_selectedTier` and resolves against the
  *previous* list, so the tier the new list finds selected is the one that
  resolve landed on. With "Use one voice everywhere" on, memory-sync's
  reconcile stages the manager (`_selectedTier = null`) whenever the
  remembered voice is missing from the list about to land, and Zotero's
  own fallback then resolves the substitute — the stranded move never
  runs. It runs with the switch off, and whenever a tier is left selected
  that the new list lacks while the entry's voice is still listed; the
  case file checks it directly (`_selectedTier = 'azure'` +
  `_resolveVoice()`). "Remembered voice" in the rule is Zotero's entry
  voice for the language (`_persistedVoices.voice`), "default voice" the
  plugin's memory.
- **Zotero's two entries stay as Zotero builds them** — present and greyed
  when empty — while a provider's entry disappears when it has nothing to
  offer; `local` is dropped unless OS voices are still listed (the hiding
  not attached), so nothing is ever lost.
- **No migration, one exception.** Old `tierVoices.local` keys stay in the
  pref: `_findFallbackVoice` takes an empty target pool as "the whole
  pool" and `_applyVoice` sets the tier from the voice, so they are
  harmless and pile up under the provider keys. The system-voice adoption
  (issue #12) now moves its rewritten id from `local` to `system`, pushed
  last, since the plugin's copies carry that tier.
- **Wording that went with the Local tier.** `ztts-tier-local` is retired
  (the l10n diagnostic's `tier` probe reads Standard now), the substitute
  toast says "no other voice of Zotero-TTS is" in both locales, the
  Options key's help says "the voice mode", and `ztts-provider-system`
  names the System entry (系统). The voice browser's `tierLabel` became
  `zoteroTierLabel` in voice-catalog.ts; `pluginVoiceLabel` is gone.
- **Tests.** The realm-array fixture (`find` / `some` / `filter` / `map`
  answering nothing) is what every list handed to provider-tiers.ts is;
  vitest's `mock.contexts` proves the original `createElement` is called
  with the React object as `this`. The voice browser's fixture grew a
  second Azure multilingual voice so the two-row cases still have two
  rows under one entry.

- **Labels.** `ztts-tier-standard` / `-premium` now read `Zotero

- **`listBrowserVoices` re-added the hidden tier.** The pane's columns
  (`providerTierColumns`) left Standard out correctly, but the listing's
  safety net — "a provider that listed while the settings do not name it
  keeps its column" — took `listedColumns(catalog)`, which appends both
  of Zotero's tiers unconditionally, and put `Zotero Standard (0)` back;
  with everything off the two phantom columns made `tiers.length` 2, so
  the status line said "No voices" instead of "No provider is on". Fixed
  in 1.12.11-beta2: with the pane's columns given, only a plugin
  provider's column is merged back, never one of Zotero's (`isZoteroTier`);
  without them (the diagnostic, the tests) the old list stands.
- **`manager.languages` is the selected tier's list, not a union across
  tiers** (`voices` filters by `_selectedTier` first): a "both on" read
  gave 9 languages with Standard selected and ~67 with Fish. Language
  coverage is read off `_allVoices[i].language` (the field the manager's
  voice objects carry; `locale` is the plugin's `BrowserVoice` only).
- **`lastMove` is null after a close and reopen.** The stranded rule
  records a move only when `_selectedTier` is already a string when
  `_resolveVoice` runs; a stopped session carries none into its next
  resolve, and Zotero's own restore finds the hidden voice gone (the hide
  runs before it looks) and lands elsewhere by itself. Through the UI a
  Zotero tier can only be hidden after the reading guard stopped every
  session, so the rule is reachable only by writing `_selectedTier` on a
  live manager (`cases/provider-tiers.md` item 5 does).
- **Read `options` after the catalog settles.** Right after a popup
  opens, `providerTiers().options` can show the nothing-has-voices
  fallback (Zotero's three, greyed) while `tiers` in the same read is
  already right: the plugin's catalog (Fish's 339 voices) is still
  loading. A read 3 s later is correct; the kit polls until `tiers` and
  `options` stop changing, up to 6 s.
- Measured on the owner's profile: 28 Standard voices with 115 credits,
  1,452 Premium with 283 (`tts/credits`, credits not minutes); the
  pane has 17 groupboxes since #111 and #112 (the About case said 14 at
  1.11.7).
