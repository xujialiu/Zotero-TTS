## The store keeps the resume point, and a center is noisier than its rect (2026-08-31 00:30, issue #14)

The positions store now holds, for a PDF, exactly what resume reads: the
center of the first rect as a zero-area point, `normalizePosition` in
read-aloud-position.ts, with `resumeTarget` an alias of it — one normal
form, so what is stored and what is handed to Zotero can never drift.
Issue #14 holds the evidence for why (the unbounded rect list); this entry
holds what the fix itself taught.

- **An unrounded center made entries bigger.** Measured live before
  implementing: `(x1 + x2) / 2` over the store's 58-char single-rect PDF
  entry produced `204.20000000000005` — the "normalized" point serialized
  to 77 chars, larger than the raw position it replaced. Coordinates are
  therefore rounded to one decimal. That stays exactly idempotent
  (`(a + a) / 2 === a` in IEEE 754, and one more round trips nothing at
  coordinate magnitudes), and 0.05 PDF units cannot leave a glyph rect
  6–12 units tall. At the `.X5` boundary IEEE went up on this machine:
  `526.85 → 526.9`.
- **"Reduced the next time it is written" had a hole.** `writePositions`
  serializes the whole array on every flush, so a fat entry whose document
  is never played again would have gone out at full size on every flush
  until 50 newer documents rotated it off. The store is therefore
  normalized on load and marked dirty when that changed anything: the fat
  sheds on the first flush (~12 s after startup — the first idle tick past
  the 10 s throttle), listening or not. Live: 1,085 → 984 chars, the write
  landed +8–17 s after install (measured with two 8 s polling windows),
  re-running it produced a byte-identical result, every `ts` untouched,
  every selector entry byte-identical.
- **The silent freeze was `dirty = false`, not missing logging.** A failed
  `writePositions` was already reported twice — `guard()` calls
  `deps.error`, and `Zotero.Prefs.set` logs before rethrowing
  (xpcom/prefs.js:322-325). The bug was only that the failure was marked
  done, so nothing ever retried and the pref froze at its last good value.
  Keeping `dirty` alone would retry on every 500 ms active tick — a
  logError twice a second — so `lastWrite` now advances on failure too:
  one attempt per 10 s window until the write lands.
- **Zotero re-seeds the raw position on reader open.** Opening a PDF whose
  entry was already healed put the original 4-rect `savedPosition` back
  into `_state.readAloudState` (Zotero's own restore path), while the
  store held the point. `record` normalizes before `samePosition`, so the
  whole session left the entry's `ts` and 51 chars untouched; compared
  raw, every restart would rewrite every open document once. A newly
  spoken sentence went in normalized (51 chars) — the invariant holds for
  new writes, not only healed ones.
- The 4096-byte budget in `writePositions` counts UTF-8 bytes
  (`TextEncoder`), not string length — snapshot selectors can carry CJK
  text where the two differ by 3×. The newest entry is written even when
  it alone exceeds the budget: losing the freshest bookmark is worse than
  one oversized write. Interim while the store lives in a pref; #16
  deletes it with `MAX_POSITIONS`.

Verified live on 1.9.2-beta (Zotero 10.0.2-beta.1, macOS), full evidence
on the issue: heal exact to the predicted bytes; `Shift+Space` resume ran
with the healed point (trace `resume item 21785 target
{"pageIndex":1,"rects":[[526.9,485.2,526.9,485.2]]}`), popup open and
speaking on the stored page within 1.6 s; a restored already-normal store
survived a reinstall 25 s without a single write; no pref-size warnings,
no plugin errors. Re-verified as 1.9.4-beta6 after rebasing onto main
(#17–#21) — the pass had installed 1.9.2-beta over the main worktree's
1.9.3, a downgrade the rebase repaired.

`diagnostics.position()` now reports `{count, chars, entries:
[{key, ts, kind, chars, rects?}]}` and describes each reader's
`zoteroSaved` the same way instead of dumping either — the dump itself was
100 KB with one pathological entry, and a cross-compartment object
mid-teardown must describe as `unserializable`, not break the report.

## The positions moved into zotero-tts.sqlite, and the pass ran against a zombie (2026-08-31 02:25, issue #16)

The store left the pref for `new Zotero.DBConnection('zotero-tts')` →
`<data dir>/zotero-tts.sqlite`: `position-store.ts` owns the schema
(`PRAGMA user_version`), the one-time pref import (cleared only after the
insert transaction commits), the startup sweep, the load, a self-coalescing
serialized write queue (deletes ride the same queue, last op per key wins;
failed batches re-queue *behind* anything newer; retries gated to one per
10 s), and the permanent close. The sampler stays synchronous — `save()`
per changed sentence, the tick doubles as the retry heartbeat, throttle and
both caps deleted. A notifier observer on `('delete','item')` removes rows
from `extraData[id] = {libraryID, key}` — and stays synchronous, because
`Zotero.Notifier` *awaits* every observer (`notifier.js:167`). Shutdown:
`drain()` then `closeDatabase(true)`, each behind a 3 s `withTimeout`, the
close in a `finally` — Sqlite.sys.mjs blocks `profile-before-change` on
every open connection, so a leak is a 60 s AsyncShutdown hang.

Verified through the bridge, by SQL trace (Zotero's own DB logging shows
every statement): import 3 rows with original `ts`, pref deleted at libpref
level; one spoken sentence = one on-disk `REPLACE`; trash and restore touch
nothing, `eraseTx` deletes the row in ~1 s; erasing a *parent* deletes the
child attachment's row (children erase through their own `erase()`, no
`skipNotifier` — `item.js:5573`); an in-place reinstall logs `Closing
database` → `PRAGMA wal_checkpoint(TRUNCATE)` → `Database closed`, no
timeout, then reopens idempotently (no second `CREATE TABLE`).

What broke, and what it taught:

- **The first install failed against a half-uninstalled plugin.** Zotero's
  `addonVersions` map had lost the entry, so `onInstalling` skipped the old
  scope's shutdown/unload (`plugins.js:709-724`) and the orphaned prefs
  pane collided: `Pane with ID zotero-tts-pane already registered` — and
  `registerPrefsPane` is the one startup call outside any try/catch
  (`index.ts:997`), so the whole startup aborted. Installing the same xpi
  a second time recovered. Worth hardening some day: the pane failing
  should not take the voices down.
- **`_unloadScope` only deletes the map entry — the old sandbox lives on.**
  A 1.9.x zombie kept ticking all session: it re-created
  `readAloud.positions` after every playback (its own sampler), which the
  next startup then imported and swept (`imported 5 / swept 2` — an
  unplanned live proof of the sweep). `imported: 0` and the pref staying
  gone are only observable after a Zotero restart clears the zombie. The
  zombie also owned ambiguity over which copy patched the test reader —
  see the open item below.
- **HTML snapshots cannot be read aloud here at all**: `Zotero.SDT.getPack`
  answers `{ok:false, reason:"unavailable"}` and
  `_requestReadAloudSegments` bails without a pack
  (`reader.js:83737-83790`) — the manager sits `active` with
  `segments: null`. Playback fixtures must be PDFs.
- **A programmatic Read Aloud start hits the autoplay gate**
  (`NotAllowedError`, `reader.js:38319`);
  `reader._iframeWindow.document.notifyUserGestureActivation()` unblocks
  it, transiently.
- **A `cupsfilter` text→PDF is a useless highlight fixture**: all 60
  segments resolved to *two* distinct `sourcePosition`s — one whole-page
  rect per page — so word and sentence highlight both covered the page and
  the ~75 ms word→sentence swap at each boundary read as flashing. Word
  timestamps were real (Azure, 16 per sentence, `activeWordTimestamp:
  "real"`); the geometry was the document's. Not a bug; the blue is the
  shipped default (`#3478f6`@70, `addon/prefs.js:40`, 9d7005e).

Open, to re-check in a clean session: that test reader reported
`patched: false` in `diagnostics.highlight()` while plugin-styled colors
were visibly drawn, and the `attached to a PDF view` debug line never
appeared — consistent with the zombie's patch owning the reader, but not
proven. (The tester's quoted "slot" log lines exist in no version of the
source — a paraphrase, caught by `git log -S`; the color/rect readings, not
those quotes, are what the flicker verdict rests on.) After a restart: play
a PDF, expect `patched: true` and the attach line; if still false, that is
a real bookkeeping bug and gets its own issue.

## Clean session: the zombie owned the patches, and imported hit 0 (2026-08-31 02:35, issue #16)

The restart settled everything the poisoned session could not. The open
`patched: false` item closes as a zombie artifact, not a defect: in the
clean session the same fixture reader reports `patched: true`, both
`highlight style attached to a … view` debug lines appear, and
`sentenceSlot` is `"ours"` where the poisoned session said `"other"` — the
1.9.x sandbox had shadowed the views first, so the new instance's `attach`
never claimed them while the zombie's shadowing drew the colors.

The rest, field by field: the first start after the restart imported the
zombie's final pref write and swept its dead keys (`imported 6 / swept 3 /
loaded 3`), and the pref never came back — zero `Creating string pref`
hits across a full playback. The three original bookmarks came through the
real quit **byte-identical** (each row read back through a reopened
reader, not inferred from the count). An in-place reinstall then showed
the steady state: `imported 0 / swept 0`, no `CREATE TABLE`, no
`PRAGMA user_version = 1`, exactly one `Asynchronously opening database`,
and the deletion observer re-registered and fired the session's only
`DELETE` when the test item was erased. Zotero also logs `Database is on
apfs filesystem` at our open — the name-form connection getting the same
filesystem probing as Zotero's own.
