## The store keeps the resume point, and a center is noisier than its rect (2026-08-31 00:30, issue #14)

The positions store now holds, for a PDF, exactly what resume reads: the
center of the first rect as a zero-area point, `normalizePosition` in
read-aloud-position.ts, with `resumeTarget` an alias of it — one normal
form, so what is stored and what is handed to Zotero can never drift.
Issue #14 holds the evidence for why (the unbounded rect list); this entry
holds what the fix itself taught.

- **An unrounded center made entries bigger.** Measured live before
  implementing: `(x1 + x2) / 2` over the store's 58-char single-rect PDF
  entry produced `204.20000000000005` — the "normalized" point serialized
  to 77 chars, larger than the raw position it replaced. Coordinates are
  therefore rounded to one decimal. That stays exactly idempotent
  (`(a + a) / 2 === a` in IEEE 754, and one more round trips nothing at
  coordinate magnitudes), and 0.05 PDF units cannot leave a glyph rect
  6–12 units tall. At the `.X5` boundary IEEE went up on this machine:
  `526.85 → 526.9`.
- **"Reduced the next time it is written" had a hole.** `writePositions`
  serializes the whole array on every flush, so a fat entry whose document
  is never played again would have gone out at full size on every flush
  until 50 newer documents rotated it off. The store is therefore
  normalized on load and marked dirty when that changed anything: the fat
  sheds on the first flush (~12 s after startup — the first idle tick past
  the 10 s throttle), listening or not. Live: 1,085 → 984 chars, the write
  landed +8–17 s after install (measured with two 8 s polling windows),
  re-running it produced a byte-identical result, every `ts` untouched,
  every selector entry byte-identical.
- **The silent freeze was `dirty = false`, not missing logging.** A failed
  `writePositions` was already reported twice — `guard()` calls
  `deps.error`, and `Zotero.Prefs.set` logs before rethrowing
  (xpcom/prefs.js:322-325). The bug was only that the failure was marked
  done, so nothing ever retried and the pref froze at its last good value.
  Keeping `dirty` alone would retry on every 500 ms active tick — a
  logError twice a second — so `lastWrite` now advances on failure too:
  one attempt per 10 s window until the write lands.
- **Zotero re-seeds the raw position on reader open.** Opening a PDF whose
  entry was already healed put the original 4-rect `savedPosition` back
  into `_state.readAloudState` (Zotero's own restore path), while the
  store held the point. `record` normalizes before `samePosition`, so the
  whole session left the entry's `ts` and 51 chars untouched; compared
  raw, every restart would rewrite every open document once. A newly
  spoken sentence went in normalized (51 chars) — the invariant holds for
  new writes, not only healed ones.
- The 4096-byte budget in `writePositions` counts UTF-8 bytes
  (`TextEncoder`), not string length — snapshot selectors can carry CJK
  text where the two differ by 3×. The newest entry is written even when
  it alone exceeds the budget: losing the freshest bookmark is worse than
  one oversized write. Interim while the store lives in a pref; #16
  deletes it with `MAX_POSITIONS`.

Verified live on 1.9.2-beta (Zotero 10.0.2-beta.1, macOS), full evidence
on the issue: heal exact to the predicted bytes; `Shift+Space` resume ran
with the healed point (trace `resume item 21785 target
{"pageIndex":1,"rects":[[526.9,485.2,526.9,485.2]]}`), popup open and
speaking on the stored page within 1.6 s; a restored already-normal store
survived a reinstall 25 s without a single write; no pref-size warnings,
no plugin errors. Re-verified as 1.9.4-beta6 after rebasing onto main
(#17–#21) — the pass had installed 1.9.2-beta over the main worktree's
1.9.3, a downgrade the rebase repaired.

`diagnostics.position()` now reports `{count, chars, entries:
[{key, ts, kind, chars, rects?}]}` and describes each reader's
`zoteroSaved` the same way instead of dumping either — the dump itself was
100 KB with one pathological entry, and a cross-compartment object
mid-teardown must describe as `unserializable`, not break the report.

## The positions moved into zotero-tts.sqlite, and the pass ran against a zombie (2026-08-31 02:25, issue #16)

The store left the pref for `new Zotero.DBConnection('zotero-tts')` →
`<data dir>/zotero-tts.sqlite`: `position-store.ts` owns the schema
(`PRAGMA user_version`), the one-time pref import (cleared only after the
insert transaction commits), the startup sweep, the load, a self-coalescing
serialized write queue (deletes ride the same queue, last op per key wins;
failed batches re-queue *behind* anything newer; retries gated to one per
10 s), and the permanent close. The sampler stays synchronous — `save()`
per changed sentence, the tick doubles as the retry heartbeat, throttle and
both caps deleted. A notifier observer on `('delete','item')` removes rows
from `extraData[id] = {libraryID, key}` — and stays synchronous, because
`Zotero.Notifier` *awaits* every observer (`notifier.js:167`). Shutdown:
`drain()` then `closeDatabase(true)`, each behind a 3 s `withTimeout`, the
close in a `finally` — Sqlite.sys.mjs blocks `profile-before-change` on
every open connection, so a leak is a 60 s AsyncShutdown hang.

Verified through the bridge, by SQL trace (Zotero's own DB logging shows
every statement): import 3 rows with original `ts`, pref deleted at libpref
level; one spoken sentence = one on-disk `REPLACE`; trash and restore touch
nothing, `eraseTx` deletes the row in ~1 s; erasing a *parent* deletes the
child attachment's row (children erase through their own `erase()`, no
`skipNotifier` — `item.js:5573`); an in-place reinstall logs `Closing
database` → `PRAGMA wal_checkpoint(TRUNCATE)` → `Database closed`, no
timeout, then reopens idempotently (no second `CREATE TABLE`).

What broke, and what it taught:

- **The first install failed against a half-uninstalled plugin.** Zotero's
  `addonVersions` map had lost the entry, so `onInstalling` skipped the old
  scope's shutdown/unload (`plugins.js:709-724`) and the orphaned prefs
  pane collided: `Pane with ID zotero-tts-pane already registered` — and
  `registerPrefsPane` is the one startup call outside any try/catch
  (`index.ts:997`), so the whole startup aborted. Installing the same xpi
  a second time recovered. Worth hardening some day: the pane failing
  should not take the voices down.
- **`_unloadScope` only deletes the map entry — the old sandbox lives on.**
  A 1.9.x zombie kept ticking all session: it re-created
  `readAloud.positions` after every playback (its own sampler), which the
  next startup then imported and swept (`imported 5 / swept 2` — an
  unplanned live proof of the sweep). `imported: 0` and the pref staying
  gone are only observable after a Zotero restart clears the zombie. The
  zombie also owned ambiguity over which copy patched the test reader —
  see the open item below.
- **HTML snapshots cannot be read aloud here at all**: `Zotero.SDT.getPack`
  answers `{ok:false, reason:"unavailable"}` and
  `_requestReadAloudSegments` bails without a pack
  (`reader.js:83737-83790`) — the manager sits `active` with
  `segments: null`. Playback fixtures must be PDFs.
- **A programmatic Read Aloud start hits the autoplay gate**
  (`NotAllowedError`, `reader.js:38319`);
  `reader._iframeWindow.document.notifyUserGestureActivation()` unblocks
  it, transiently.
- **A `cupsfilter` text→PDF is a useless highlight fixture**: all 60
  segments resolved to *two* distinct `sourcePosition`s — one whole-page
  rect per page — so word and sentence highlight both covered the page and
  the ~75 ms word→sentence swap at each boundary read as flashing. Word
  timestamps were real (Azure, 16 per sentence, `activeWordTimestamp:
  "real"`); the geometry was the document's. Not a bug; the blue is the
  shipped default (`#3478f6`@70, `addon/prefs.js:40`, 9d7005e).

Open, to re-check in a clean session: that test reader reported
`patched: false` in `diagnostics.highlight()` while plugin-styled colors
were visibly drawn, and the `attached to a PDF view` debug line never
appeared — consistent with the zombie's patch owning the reader, but not
proven. (The tester's quoted "slot" log lines exist in no version of the
source — a paraphrase, caught by `git log -S`; the color/rect readings, not
those quotes, are what the flicker verdict rests on.) After a restart: play
a PDF, expect `patched: true` and the attach line; if still false, that is
a real bookkeeping bug and gets its own issue.

## Clean session: the zombie owned the patches, and imported hit 0 (2026-08-31 02:35, issue #16)

The restart settled everything the poisoned session could not. The open
`patched: false` item closes as a zombie artifact, not a defect: in the
clean session the same fixture reader reports `patched: true`, both
`highlight style attached to a … view` debug lines appear, and
`sentenceSlot` is `"ours"` where the poisoned session said `"other"` — the
1.9.x sandbox had shadowed the views first, so the new instance's `attach`
never claimed them while the zombie's shadowing drew the colors.

The rest, field by field: the first start after the restart imported the
zombie's final pref write and swept its dead keys (`imported 6 / swept 3 /
loaded 3`), and the pref never came back — zero `Creating string pref`
hits across a full playback. The three original bookmarks came through the
real quit **byte-identical** (each row read back through a reopened
reader, not inferred from the count). An in-place reinstall then showed
the steady state: `imported 0 / swept 0`, no `CREATE TABLE`, no
`PRAGMA user_version = 1`, exactly one `Asynchronously opening database`,
and the deletion observer re-registered and fired the session's only
`DELETE` when the test item was erased. Zotero also logs `Database is on
apfs filesystem` at our open — the name-form connection getting the same
filesystem probing as Zotero's own.

## The speed resolver was a looser mirror than Zotero's, and a fresh tab restores from the raw tag once (2026-08-31 11:00, issue #26)

Issue #26 holds the evidence (the disagreement table, the live traces);
this entry holds what Zotero does, verified in the 10.0.2-beta.1 bundle,
and what the fix is built on.

- **Zotero's `resolveLanguage`** (bundle 37977-38100,
  `src/common/read-aloud/lang.ts`): an exact key first, case-sensitively;
  else the keys whose *normalized* base matches — `normalizeLanguage` maps
  `cmn` → `zh` and the regions `XA`/`SA` → `001`, `CN`/`HK`/`TW` → none;
  `getBaseLanguage` is `lang.replace(/-.+$/g, '')`, so only a hyphen
  separates a region. Among the candidates: an exact regional match, then
  the region named by the first `navigator.languages` entry in that base
  language (no second try — a navigator `en-AU` against keys `en-GB,
  en-US` gives the first candidate, not the default), then
  `DEFAULT_REGIONS` (`zh` CN, `nl` NL, `en` US, `fr` FR, `pt` BR, `es`
  ES), then the first candidate. Ours split on `[-_]` and lowercased:
  it matched `en_US`, `EN`, `zh_CN` to the base language where Zotero
  matches nothing, and missed `cmn` ↔ `zh`.
- **The tag reaches the manager raw.** `sdt_segments_getSDTLang` (71241)
  returns `getBaseLanguage(props.language || props.Language ||
  props['dc:language'])`; `setLanguage` (82041) stores
  `getBaseLanguage(lang)` again. `en_US` from an EPUB's `dc:language`
  survives both, and so does `English` from a PDF's `/Lang` — the
  `"English"` key seen on 2026-08-27 and called harmless is this: Zotero
  reads and writes that document under `English`, and the plugin's
  speed-only entry was the right key by luck (an exact match).
- **A fresh tab restores once, from the raw tag, and the later move does
  not re-sync.** `_prepareReadAloud` (83983-83995): `loadVoices` (async,
  not awaited), a sync that returns on a null language, then
  `_loadSDT().then` → `setLanguage(docLang)` →
  `_syncPersistedVoicesToManager` (83883), which does
  `resolveLanguage(manager.lang, keys)`; null gives `{}`, i.e.
  `applyPersistedVoices({})` — which also clears `_voiceID` — and no
  `setSpeed`. When the voice list lands, `_resolveVoice` (82134-82143)
  finds no voice for base `en_US` and moves `_lang` to
  `getBaseLanguage(resolveLanguage(lang, languages) || languages[0])` =
  `en`, and `_onReadAloudEngineStateChanged` (83588) activates. None of
  the sync's four callers (83985, 83993, 84039, 84482) runs after that
  move. So for a document tagged `en_US` neither the speed nor the voice
  stored under `en` is restored on a tab's first open — a Zotero defect,
  upstream. A second popup open in the same tab syncs again, on `en` by
  then. memory-sync masks it whenever a voice is remembered: it moves the
  manager to the voice's lane before the restore runs.
- **The write side is symmetric.** `_persistCurrentVoice` (82100) writes
  under `getBaseLanguage(this._lang)` and xpcom `_setReadAloudVoice`
  (xpcom/reader.js 1730) stores the key verbatim: Zotero would create
  `en_US` itself. So the plugin's rule is now Zotero's — write under
  `resolveVoiceLang(lang, keys, preferred) ?? lang`.
- **The port.** `core/read-aloud-speed.ts` carries the three tables and
  the four steps line for line; `preferred` stands in for
  `navigator.languages`, which the sandbox has none of — index.ts reads it
  off an open reader's `_iframeWindow.navigator.languages` (Firefox derives
  it from `intl.accept_languages`, the same in every window), `[]`
  otherwise, which leaves `DEFAULT_REGIONS` to decide. It only matters
  among regional keys, which Zotero's own writes never produce.
  `planSync`, `entryRegion`, `readPersistedSpeed` and `persistSpeed` take
  it. `diagnostics.resolveVoiceLang(lang, keys?, preferred?)` runs the
  shipped function, so a live check pits it against Zotero's own, copied
  out of the bundle, rather than against a reimplementation.
- **Opening the popup starts playback.** `toggleReadAloudPopup(true)` →
  `_prepareReadAloud`, and `_onReadAloudEngineStateChanged` calls
  `activate()` as soon as a voice resolves with the popup open — a
  research run that opens the popup speaks (four times this morning).
  `_prepareReadAloud()` alone, popup closed, runs the same restore path
  without activating.

Verified live on 1.10.1-beta (Zotero 10.0.2-beta.1, Windows), evidence on
the issue: the shipped `diagnostics.resolveVoiceLang` against Zotero's
`resolveLanguage` copied out of the bundle, 15/15 agree; with "one speed
everywhere" on and "same voice" off, opening the `en_US` EPUB created
`en_US: { speed: 1.5 }`, left `en.speed` alone and put the manager at 1.5
while still on `en_US` (it stayed at 1 before); Zotero's own restore
applied an `en_US.speed` of 2.5 with both switches off; Shift+C in the
idle window wrote `en_US`, not `en`; the shipped defaults behaved as
before. Learned driving it:

- **Seeding `reader.readAloudVoices` while "one speed everywhere" is on
  is read as a user's speed change** — memory-sync's observer learns the
  moved `speed` and spreads it to every entry and the memory. Turn
  `readAloud.globalSpeed` off before seeding the pref, on again after.
- **An in-place upgrade followed at once by `Zotero.Reader.open` froze
  Zotero** ("Not Responding"; `_internalReader` still undefined 6.4 s
  after `open()` resolved, an RDP `ECONNRESET` just before) and needed a
  kill and a restart, which then ran Zotero's database integrity check.
  After the restart the same EPUB initialized in 0.7-0.9 s six times in
  a row with the same guard. One occurrence, not reproduced; recorded so
  the next one has a reference. A run installs, lets Zotero settle, and
  opens readers with a hard ceiling on `_internalReader` appearing.
- `_prepareReadAloud()` with the popup closed runs the whole restore
  path — `loadVoices`, `setLanguage(docLang)`, the shadowed sync, the
  `_resolveVoice` move — without activating: the way to drive it
  silently. The raw-tag window before the move is 0.3-1.1 s; acting
  inside it means polling at ≤20 ms in the same script. A sampling loop
  past ~6.5 s hits the bridge's eval ceiling and returns bare
  `undefined` with its side effects done.

## A startup step fails on its own now, and a diagnostic says which (2026-08-31 11:32, issue #25)

Issue #25 holds the incident — a pane collision after an in-place install
aborting the whole startup; this entry holds what was learned making a
failed step cost only itself.

- **`Zotero.ZoteroTTS` says nothing about startup.** It is assigned at
  module evaluation (the `Zotero.ZoteroTTS = {…}` at the bottom of
  index.ts), before `startup()` runs. This morning's run took
  `diagnostics.resolveVoiceLang` existing as proof that the build had
  started, and had proved only that the bundle evaluated.
  `diagnostics.startup()` is the proof now: `{ version, steps: [{ name,
  ok, error? }], failed }`, every step's outcome in order; the tester
  rulebook runs it right after every install, before anything else.
- **The steps.** `core/startup-steps.ts` — `runStartupSteps(steps,
  report)`: each `[name, fn]` awaited in order, a throw or rejection
  recorded as `{ ok: false, error: String(e) }` and handed to the
  reporter (which may not stop the run either), the next step run
  regardless. `startup()` is the list: legacy provider setting, settings
  pane, Read Aloud memory, reading-position store, highlight colors,
  system speech helper, system-voice hiding, Multiple-languages-first
  ordering, Read Aloud hook, Read Aloud shortcuts. The reporter does what
  the nine hand-written guards did — `Zotero.logError(e)` and a
  `[zotero-tts] failed to install the <step>: <error>` debug line — and
  the closing line names what is missing: `[zotero-tts] started without
  the settings pane`.
- **Why the pane collision costs nothing once survived.** The stale pane
  belongs to the zombie scope (`_unloadScope` deletes the map entry and
  the sandbox lives on — the 02:25 entry), and its XHTML `onload` calls
  `Zotero.ZoteroTTS.prefsPane.onPaneLoad(document)` — the global the new
  bundle reassigns the moment it evaluates. So the old pane runs the new
  pane code; no unregister-and-retry is needed, and fighting a
  still-running scope over the pane would buy nothing.
- **This morning's freeze** (an in-place install of 1.10.1-beta followed
  at once by `Zotero.Reader.open` — the 11:00 entry) may or may not have
  been this bug: nothing had checked whether startup completed, and the
  restart erased the evidence. The rulebook's new step-2 rule —
  `diagnostics.startup()` after an install, readers opened under a ~24 s
  ceiling on `_internalReader` — is what makes the next one attributable.

Verified live on 1.10.1-beta2, evidence on the issue: a clean in-place
install reports ten steps `ok`; with `Zotero.PreferencePanes.register`
shadowed to throw `Pane with ID zotero-tts-pane already registered` once
and the plugin reinstalled, the error lands in the error console with a
stack through `zotero-tts.js`, the log reads `failed to install the
settings pane: …` and `started without the settings pane`, the diagnostic
shows that one step failed and nine `ok`, the memory sync, the patches
and the shortcuts answer, and `pluginPanes` lacks the pane; the shadow
removed and one more reinstall, all ten `ok` and the pane back. Found on
the way, its own issue: **a reload (disable → enable,
`zotero_plugin_reload`) leaves a zombie** — bootstrap's `shutdown` clears
`Zotero.ZoteroTTS` after its await, on the new instance's global, so
that instance is never stopped again (#28). Restart the plugin with an
in-place reinstall, never a reload; a session that has reloaded needs a
Zotero restart before its evidence means anything.

## A reload ran two instances at once, and the old one took the new one's global (2026-08-31 11:56, issue #28)

Issue #28 holds the incident and the measurements; this entry holds
what Zotero does on a reload and what the bootstrap does about it.

- **Zotero's reload is a disable and an enable that do not wait for each
  other.** `AddonManager.addAddonListener` (xpcom/plugins.js 704)
  dispatches `onDisabled` (766-774: `await _callMethod(addon,
  'shutdown')`, then locales and default prefs) and `onEnabling`
  (755-764: `_loadScope`, `setDefaultPrefs`, `registerLocales`, `await
  _callMethod(addon, 'startup')`) as separate async callbacks. `_callMethod`
  awaits a promise a bootstrap method returns (258-261), but nothing
  makes the enable wait for the disable. An in-place install is different:
  `onUninstalling` → `onInstalling` run in sequence, and every upgrade
  logged today shows `[zotero-tts] stopped` before the next `started`.
- **So the bootstrap's `shutdown` cleared the wrong global.** `await
  Zotero.ZoteroTTS?.shutdown(); Zotero.ZoteroTTS = undefined;` — our
  `shutdown()` really waits (the position store drains and closes its
  database behind 3 s timeouts), the new bundle evaluates meanwhile and
  assigns `Zotero.ZoteroTTS`, and the old bootstrap's second line then
  lands on the new instance. From there `?.` short-circuits at every
  later shutdown and that instance is never stopped: an open
  `zotero-tts.sqlite` connection (Sqlite.sys.mjs blocks
  `profile-before-change` on it), leaked notifier observers, and its
  hook on `Zotero.Reader._readers.push` under everyone else's — the probe
  saw `_getReadAloudRemoteInterface` assigned twice on a pushed reader,
  the innermost (the zombie's) writing last. The "zombie owned the
  patches" of the 02:25 entry, produced on demand.
- **The fix is two waits on the one object both scopes share.**
  `shutdown` takes `const instance = Zotero.ZoteroTTS`, parks the promise
  of its shutdown on `Zotero.ZoteroTTSPendingShutdown`, and in a `finally`
  clears `Zotero.ZoteroTTS` only if it still is that instance; a failing
  `shutdown()` is `Zotero.logError`ed and the promise resolves anyway.
  `startup` does `await Zotero.ZoteroTTSPendingShutdown` before it loads
  the bundle. A reload thus becomes the serialized stop → start an
  install already is: the database closed, the observers gone and the
  patches undone before the next scope installs its own. Pinned by
  `test/bootstrap.test.ts`, which evaluates `addon/bootstrap.js` with a
  fake `Zotero`/`Services` (each `loadSubScript` minting an instance) and
  plays the race: a shutdown left pending while `startup` is called holds
  the bundle back and leaves the new global standing.
- **Zotero's own cleanup is not on that chain.** `_callMethod`
  (plugins.js 256-281) first awaits the bootstrap's shutdown and only then
  notifies its observers — among them the one that removes a plugin's
  preference panes (preferencePanes.js 183-199) — while the new `startup`
  resumes the moment the parked promise resolves. So on a reload from an
  instance holding the pane, `register`'s synchronous name check
  (preferencePanes.js 138-141) still found the old pane: the `settings
  pane` step failed (gracefully, #25) and the pane was gone until the next
  reload or reinstall. The repository never called
  `Zotero.PreferencePanes.unregister(id)` (synchronous, 172-175): now
  `shutdown()` removes the pane itself, first thing, and the observer
  finds nothing left.
- **Driving rule.** A plugin restart in a bridge run is an in-place
  reinstall (`zotero_plugin_install` with the same xpi), the path a real
  upgrade takes; `zotero_plugin_reload` is used only to verify this fix.
  A session that reloaded on a build before it needs a Zotero restart
  before its evidence means anything — the reload's zombie cannot be
  reached from outside (its global is gone, its observers are closures).

Verified live on 1.10.1-beta3 and -beta4, evidence on the issue: after
a reload `Zotero.ZoteroTTS` is an object (`undefined` before), the parked
promise is gone at rest, the `_readers.push` probe sees one assignment
(two before), the log has the old instance's `stopped` — `Closing
database`, `Database closed`, both notifier observers unregistered —
before the new `started`, and the reloaded instance logs the same on the
next reinstall (nothing, before); three reloads in a row chain their
observer ids without a gap. beta3 still lost the pane on a reload — the
observer race above — and beta4, which unregisters the pane in
`shutdown()`, registers it cleanly on every reload: no `Pane with ID`
error, no `unregistered due to shutdown` line. Learned driving it:
`zotero_clear_logs` clears `Zotero.Debug`'s output and the console, not
`Zotero.getErrors()`, and `Debug.get()` prints that store above a `====`
separator — the previous round's errors reappear after every clear and
read like a regression until the buffer is split at the separator.

## A release is checked from chrome scope, and the gear menu installs rather than offers (2026-08-31 12:35)

1.10.1 (#26, #25, #28) was released from the `xujialiu/b7` worktree —
the release and `update.json` commits made there, `main` fast-forwarded
with `git -C <primary checkout> merge --ff-only`, the tag on the
`chore: release` commit as before — and the update path verified through
the bridge instead of by hand. What that taught about Zotero's updater:

- **The `AddonManager` global of a chrome-scope eval is not the module.**
  `typeof AddonManager` is `"function"` there — the WebIDL constructor
  behind `navigator.mozAddonManager`, with no `getAddonByID`. The module
  is `ChromeUtils.importESModule('resource://gre/modules/AddonManager.sys.mjs').AddonManager`;
  a `typeof` guard picks the wrong one silently.
- **`addon.findUpdates(listener, UPDATE_WHEN_USER_REQUESTED)`** is the
  check: `onUpdateAvailable(addon, install)` with `install.version` and
  `install.sourceURI.spec` (the release asset), then
  `onUpdateFinished(addon, 0)` — 473 ms against raw.githubusercontent,
  no CDN lag. The gate is one line, `AddonUpdateChecker.sys.mjs:576`:
  `Services.vc.compare(newestVersion, update.version) >= 0` → skip;
  `1.10.1-beta4` vs `1.10.1` compares `-1` (a string suffix sorts before
  the bare number), so a beta build takes the release. The check leaves an
  `AddonInstall` in `STATE_AVAILABLE` behind; `install.cancel()` clears it
  without a download.
- **Tools → Plugins → gear → "Check for Plugin Updates" installs, it does
  not offer.** `aboutaddons.js:323-351`: its `onUpdateAvailable` calls
  `install.install()` whenever `AddonManager.shouldAutoUpdate(addon)` —
  true with `applyBackgroundUpdates` at its default and
  `extensions.update.autoUpdateDefault` on, which is every normal
  install. So after a release the beta on this machine upgrades itself
  at the next check, background or clicked; nothing waits for a yes.

## A bug hunt over the released 1.10.1, through the bridge: five runs, nine issues, and what Zotero showed (2026-08-31 16:01)

The release itself, not a branch: five verification briefs to the tester
agent — baseline, pane and providers; the voice browser; the Read Aloud
integration on a fixture PDF; shortcuts and the two-tab sync; resume,
colors and the lifecycle — plus two research follow-ups, every listed
behavior PASS except the ones that became issues, the user's prefs
restored byte-identically after every run, Zotero's credits untouched.
The fixtures were two hand-written PDFs (`make_fixtures.py` in the
session's scratchpad, not in the repo). What came out: #31 the voice
browser's status line clipped at the window's edge, #32 the
`defaultVoice()` diagnostic behind the pane, #33 the browser not scrolling
to the default, #34 the Server preset overwriting the user's Base URL,
#35 the metered fallback (critical), #36 the lane move undone by the
tier filter, #37 the stale list on a popup reopen, #38 an upgraded-over
tab served by the stopped instance, #39 two diagnostics that mislead.
The issues hold the evidence; this entry holds the Zotero facts, all
from the 10.0.2-beta.1 bundle (`resource/reader/reader.js` unless said).

- **Voice resolution, the whole chain.** `_resolveVoice` (82119-82171):
  the candidates are `getVoicesForLanguage(this.voices, lang)`, and
  `isLanguageSupported` (38014-38039) demands equal base languages — the
  only wildcard is `*` ("e.g. OpenAI"), so the plugin's `mul` is a
  language of its own that an `en` document never sees. If the current
  tier's `languages` lack the manager's base language the language is
  **reset** (82134-82143) — and `this.voices` (81994-81996) is filtered
  to `_selectedTier`, which `setLanguage` (82040-82057) does not clear.
  `_findFallbackVoice` (82173-82213): the target tier is `_selectedTier`
  or the last key of the entry's `tierVoices`; a tier with nothing for
  the language widens the pool to every tier; then the tier's voice, the
  entry's voice, a region match (`_region || persistedRegion ||
  getPreferredRegion`), else null and `voicesForLang[0]`.
  `_persistCurrentVoice` runs only under `_pendingSetVoice` — a user's
  pick — so a fallback is never written and never announced. That chain
  is why an unoffered `local::am_puck` under favorites-only lands on the
  one English favorite, Zotero's metered Standard voice (#35), and why
  a manager on Standard cannot be moved to `mul` by `setLanguage` alone
  (#36).
- **`_prepareReadAloud` (83983-83995)** starts `loadVoices` without
  awaiting it and runs `_syncPersistedVoicesToManager` on the list from
  the previous open; the `_loadSDT().then` block sets the language only
  while `lang` is unset, so a second call skips it. Nothing syncs again
  when the new list lands (#37, the shape of #26 on a later open).
- **A reader's remote interface is read once**, at `_open()`
  (`xpcom/reader.js:267`, kept at 82634 and handed to the manager at
  82024): a tab open across an in-place upgrade keeps the stopped
  instance's `getVoices`/`getAudio` for its whole life (#38), while the
  four prototype-shadowing modules re-attach to it at startup.
- **`selectTier()` and `selectVoice()` activate an idle manager** and
  start synthesis with the popup closed — not only the popup's open.
  `selectVoice(voiceID)` takes one argument in this build (82060): the
  persist is unconditional.
- **The end of a document rewinds**: `_handleSegmentEnd` sets
  `_position = _backwardStopIndex ?? 0` (39498-39500) and the manager
  stays `active`, paused — a short fixture restarts itself.
- **Replays never reach the plugin's cache**: `_getAudioData` (40320)
  answers a skip-back from the controller's own `_audioBuffers`.
- **Zotero's own position drop** is `_onChangeViewState` nulling the
  persisted `lastReadAloudPosition` when the view is more than five
  pages from it (84364-84366; `isPositionNearView` 76414-76419);
  `_state.readAloudState.savedPosition` stays until the next open, where
  it is seeded from the synced setting (82702) — what
  `diagnostics.position().zoteroSaved` reads is the copy that does not
  go null (#39).
- **The follow lock**: `lockPositionToReadAloud` (76357-76359) sets
  `view._readAloudPositionLocked`, `_onManualNavigation` (76639-76643)
  clears it, and the follow scrolls with `behavior: 'smooth'`
  (76331-76340, `scrollTo` at 76192-76200). Smooth scrolling did not
  animate in this Zotero window at all — Zotero's own follow included —
  so "the view comes back" is a check only eyes can make here.
- **Hidden views lose their canvases.** pdf.js discards a page's canvas
  and text layer when the view is not displayed — the window minimized
  for about 30 s, or the tab in the background — and `_handlePageDestroy`
  (75708-75711) empties `view._pages`; they come back 0.2-0.5 s after the
  view is shown. Not the plugin's doing, not an upgrade's: measured six
  ways, two of them in-place reinstalls with a session open and paused,
  which blanked nothing. What it touches is ours: `highlightStyling.attach`
  needs a rendered page, so an upgrade taken while a tab is hidden leaves
  that tab without the plugin's colors (comment on #38). One blank tab on
  a visible, focused window that did not recover was seen once (run 5)
  and never again; open, with no mechanism.
- **Size-zero text never reaches the segments.** A line drawn at
  `/F1 0 Tf` in a hand-written PDF is absent from Zotero's structured
  text, so #15's guard (`invisible-text.ts`) is never consulted; the
  latexit shape that guard was built for is an inline span at size zero
  in a transparent color, and only that shape exercises it.
- **`Zotero.getErrors()` behaves as a ring**: 26 entries through the
  whole day while the contents rotated. New errors are found by content
  and timestamp, and the debug store is the record. `diagnostics.highlight()`
  adds one error per call on a tab whose popup never opened (#39), which
  is how a read-only diagnostic evicted a day's evidence.
- **Driving, for the rulebook (updated today):** a trusted TIP keydown
  supplies the autoplay activation itself; `keydown()` returning 1 says
  only that someone consumed the key — the reader takes the arrows when
  the plugin declines; an options object built in chrome scope reads as
  empty in the reader compartment (`Cu.cloneInto` it); `zotero_execute_js`
  wraps only a top-level `return`; "Listing voices…" is caught only by
  opening the pane (`Zotero.Utilities.Internal.openPreferences`) and
  polling in one script, and `win.close()` is asynchronous.
- **Small things seen, no issue:** the favorites pref is an ordered array
  that `toggleFavoriteVoice` appends to, so an un-heart and re-heart
  reorders it — parsed-equal, not byte-identical, to a backup diff; the
  six Azure dialect locales (`zh-CN-guangxi` …) show as bare tags in the
  language column because `Intl.DisplayNames` has no name for them, as
  they do in the popup's dropdown; the shortcut rows repaint only from
  their own handlers, so a pref written from outside the pane leaves a
  row stale until the next click; the OpenAI section's heading stays

  follows its engine.

## Every pick of the Server dropdown was a first pick, so each server now keeps its own address (2026-08-31 16:55, issue #34)

Report, from the 1.10.1 bug hunt: with the OpenAI section on
Chatterbox-TTS-Server at its own address, opening the Server dropdown,
looking at OpenAI and switching back left `http://localhost:8004` in Base
URL — the preset's default, not the user's — and nothing in the pane said
so; the next Enable probed a server that was not there.

- **Cause.** The `command` handler in `ui/server-preset-rows.ts` wrote
  `openai.server` and then every key of `PRESETS[id].defaults`,
  unconditionally. The 2026-08-23 entry says a preset "fills its defaults
  once on switch (never on load)": that "once" only ever meant "not on
  load" — the code had no notion of a first pick against a later one, so
  every pick was a first pick. `other`, with no defaults, was the worst
  case: its address was overwritten on the way out and never written back
  on the way in.
- **Fix: each server keeps its own address and model.** One new string
  pref, `openai.presetValues`, a JSON object keyed by preset
  (`{"chatterbox":{"baseURL":…,"model":…},…}`; `readAloud.favoriteVoices`
  is the precedent for JSON in a string pref). `core/server-presets.ts`
  `switchPreset(remembered, from, to, current)` files the current
  baseURL+model under `from` and returns, for `to`, what is filed there
  with gaps filled from its defaults — so a first visit still fills the
  defaults the README promises, a revisit restores the user's values, and
  a first visit to `other` still writes nothing. Both fields are filed
  whether or not the preset uses them (Chatterbox ignores the model; it
  still comes back with the address). `parsePresetValues` keeps only known
  presets and string fields; anything else reads as an empty memory,
  which on the first switch behaves exactly as before the fix — nothing
  to migrate. The pref is in `DEFAULTS`/`prefs.js`, so the backup carries
  it (`settings-backup.ts` derives `KNOWN` from `DEFAULTS`); a pre-fix
  backup restores without it and leaves the install's memory alone.
- **Two details of the handler.** The preset being left must come from
  the prefs (`serverPreset(loadSettings(prefs).openai)`): when `command`
  fires, `menu.value` is already the new choice. And the values for `to`
  are read from the memory *after* the current ones were filed, so
  re-picking the current entry — which fires `command` like any other
  pick — files the current values and reads them straight back; read
  before filing, a re-pick would revert whatever the user typed since the
  last visit.
- **Rejected.** Filling only a field that is empty or holds some preset's
  default (no pref, three lines): a user with a custom address would no
  longer get `api.openai.com` filled in, and one who really switched and
  typed the OpenAI address would still lose the other server's on the way
  back. A memory kept only while the pane is open: reopen, switch back,
  gone again. A dropdown that only grays out: half its purpose gone.
- **Verified live** (1.10.2-beta through the bridge, the section unlocked,
  the prefs read after every pick, `presetValues` compared parsed against
  expectations written before the run): the issue's exact sequence —
  Chatterbox at `https://h200-chatterbox.xujialiu.top` → OpenAI
  (`api.openai.com` / `gpt-4o-mini-tts` filled, `presetValues` =
  `{chatterbox:{h200, tts-1}}`) → Chatterbox (the h200 address and `tts-1`
  back, `presetValues` gaining `openai:{…}`); the `other` round trip after
  setting a test address; a re-pick of the current entry after an edit
  keeps the edit; the memory survives closing and reopening the pane, and
  a load writes nothing. Enable afterwards: "Connected. 28 voices
  available. Synthesis works." No plugin errors; zero `can't access dead
  object` at the in-place upgrade.
- **For the next tester.** The key order inside `presetValues` changes
  between writes (`parsePresetValues` re-emits keys in `SERVER_PRESETS`
  order and a new `from` is appended), so compare it parsed, never as a
  string. `menuitem.doCommand()` on the menulist's item is a faithful
  pick: the menulist's own `command` handler selects the item before the
  plugin's listener reads `menu.value`. While the provider is on, the
  dropdown is locked with the fields (`provider-rows.ts` selects
  `input, menulist`), so a run clicks Disable first and Enable last.
