## Zotero's PDF follow measures a sentence by its first-page box and only asks whether the box's top is on screen, so a sentence continued on the next page or column is left cut (2026-09-10 10:12, issue #83)

**The user reported** a sentence half on screen while Read Aloud was
following a PDF — the start visible, the tail past the bottom edge, on
the next page or at the top of the next column — and Shift+Enter not
bringing the tail in. Two bridge runs settled it; the first chased a
different defect (the entry below), the second found this one.

**The rule** (Zotero 10.0.2-beta.9, BuildID 20260909034856 — Zotero
updated itself between the two runs, and every reader.js number of
beta.8 is 2 lower). The PDF view follows on every state push while the
position is locked: `setReadAloudState` (reader.js:76421) takes
`activePosition = state.activeSegment?.sourcePosition` (76430), the
sentence's position and never the word's, and its follow branch (76469)
calls `navigateToPosition(activePosition, { ifNeeded: true,
visibilityMargin: -innerHeight / 4, block: 'center', inline: 'nearest',
behavior: 'smooth' })` (76472–76479). `navigateToPosition` (76274)
measures the position with `getPositionBoundingViewRect` (77036) →
`getPositionBoundingRect(position, position.pageIndex)` (32305): the
box of the rects on the sentence's **first page**; `nextPageRects` come
back only for `pageIndex + 1`, which the follow never asks for. The
decision is `getScrollTarget` (75155): with `inline: 'nearest'` and
`ifNeeded` the position is "vertically visible" — nothing scrolls —
unless its top is below `scrollTop + clientHeight − innerHeight/4` or
its bottom above `scrollTop + innerHeight/4` (75171). The box's bottom
is never compared with the viewport's bottom edge, its top never with
the top edge; when it does scroll, the box's *top* goes to the center
line (`top = y − clientHeight/2 − 5`, 75183). A column-crossing
sentence's box spans the page (its tail's lines are near the page top),
so with the page top scrolled off it is "visible" by both tests.

**Measured** on a two-column IOVS article (10 pages, 429 sentences,
page-width zoom, viewport 1184 × 994): 3 sentences cross a page, 5
cross a column; simulating the follow over the whole paper, 7 (1.6 %)
are left partly off screen — 4 with the tail below, 3 above — 9 (2.1 %)
at a 700 px viewport and 11 (2.6 %) at 500 px, the overshoot's median
505 px. A single-column thesis (977 sentences): 0.2–0.6 %. Live, case A
(sentence 82, crossing a page): Zotero's box `[609, 2859, 1056, 2894]`,
the full extent `[128, 2859, 1056, 3738]` (879 px); the follow centered
the head at y 502 and left the tail 387 px below the bottom edge, 22
calls, none moving. Case B (sentence 101, crossing a column): box
`[498, 3645, 1055, 4384]` (739 px); head at y 561, tail 163 px above the
top edge, 18 calls, `scrollTop` pinned. Both fit the viewport: any
`scrollTop` in [2744, 2859] shows all of A, [3390, 3645] all of B. Only
3 of 429 sentences (0.7 %) are taller than the viewport.

**Shift+Enter cannot help by construction.** The key locks
(`lockPositionToReadAloud`, 76494, via `_lockPositionToReadAloud`,
84184) and re-emits the state, which lands in the same branch with the
same options: measured as exactly one `navigateToPosition` call and no
movement in 1.5 s, in both cases. Nor does `ifNeeded: false` on the
same call: for A it lands where it already is (the box is still the
first page's), for B it centers the box's top — the tail — and puts the
head 248 px below the bottom. The DOM views navigate to
`_collapseToStart(segmentSelector)` with the same margin (53248–53259):
the start only; not measured, not in #83.

**The fix's shape** is on #83's plan: measure the whole (both pages)
against the viewport's edges, center it when it fits, and follow the
part being read when it does not.

## The follow's own smooth scroll can drop the position lock: a flat 100 ms timer clears Zotero's "scrolling is mine" flag before the animation's late first frame (2026-09-10 10:14, issue #85)

Found by the first run of the day, before the user's report was
understood; a separate defect, with its own everyday triggers.

**The mechanism** (beta.8 numbers, BuildID 20260908212007). Around the
follow's call, `setReadAloudState` sets `this._readAloudScrolling =
true`, navigates with `behavior: 'smooth'`, and clears the flag through
`debounceUntilScrollFinishes(viewerContainer)` (76467–76485), which
resolves 100 ms after the last `scroll` event — or **100 ms flat when
none arrives** (31516–31534: the timeout is armed at once). The
container's scroll listener (75410–75418) treats every `scroll` event
that lands while the flag is down as the user's:
`_onManualNavigation()` (76774) → `_readAloudPositionLocked = false`,
and nothing follows again until `lockPositionToReadAloud()` (the
popup's skip buttons, the plugin's Shift+Enter, an unpause with the
position in view).

**Measured** (64-page thesis, Azure `en-US-AndrewNeural`, the view
instance's flags replaced by logging accessors):

- Visible and focused, the healthy case: the animation's first frame
  31–59 ms after the call (n = 4), 33–38 frames over 663–717 ms, the
  flag cleared ~110 ms after the last frame. The headroom against the
  timer is 41–69 ms.
- Window hidden: the flag cleared at +107 ms with no frame; the first
  frame at +1250 ms with the flag down → the drop, from the scroll
  listener; 27 more frames, each dropping it again.
- A tab switch: with the reader tab in the background the 100 ms timer
  is throttled to ~1 s (cleared at +1018 ms), pdf.js resets the
  container's `scrollTop` to the top when the tab is shown again (1243),
  the queued animation runs from there (first frame +1041 ms) → the
  drop, and a visible jump to the front of the document and back.
- Zoom in or out: one reflow `scroll` event with no follow in flight →
  the drop. A sidebar toggle's one event was absorbed only because a
  follow happened to be in flight.
- A 150 ms busy-wait right after the navigate did **not** reproduce it:
  the blocked main thread holds the timer too, and on unblocking the
  refresh tick runs first and re-arms the debounce.
- `behavior: 'instant'` in the same tab-switch scenario: the scroll
  lands synchronously, its one event arrives with the flag still up, no
  drop — the cure by construction.
- `general.smoothScroll` is false in this profile and the follow still
  animates: that pref governs wheel and key scrolling, not
  `scrollTo({ behavior: 'smooth' })`.
- Every push arms its own debouncer; six resolutions in a row were
  observed. An early one can clear the flag while a later animation is
  still producing frames — seen, not shown to have caused a drop alone.

**What the user meets:** switching tabs or windows while a PDF reads, a
covered or minimized window, a zoom — then nothing follows until
Shift+Enter, which can lose the lock the same way. The 2026-09-08 note
that the PDF's smooth scroll "holds still" in the bridge was this: a
hidden window's animation starting a second late. Issue #85, opened the
same day with this evidence and left unfixed for now; the user does not
report Zotero's defects upstream anymore.

## Bridge traps the two runs met, for the next brief (2026-09-10 10:16)

- **Never hook `container.scrollTo` from chrome.** The options dictionary
  crosses the compartment as empty and every call becomes a no-op; three
  "the follow never scrolls" readings were the hook's doing. Log around
  `navigateToPosition` on the view instance instead, and `cloneInto` any
  options object handed to `navigateToPosition` or `scrollTo`.
- **An instance hook needs `Cu.exportFunction(fn, Cu.waiveXrays(view),
  { defineAs })`**; a plain assignment lands on the Xray expando and the
  reader never sees it. Reader-realm arrays cannot take a chrome
  callback (`rects.map(chromeFn)` throws "Permission denied to pass
  object to privileged code"): index loops only.
- **`===` across the membrane is false.** In a chrome listener on the
  pdf.js document, `ev.target` is an Xray wrapper while the element
  reached through the waived view is waived; `isSameNode` is true. A
  filter written with `===` drops every event and looks dead.
- **`manager.jumpTo(sourcePosition)` lands on the preceding segment**
  (`onComputeRepositionIndex` resolves coarser); `manager.repositionTo(
  index)` (reader.js:82609, beta.9) is exact. Both set `_paused = false`,
  so freeze with `togglePaused()` before a screenshot.
- **`win.restore()` un-maximizes a window that is not minimized.** Read
  `windowState` first; a script that calls it at the top of every run
  silently took the window from maximized to normal.
- **`iw.browsingContext` is undefined on the reader's content window**;
  `drawSnapshot` goes through the main window's.
- **The audio device comes and goes** on this machine: the 2026-09-08
  "no output device" state (the AudioContext never resumes) held for the
  first run and was gone by the second, which spoke aloud — a
  script-started session then advances by itself and drifts a
  measurement. Check `manager._controller._audioContext.state` first.
- **Zotero updates itself between runs**: beta.8 → beta.9 in the middle
  of the day, every reader.js line number +2. Cite the BuildID with the
  numbers, and re-derive them for the build actually running.

## Settings sync is one shared file merged one setting at a time, and a check's flip stays at the file's stamp (2026-09-10 10:30, issue #68)

The two-way settings sync shipped behind *Sync settings between computers*
(`webdav.syncSettings`, default false), on top of the per-machine backup
files of #41, which stay as they are. What the design settled and why:

- **One shared file, per-setting recency — not "the newest machine file
  wins".** `zotero-tts-shared-settings.json` holds `{ key, value, ts, by }`
  per setting; each machine keeps, per setting, when it last changed it
  (`webdav.syncState`, an undeclared pref outside DEFAULTS like
  `webdav.machineId`, so a restored backup cannot carry one machine's
  stamps to another). A sync adopts an item strictly newer than the local
  stamp and pushes a stamp strictly newer than the file's; equal stamps do
  nothing, values equal or not. The whole-snapshot alternative loses an
  offline computer's change silently the first time it pulls a newer file,
  and cannot express "what changed here". `core/settings-sync.ts` is the
  pure half, `core/settings-sync-transport.ts` the transport, in the
  positions transport's shape (#40); the in-flight/trailing machinery both
  share moved to `core/single-flight.ts`, the positions tests unchanged.
- **Seeding: a setting still at its default has no opinion.** At the first
  sync with the switch on, every synced setting that differs from its
  default is stamped "now"; the rest stay unstamped and take the file's
  value. So the configured computer seeds the file whichever computer
  turns the switch on first, a fresh install joins and receives, and a
  setting set differently on two configured computers goes to the one
  that turned the switch on later — the one coin toss, said in the `?`.
  Stamping "now" on every key at switch-on would have made the newcomer
  overwrite the configured machine.
- **Stamps are written on every change, switch on or off**, so a change
  made while the switch was off keeps its true age when it goes back on;
  and the transport re-reads the state before every write (`updateState`)
  — a provider check can take 15 s, and a setting the user changes
  meanwhile must not have its stamp overwritten by the sync's bookkeeping.
- **The transport's own writes are flagged** (`applying`), and Zotero's
  pref observers fire synchronously inside `Zotero.Prefs.set`, which is
  exactly what lets a flag around the write keep the transport's observer
  from stamping an adoption as this machine's change.
- **A failed check's flip never travels.** A provider section with an
  adopted key is checked (the pane's check, split into a headless
  `runConnectionCheck` in `ui/prefs-pane.ts`); one that fails is switched
  off here with its `enabled` stamp set to the file's item's `ts` — or the
  stamp dropped when the file has no such item, which is the common case
  for `openai.enabled` since its default is true and defaults have no
  opinion. Equal stamps do nothing, so the flip is neither pushed (the
  working copy elsewhere stays on) nor re-applied (this machine stays off);
  it is remembered as `held` with the check's message, and the next
  adoption in that section turns it on and checks again. Without this a
  key that fails on one computer would switch the provider off on all of
  them, by way of the auto-observed flip.
- **The local-address rule is section-wide, decided on either side.** A
  provider section (`openai.*`, `local.*`) whose address is local —
  loopback, RFC 1918, link-local, 100.64/10, ULA/link-local v6,
  `.local`/`.lan`/`.home`/`.internal`, a bare hostname, anything that does
  not parse — is neither written into the file nor applied from it; a
  section the *file* puts at a local address (a hand-edited file) is not
  applied either. Filtering the address key alone would have carried the
  switch and the voice without the server behind them. The owner's rule
  (2026-09-10): a LAN address is local, no exceptions; a home NAS is
  configured once per computer. `openai.presetValues` travels with its
  section, presets at a local address stripped on the way up and merged
  preset by preset on the way down.
- **While a tab reads, the batch splits** — provider sections and the
  favorites pair wait for the next trigger after the reading stops, the
  rest (shortcuts, colors, delays, volume, prefetch, cache, the two Read
  Aloud switches) applies at once — unlike a restore, which refuses whole
  (ui/reading-guard.ts). The status line under the switch says how many
  wait.
- **The shutdown flush pushes only.** Adoption plus a provider check can
  outlast the 8 s bound every shutdown flush shares; the next start adopts.
- **Diagnostics never print a value that is a secret.** `settingsSync()`
  reports the stamps as keys and a count; `sharedSettings()` masks
  `apiKey`/`apiToken`/`password`/`headers`/`presetValues` values as a
  length. A push or an adoption is proved by the stamps and the counters.

What travels: every setting in the backup set except `webdav.*` (the
connection and the three switches) and `system.enabled` (a platform's) —
54 keys of 61 today — minus any held section. The default voice and the
remembered speed live outside the backup set and travel with neither the
backup nor this sync; that is #82.

## Live: a paused player anywhere defers provider items for as long as it stays open, the pane's own poke buries the applied line, and a dead URL logs twice (2026-09-10 10:50, issue #68)

The 1.11.7-beta pass through the bridge (11 of 13 checks; the tester's
table is on the issue) confirmed the design and taught three things:

- **The owner keeps a paused Read Aloud player open in a tab for hours.**
  The deferral gate is `playerStop.open()` over every reader, paused and
  never-started popups included (the reading guard's definition), so on
  that profile no provider-section item and no favorites change can apply
  until that one player closes — and the two checks that needed one to
  apply (the held-provider flip and the deferred voice's arrival) could not
  run without closing the user's session, which the tester rightly did
  not. It is the invariant of issue #11 at work, and the status line says
  how many wait; but a follow-up pass with no player open is still owed
  for item 20 of the checklist, and a user who wonders why a key change
  from the other computer "has not arrived" should look for a paused
  player first.
- **Opening the pane is a trigger, and its sync overwrote the line the
  user came to read.** The applied form (`2 from tester applied here`)
  lived about 100 ms before the pane-open sync's "nothing new" replaced it
  (measured with a poll inside one script; a second bridge call already saw
  the plain form). Fixed the same day: the line keeps naming the last batch
  that changed something here, with its own time
  (`ztts-sync-status-last`), and is hidden rather than blank while the
  switch is off (the empty description kept a line's height under the
  switch).
- **A dead WebDAV URL logs two errors per window, not one, on a profile
  with the auto-upload on** — `webdav.url` is in the auto-upload's watched
  set (61 keys), so changing it to the dead address queued an upload of
  the machine file that failed 2 s after the sync's own failure with the
  same message. Each feature keeps its one-report-per-window rule; the
  console just cannot tell them apart, `diagnostics.settingsUpload()` can.
- Measured for the record: the switch-on seed pushed 15 of 54 keys on the
  win11 profile, none of `webdav.*` although two of those switches are
  non-default; the change debounce fired at 10.8 s; the retry fired at
  exactly +60 s twice, unprompted; the recovered retry reported `deferred`
  (the voice still waiting on the player), which is the right outcome for
  a completed sync with something held back; and stamping is
  unconditional — a held section's keys are stamped and not pushed, so
  `state.stamped` is not the list of the file's keys.

## The follow's call is answered by the plugin: the whole sentence, both pages, against the viewport's edges (2026-09-10 11:47, issue #83)

**The fix** is `src/read-aloud/sentence-in-view.ts`, wired in
`index.ts` beside the highlight styling and attached where every
per-reader module is (`onVoicesRequested`, `watchReader`). It shadows
`navigateToPosition` on the PDF view's prototype per tab
(proto-patches.ts) and answers the follow's own calls — `ifNeeded`,
`inline: 'nearest'`, a negative `visibilityMargin`; no other caller has
that shape (reader.js:76472; the selection's call at 76721 is `block:
'nearest'`, the outline's, find's and annotation's pass no `ifNeeded`).
It measures the head (the first-page box, as Zotero does, 77036 step for
step) and the whole (the union with the next page's box when the
position carries `nextPageRects`), keeps Zotero's trigger on the head
(75171), adds "any part of the whole outside the viewport less a margin
of a fortieth of it, 8–24 px", and scrolls `#viewerContainer` itself
with the follow's own `behavior` — inside the call, so Zotero's
`_readAloudScrolling` flag and `debounceUntilScrollFinishes` around it
(76470–76485) work as before. The target: the whole's center when it
fits the viewport less twice the margin; for a taller sentence, the
center of the word being read when that leaves the viewport (real word
timing only — `highlightStyling.wordTiming`, the whole-segment stand-in
is not a word), or the head at the top edge plus the margin when there
is no word, once. A fitting sentence on which neither rule fires is left
to Zotero's method (`handled: false`), which keeps the horizontal axis;
a taller one is always ours, since Zotero's rule would center its head
again on every push after the word moved on. The same target is not
re-issued within 1.5 s (the follow calls on every word push, and the
targets do not depend on where the animation is). The scroll options are
cloned into the container's own window (`ownerDocument.defaultView`):
`scrollTo` reads a foreign dictionary as empty. A throw anywhere in the
measuring falls back to Zotero's call. `diagnostics.sentenceInView()`
reports the boxes, `fits`, `cut`, the word and the last decision; one
`[zotero-tts] sentence in view: <reason> on page N: scrollTop A -> B,
sentence H px, viewport CH px` line per scroll issued.

**Measured on 1.11.7-beta4** (the IOVS article, viewport 1198 × 1141,
Kokoro `af_alloy` at 3×, Zotero 10.0.2-beta.9): case A (sentence 82,
889 px, page-crossing) from the top of the document → one line, target
2768, the whole centered — Zotero's own would have been 2318.5, the tail
323 px below the edge; case B (101, 748 px, column-crossing) 3829 → 3492,
both column parts in view; the same cut state built by hand and a
trusted Shift+Enter → `return to spoken: pdf view, state kept` then the
`cut` line and the scroll. 30 s of playing over ten sentences: 4 lines,
one per sentence Zotero would also have scrolled for plus the cut ones.
The giant 220 (1283 px): no scroll while the word is on screen, then 4
`part` lines as the word crosses into the right column; the wordless
probe (the word position nulled on the view's state): the head to the
top edge plus 24, one line. A script scroll unlocks and the shadow goes
silent (`last.at` frozen across a `skipAhead` push); `{ block:
'nearest' }` passes through to Zotero's instant jump; no plugin errors,
0 dead-object errors over 5217 debug lines.

**Four things the run taught.**
- The line says `zotero` when Zotero's own trigger fires first — from
  the top of the document the head is far below — and `cut` when only
  ours does; the target is ours either way.
- A script scroll made while a state push is in flight does not unlock:
  the follow answers from the new position and pulls the view back, and
  the queued `scroll` event lands with `_readAloudScrolling` up. Pause,
  wait ~1.2 s, then scroll.
- At 3× the active word advances inside the animation, so two `part`
  lines 43 ms apart carry different exact targets and both go out; a
  genuinely identical target is suppressed (one line per case).
- **A hand-written two-column PDF does not get its crossing sentences
  joined.** A fixture D built like fixtures A–C (43-line columns, one
  sentence across the column break, one across the page break) came
  back as two segments each: 0 of 81 segments with `nextPageRects`, the
  column-crossing half merged with the sentence before it. Neither cut
  state could be built on it, so it was dropped; the checklist's §3a
  runs on the IOVS article, whose crossing sentences Zotero does join
  (3 of 429 with `nextPageRects`). Why the segmenter joins a journal's
  and not the fixture's was not dug out.

**Left open.** The DOM views navigate to the segment's start
(`_collapseToStart`, 53250) and are not covered; a wordless voice was
verified only by the probe above; the flag race of the entry above is
issue #85, unfixed; nothing was filed upstream, by the user's choice.

  `true` again, checks again, flips again — on every trigger. The resting

  transport itself was right, the fixture was not.

  morning, 14 in the afternoon (a default had been put back meanwhile).

  identifier, not a credential, but a 32-hex string the pre-push key scan
  flags; it joined the mask.
- **Beta numbers collide across worktrees again** (the #59/#60 lesson):
  the primary checkout had built 1.11.7-beta4 for #83 while this worktree
  was at beta3, and the tester's install of beta3 displaced it. Before
  naming a test build, read every worktree's manifest — this one's next
  is beta5 — and say in the brief which build the profile ran before.
- The Backup group's second button column was ragged (340 px against
  390 px, each row's hbox sizing itself); the first button of each row
  now carries an inline `min-width: 14em`, the shortcut rows' own way —
  a button rule in the pane's sheet must be macOS-only (issue #56,
  test/ui/pane-css.test.ts caught the first attempt).

## The held-provider flip measured, a switch turned back on between passes, and the key an adoption overwrites (2026-09-10 12:59, issue #68)

The third pass, on 1.11.7-beta5 with no player open, measured what the
two before could not (the tester's table is on the issue):

- **The flip stays home.** A crafted bad Azure key came down within 1.2 s
  of a reader open, the check answered `Connection failed: Azure voices
  returned 401`, `azure.enabled` went false here with its stamp at the
  file's item's ts, nothing was pushed, and the file kept `azure.enabled:
  true`; the next trigger adopted and checked nothing; the real key
  crafted newer turned the provider back on and the check passed. The
  deferred `azure.voice` applied at the `reader-close` that closed the
  fixture's player, its check passing too. Both status lines drew under
  their switches within ~570 ms of the pane opening; the "last change
  here" form appeared at ~200 ms and held.
- **The bad-key adoption overwrites the local pref**, so the real key must
  be kept before the fixture is written — the file's own body at the
  baseline, or the machine backup — not read from `azure.apiKey`
  afterwards. The checklist's item 20 says so.
- **The baseline was not what the previous pass had left.** Between the
  12:33 and the 12:43 passes the settings-sync switch had been turned on
  again by hand (the settings window had been left open on the pane), the
  transport re-seeded from the profile and put its 14 non-default keys —
  the Azure key, the Cloudflare token, the headers — back into the shared
  file on the folder. The tester reset it before its own run (switch off,
  file deleted, `webdav.syncState` cleared) and ended there. Two lessons:
  a pass reads the switch, the state pref and the file at its baseline
  and never assumes them clean; and turning the sync on is itself the act
  that writes this machine's keys into the shared file — by design, the
  folder already holds the machine backups with the same keys, but it is
  worth one sentence to the owner.
