## The voice list is a per-tab snapshot, so nothing may edit it while a tab reads (2026-08-30, issue #11)

*Hide System Local voices* was unguarded, and its two directions did not
match. **On** reached a tab that was already reading, destructively; **off**
did not reach it at all. Measured on 1.9.1-beta (Zotero 10.0.2-beta.1,
macOS), one reader, session active and paused, `en`, Local tier, 220 voices
(29 the plugin's, 191 the OS's):

| step | `_allVoices` | the voice being read | controller |
|---|---|---|---|
| picked `Local-Samantha` in the player | 220 | `local-…osx…Samantha` | #2 |
| switch on, nothing else | 220 | `local-…osx…Samantha` | same #2 |
| one tier chip (reader.js:38582) | **29** | **`azure::en-US-AndrewNeural`** | **new #3** |

One click moved the document from a free offline voice to a **paid** one and
restarted the sentence. Worse, and not in the issue as filed: `selectTier`
sets `_pendingSetVoice` (:82072), so the resolve ends in
`_persistCurrentVoice()` (:82166) — `reader.readAloudVoices` (`en.voice` and
`en.tierVoices.local`) and the plugin's `readAloud.memory` were both
rewritten from Samantha to the Azure voice. The damage outlives the tab, and
*Use one voice everywhere* would spread it. Off again, a tier chip and two
language picks left the list at 29 with `labelPatched: null` — no instance
left to reach `BrowserReadAloudVoice.prototype` through — and only
`loadVoices()` restored the 220.

**The fix is a rule, not a patch.** Deferring the switch instead — pinning
the pref to the moment `loadVoices` builds the list — was designed and
rejected: it ends the destruction but not the divergence. A tab whose player
opened before a change lists voices a tab opened after it does not, and *Use
one voice everywhere* then spreads a pick into a tab that has no such entry,
where `_resolveVoice` falls back exactly as measured. So every setting that
edits the list is refused while any tab is reading, and the invariant is
**every open player was built from the same settings** — the setting can
only move while no player is open anywhere, and each player opened
afterwards reads the settings as they then are.

The events, found by walking what `getVoices` depends on (`listCatalog` →
the enabled providers, `getFavoriteVoices`, and the hiding switch;
`_allVoices` is assigned in exactly one place, reader.js:82031): a provider
switched **on or off**; *Hide System Local voices*; *Offer only favorite
voices*; a ♥ marked **or unmarked** while only favorites are offered; a
settings restore from a file or from WebDAV. Two pre-existing holes of the
same kind went with them — enabling checked the guard before a connection
check that may take 15 s and never again (a player opened meanwhile still
got the write), and unmarking a ♥ was never guarded at all. Every guard
whose write follows an `await` now asks twice.

**A `preference=`-bound checkbox cannot be refused.** `_syncToPrefOnModify`
(chrome/content/zotero/preferences/preferences.js:465) dispatches
`beforesynctopreference` — a plain, non-cancelable Event — and then calls
`Zotero.Prefs.set`; the binding's listeners sit on `command`/`input`/`change`
(:542). So the two switches lost their binding and `ui/voice-list-switches.ts`
owns them: the box has already flipped itself by the time `command` fires, so
`checked` is what the user asked for and the pref is still what it was —
refused, the box goes back. The cost of unbinding is that nothing redraws
them any more, and both prefs are written from elsewhere (the System provider
turns the hiding on, a restore writes both), so each follows its own pref
observer.

**Verified live on 1.9.1-beta2**, one reader active and paused, through the
pane's own DOM:

| check | result |
|---|---|
| both boxes unbound, painted from their prefs | `preference` attribute gone, `checked` = pref for both |
| *Hide System Local voices* clicked while reading | pref unchanged, box back to its old state, notice naming the tab by title |
| *Offer only favorite voices* clicked while reading | the same |
| Azure's **Disable** clicked while reading | still "Disable", pref still true, fields still locked, the notice |
| a ♥ **unmarked** while only favorites are offered | glyph still ♥, 29 favorites still 29, the notice |
| the same two switches with the player closed | both write, both directions, no notice |
| the hiding pref written from chrome | the box follows, both ways (the observer replacing the binding) |

Only unit tests cover the restore refusal (its file picker needs a human)
and the re-check after the connection check (it needs a race). The notice
renders as the pane's own dialog, in Zotero's dark theme, as it has since
the first guard.

**Process note.** The bridge returned `{"type":"undefined"}` for two evals
that had in fact run to completion — both ended by closing the `<dialog>`.
The state was read back in a second call and was correct. Closing a modal
dialog and returning a value in the same eval is worth avoiding.

## Hiding Zotero's own Local voices became unconditional (2026-08-30 12:58, issue #17)

The *Hide System Local voices* switch, its pref
`readAloud.hideZoteroLocalVoices`, and the whole `Local-` marker are gone.
What is left of `read-aloud/system-voices.ts` is one shadow of
`_resolveVoice` that splices Zotero's own Local voices out of `_allVoices`,
every time, with nothing to read a setting from. `proto-patches.shadowGetter`
went with the marker — #9 (`498c476`) added it to shadow
`BrowserReadAloudVoice.prototype.label`, and nothing else in `src/` ever
called it; it is in git if an accessor ever needs shadowing again.

The reason it could go is #12: the system provider republishes the same SAPI
/ OneCore voices as `System-…` with word timestamps, the cache, samples and
the ♥, so the second copy the marker existed to tell apart has nothing left
to offer. The accepted cost is that a Windows user who never enables the
provider, and every macOS or Linux user until a helper exists there, sees no
operating-system voices at all.

### The unfiltered list can only be measured from chrome

The diagnostics cannot report what the splice removed: by the time
`diagnostics.systemVoices()` can look, `_resolveVoice` has already run and
`local-system` is 0 whatever happened. Two ways of getting the raw list
failed first:

- `await manager.loadVoices()` on a manager whose popup is **closed** leaves
  `_allVoices` empty (`voices: {}`). The issue #11 measurement, which used
  `loadVoices()` to get the unfiltered 15 back, only works while the session
  is still open.
- `Zotero.debug` from the plugin sandbox produced no `[zotero-tts]` line in
  `Zotero.Debug.get()`, even with `Zotero.Debug.init(true)` set inside the
  same eval. Not chased further.

What works is reading Zotero's own source straight from chrome:
`reader._iframeWindow.speechSynthesis.getVoices()`. That is exactly what
`BrowserReadAloudProvider` feeds into
`_allVoices = [...remoteVoices, ...browserVoices]`, so its length is the
unfiltered count — nine on this machine (three SAPI5 and three OneCore
English, three Chinese), the same nine issue #11 measured.

### Verified live on 1.9.2-beta

One reader tab opened for the purpose and closed afterwards. The retired pref
was written `false` — the value that used to mean "show them" — for the
decisive pass, then restored to `true`.

| check | result |
|---|---|
| `reader._iframeWindow.speechSynthesis.getVoices()` | **9** |
| player opened, pref `true` | `patched: true`, `{standard: 2, local-plugin: 6}` — no `local-system` |
| player opened, pref **`false`** | identical: `{standard: 2, local-plugin: 6}` |
| `diagnostics.patches().systemVoices` after the `false` pass | `1/1` — the `_resolveVoice` shadow alone; the old code would have added `label` |
| `diagnostics.systemProvider()` keys | `enabled, platform, unsupported, daemon, daemonAfter` — no `hideZoteroLocalVoices` |
| settings pane | no `ztts-hide-system-voices`, no help text naming the switch or the marker, 15 `?` icons (was 16) |
| errors at the end | 30, all Zotero One; none from the plugin |

`toggleReadAloudPopup(true)` opens the session **and starts speaking** —
`active: true, paused: false` half a second later. `toggleReadAloudPopup(false)`
stops it. Worth knowing before opening a player on someone's document just to
read its voice list.

**Process note.** `zotero_execute_js` returned `undefined` for two scripts
that read `doc.documentElement.innerHTML` on the settings window; the same
script without that expression answered normally. Adds to the same day's note
about evals that close a `<dialog>` — the bridge swallows a result for reasons
that are not always an exception.

## The ? sat on the note because a XUL `value` never wraps (2026-08-30 15:41, issue #18)

The *System voices* line and its `?` were drawn on top of each other: the
sentence measured 824 px in a box capped at 572 px, and the icon — laid out at
the box's edge — landed 252 px inside text that was still painting, on the word
"word-highlighted".

`style="max-width: 44em"` was written expecting the text to wrap there. It
cannot. A XUL `<description value="…">` is `white-space: nowrap` — toolkit's
`xul.css`, `:is(label, description)[value]` — whatever width the box is given,
and without a `crop` attribute nothing clips it either. **Text that can grow
goes in as a child node, never as `value`**; a `value` is for a word or two
whose length is known. The guard is in `test/ui/help-tips.test.ts`: no
`<description>` in the pane's markup carries a `value`.

The `?` icon has no margin of its own — `preferences.css` leans on the end
margin of whatever precedes it, which is why a checkbox already had a rule of
its own — and a `<description>` has none either, so once the sentence was gone
the two touched at 0 px. The checkbox rule was widened to `:is(checkbox,
description) + label.ztts-help[value]`.

Measured live on 1.9.4-beta2 (Zotero 10.0.2-beta.1, Windows): the note is 84 px
wide in a 584 px group, its right edge at 291 and the icon's left at 295 — the
4 px where every other `?` in the pane sits 5–6 px from what precedes it. The
note's computed `white-space` is `normal`, so a line that did grow would wrap
instead of running out.

**One `value` is left in the pane**, written from code rather than markup:
`ztts-voices-status` (`voice-browser-rows.ts:358` does `setAttribute('value',
…)`). Nothing is laid out beside it, so nothing can be overlapped; a long line
runs past the group instead — a 109-character "Default cleared: …" probe
measured 41 px past the groupbox's right edge. Left alone, outside the issue's
scope.
## Gecko's password reveal button is on in Zotero, and the pref does not say so (2026-08-30 15:57, issue #19)

The two **Extra headers** fields were `type="text"` while holding a
Cloudflare Access service token; issue #19 masked them. The issue's stated
reason — that Gecko's own reveal button is off in Zotero, so masking a
field whose `Name: value` pairs `core/headers.ts` drops silently would leave
a typo undiagnosable — **is wrong**, and the verification pass on
1.9.4-beta (Zotero 10.0.2-beta.1, Firefox 140, Windows) is what showed it.
Once corrected the whole feature became one attribute per field and one line
in provider-rows.

- **The pref is `false` and the button is there anyway.**
  `layout.forms.reveal-password-button.enabled` exists
  (`Services.prefs.getPrefType` → 128), has no user value, and reads
  `false` — while every `type="password"` input in the pane draws the eye.
  Do not ask the pref. Ask the anonymous content:
  `InspectorUtils.getChildrenForNode(input, true, false)` returns
  `[button, div]`, or `[div, button, div]` when the input has a
  `placeholder` (the placeholder div comes first — indexing `[0]` for the
  button is a bug). The button is `display: block`, 13×13 px at the input's
  right edge, and `visibility: hidden` while the field is empty.
- **It cannot be styled away.** Neither `input::-moz-reveal` nor
  `input::reveal` with `display: none !important` moves it, from a pane
  stylesheet or anywhere else we can reach: `block/visible/13px` before and
  after. `elementFromPoint` over it returns the host input, not the button.
  A pane that masks a field gets Gecko's eye whether it wants one or not.
- **It is inert on a `disabled` input.** A click sets `input.revealPassword`
  true on an editable field and does nothing at all on a disabled one —
  still drawn, still `pointer-events: auto`, no effect. Since provider-rows
  locks a section's fields while its provider is on, this is the whole of
  the wanted behavior for free: on = the value cannot be read by anything,
  off = you are editing, and the field's own eye reads it back.
- **But disabling does not clear `revealPassword`.** Reveal a field while
  the section is unlocked, then Enable: `disabled` goes true and the value
  **stays in the clear** — and the eye is now inert, so nothing can put it
  back short of reopening the pane. That is the one line the plugin owes
  this: `provider-rows.ts` `paint()` clears `revealPassword` on every
  `type="password"` field it locks. Traced through all four stages before
  and after the fix.
- **`input.type = 'text'` clears `revealPassword`** as a side effect, so a
  control that flips the type composes with the eye instead of leaving a
  field stuck visible. Not used any more, but it is what made the
  Show / Hide version safe.
- **An empty `type="password"` still matches `:placeholder-shown`** —
  measured in this build with a throwaway input in the pane document: text
  empty `true`, password empty `true`, password filled `false`. Masking
  costs a field no placeholder, which is what let the header fields keep
  their `Name: value; Name: value` hint.

**Process, for the next pane verification.**

- A plugin pane's content is inserted **lazily**. `zotero_open_preferences`
  with the plugin id opens the window and reports the pane, but
  `#prefs-content > .pane-container` for it stays empty and every `.ztts-*`
  query answers zero. What fills it is
  `Zotero_Preferences.navigateToPane('zotero-tts-pane')` on
  `Services.wm.getMostRecentWindow('zotero:pref')`, awaited, then a beat.
  A new build needs the window closed and reopened; the markup is not
  re-read otherwise.
- **`Zotero.Prefs.set` takes names relative to `extensions.zotero.` unless
  the third argument is `true`.** `Zotero.Prefs.set('extensions.zotero.zotero-tts.openai.enabled', true)`
  silently creates `extensions.zotero.extensions.zotero.zotero-tts.openai.enabled`
  and changes nothing. `Zotero.Prefs.get(name, true)` reads the full name
  with two arguments, which is what makes the asymmetry easy to miss.
- **Test connection is a pref-free way to exercise the section lock.**
  `onTest` ends in the same `paint(id)` the switch runs and writes no pref
  whatever the outcome — so a repaint can be provoked without toggling a
  provider on a machine whose server may be down.
- Do not verify a lock by clicking **Enable** on someone's working
  provider: Enable only goes back on if its connection check passes, and
  the Chatterbox server answered 502 during this pass, leaving the provider
  off. Restoring it meant writing the pref directly.

## A restored backup turned providers on without checking them (2026-08-30 17:42, issue #21)

`Enable` is a commit point: the connection check has to pass before the
switch pref goes on, which is why the voice browser lists on the switch
alone — no pref watching, no debounce (`ui/provider-rows.ts`). **The two
restore paths went around it.** `core/settings-backup.ts` `applyBackup`
writes every key the file holds, `openai.enabled` through `system.enabled`
among them, and `onRestored` only repaints. So a backup from another
machine — a local engine at `http://localhost:8880` that is not running
here, a key rotated since, an expired Cloudflare token — left a section
reading **Disable** with its fields locked, exactly as after a check that
passed, and a provider that plays nothing.

The fix is `providerRows.verifyEnabled()`, awaited by both restore paths:
every provider the restored prefs turn on is checked as Enable would check
it, in parallel (each is bounded by its own timeout; four in a row would be
a minute of a pane that looks frozen), and one that fails goes back off with
its message in the same line Enable writes to. The reading guard is not
asked a second time — the restore already refused if a tab was reading, and
all this can do is turn a switch *off*, back toward the state before it.

**Verified live** on 1.9.4-beta5 with a hand-written backup file: a snapshot
of the real prefs with `local.baseURL` pointed at `http://localhost:9999`
and all four `enabled` true. Restoring it turned Kokoro-FastAPI off with
"Local TTS server is not running at that address." and left the other three
on.

### What the bridge cannot do to a plugin pane

Three of these cost most of the session.

- **A chrome-scope monkey patch is invisible to the plugin sandbox.**
  Patching `FilePicker.prototype.show` from `zotero_execute_js` to stub the
  file dialog does nothing: the sandbox is another compartment and sees the
  module through an Xray, which hides an expando added on our side. The
  sandbox therefore calls the **real** `show()` — and `nsIFilePicker.show()`
  is async and does not block the main thread, so every symptom points the
  wrong way: the script returns normally, the message line stays `null`, the
  patch's call counter stays 0, no error is logged, and native save dialogs
  quietly pile up on the desktop. Anything of the pane that goes through a
  file dialog is a hand round for the user, always. (`FilePicker.file` is
  also a prototype getter, so `this.file = path` throws in strict mode —
  shadow it with `Object.defineProperty` if ever patching from inside.)
- **`nsIEventListenerService.getListenerInfoFor` does not report the
  sandbox's listeners.** It answered `click, command, keypress, keypress`
  identically for a button whose plugin handler ran and one whose handler
  appeared not to, so it cannot be used to ask "did the plugin attach
  here?". Those four are MozButton's own. Ask a side effect instead — a
  dialog-free handler such as *Test connection* writing its line.
- **Calling `onPaneLoad` twice on one document doubles every listener**, and
  the damage is not obvious: the user reported "I can't disable". One click
  on **Disable** ran both handlers — the first switched the provider off,
  the second saw it off and ran the Enable branch, whose check passed, so it
  came straight back on. Never re-run it to "reinitialize"; close the
  settings window and reopen it.

A synthetic `new win.Event('command', { bubbles: true })` on a pane button
does reach the plugin's handler — that part works, and is how the switches,
Test connection and the WebDAV buttons were driven all session.
