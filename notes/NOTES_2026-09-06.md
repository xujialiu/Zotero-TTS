## Xiaomi MiMo's TTS is a chat completion, and the plugin's OpenAI section learned that route (2026-09-06 01:12, issue #50)

A user could not connect Xiaomi's MiMo-V2.5-TTS through *Other
OpenAI-compatible server*: Test connection said "Connected, but synthesis
failed: OpenAI speech: HTTP 404". Probed live against
`https://api.xiaomimimo.com/v1` with the user's key before anything was
written; what the API actually does, kept here so the next session need
not probe again:

- `/v1/models` answers (401 without a key, 200 with one) and lists
  `mimo-v2.5`, `mimo-v2.5-asr`, `mimo-v2.5-pro`, `mimo-v2.5-tts`,
  `mimo-v2.5-tts-voiceclone`, `mimo-v2.5-tts-voicedesign`. **`/v1/audio/speech`
  and `/v1/audio/voices` are 404 at the gateway** (an openresty HTML page),
  key or no key. That is the whole report: the model list passed
  ("Connected"), the two-character probe on the speech route failed
  ("synthesis failed: HTTP 404").
- Speech is `POST /v1/chat/completions` with the text in an **`assistant`**
  message — `{ model, messages: [{ role: "assistant", content }],
  audio: { format, voice } }`; a `user` message is an optional style
  instruction, left out. The reply is an ordinary chat completion whose
  `choices[0].message` has `content: ""` and `audio: { id, data: <base64>,
  expires_at: null, transcript: null }` — the shape OpenAI gave its audio
  chat models. Formats: `wav` (24 kHz, 16-bit mono), `mp3` (64 kbps; 45 KB
  for 5.7 s where the wav is 269 KB), `pcm`, `pcm16`; anything else is a
  400 whose `param` names those four. A sentence took 2.5–2.9 s.
  `stream: true` works (pcm16 pieces under `choices[0].delta.audio.data`)
  and is not used: Read Aloud takes one blob per segment.
- **No timestamps of any kind.** `transcript` is null in every reply,
  streaming chunks carry only audio, and `timestamps`, `word_timestamps`
  and `return_timestamps` in the request are ignored without an error. So
  sentence highlighting, exactly as on OpenAI's speech route.
- Voice ids are the documented names, the Chinese ones as they are
  (`冰糖` worked verbatim): `mimo_default`, `冰糖`, `茉莉`, `苏打`, `白桦`,
  `Mia`, `Chloe`, `Milo`, `Dean`. A wrong one is a 400 in OpenAI's error
  shape with the detail in **`param`**, not `message` — `{ "error": {
  "code": "400", "message": "Param Incorrect", "param": "Unknown voice:
  alloy. Available voices: [mimo_default, 冰糖, …]", "type": "" } }` —
  where OpenAI puts the detail in `message` and the field name in
  `param`; the provider's `serverReason` therefore quotes the longer of
  the two after the status, so the pane says which voices exist.
  `Authorization: Bearer` is accepted (the docs also offer an `api-key`
  header). The platform calls the TTS models "free for a limited time".

What it became: a **Xiaomi MiMo** entry in the OpenAI section's Server
dropdown. `core/server-presets.ts` gives every preset a `synthesis` route
(`speech`, OpenAI's `/v1/audio/speech`, for the three that existed; `chat`
for MiMo), MiMo the documented voices as its fallback list (there is no
list to ask for) and `voiceName: 'MiMo'`, so the player and the voice
browser say `MiMo-冰糖` rather than `OpenAI-冰糖`
(`read-aloud/catalog.ts`). `providers/openai.ts` folds `synthesize` and
`checkSynthesis` into one `speak()` that posts on the configured route,
decodes the base64 mp3 into an `audio/mpeg` Blob and treats a reply
without audio — a chat model in the Model field — as a `SynthesisError`
at Test connection and while reading alike. The result carries
`note: 'audio through /v1/chat/completions'`, which the per-segment debug
line shows when there are no timestamps — the proof the chat route
answered, since the speech route cannot on this server. Weighed and
rejected, on the issue: a provider section of its own, an automatic
fallback to the chat route on a 404, the voiceclone/voicedesign models,
streaming.
