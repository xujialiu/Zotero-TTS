## Xiaomi MiMo's TTS is a chat completion, and the plugin's OpenAI section learned that route (2026-09-06 01:12, issue #50)

A user could not connect Xiaomi's MiMo-V2.5-TTS through *Other
OpenAI-compatible server*: Test connection said "Connected, but synthesis
failed: OpenAI speech: HTTP 404". Probed live against
`https://api.xiaomimimo.com/v1` with the user's key before anything was
written; what the API actually does, kept here so the next session need
not probe again:

- `/v1/models` answers (401 without a key, 200 with one) and lists
  `mimo-v2.5`, `mimo-v2.5-asr`, `mimo-v2.5-pro`, `mimo-v2.5-tts`,
  `mimo-v2.5-tts-voiceclone`, `mimo-v2.5-tts-voicedesign`. **`/v1/audio/speech`
  and `/v1/audio/voices` are 404 at the gateway** (an openresty HTML page),
  key or no key. That is the whole report: the model list passed
  ("Connected"), the two-character probe on the speech route failed
  ("synthesis failed: HTTP 404").
- Speech is `POST /v1/chat/completions` with the text in an **`assistant`**
  message — `{ model, messages: [{ role: "assistant", content }],
  audio: { format, voice } }`; a `user` message is an optional style
  instruction, left out. The reply is an ordinary chat completion whose
  `choices[0].message` has `content: ""` and `audio: { id, data: <base64>,
  expires_at: null, transcript: null }` — the shape OpenAI gave its audio
  chat models. Formats: `wav` (24 kHz, 16-bit mono), `mp3` (64 kbps; 45 KB
  for 5.7 s where the wav is 269 KB), `pcm`, `pcm16`; anything else is a
  400 whose `param` names those four. A sentence took 2.5–2.9 s.
  `stream: true` works (pcm16 pieces under `choices[0].delta.audio.data`)
  and is not used: Read Aloud takes one blob per segment.
- **No timestamps of any kind.** `transcript` is null in every reply,
  streaming chunks carry only audio, and `timestamps`, `word_timestamps`
  and `return_timestamps` in the request are ignored without an error. So
  sentence highlighting, exactly as on OpenAI's speech route.
- Voice ids are the documented names, the Chinese ones as they are
  (`冰糖` worked verbatim): `mimo_default`, `冰糖`, `茉莉`, `苏打`, `白桦`,
  `Mia`, `Chloe`, `Milo`, `Dean`. A wrong one is a 400 in OpenAI's error
  shape with the detail in **`param`**, not `message` — `{ "error": {
  "code": "400", "message": "Param Incorrect", "param": "Unknown voice:
  alloy. Available voices: [mimo_default, 冰糖, …]", "type": "" } }` —
  where OpenAI puts the detail in `message` and the field name in
  `param`; the provider's `serverReason` therefore quotes the longer of
  the two after the status, so the pane says which voices exist.
  `Authorization: Bearer` is accepted (the docs also offer an `api-key`
  header). The platform calls the TTS models "free for a limited time".

What it became: a **Xiaomi MiMo** entry in the OpenAI section's Server
dropdown. `core/server-presets.ts` gives every preset a `synthesis` route
(`speech`, OpenAI's `/v1/audio/speech`, for the three that existed; `chat`
for MiMo), MiMo the documented voices as its fallback list (there is no
list to ask for) and `voiceName: 'MiMo'`, so the player and the voice
browser say `MiMo-冰糖` rather than `OpenAI-冰糖`
(`read-aloud/catalog.ts`). `providers/openai.ts` folds `synthesize` and
`checkSynthesis` into one `speak()` that posts on the configured route,
decodes the base64 mp3 into an `audio/mpeg` Blob and treats a reply
without audio — a chat model in the Model field — as a `SynthesisError`
at Test connection and while reading alike. The result carries
`note: 'audio through /v1/chat/completions'`, which the per-segment debug
line shows when there are no timestamps — the proof the chat route
answered, since the speech route cannot on this server. Weighed and
rejected, on the issue: a provider section of its own, an automatic
fallback to the chat route on a 404, the voiceclone/voicedesign models,
streaming.

Extra headers are disabled on the MiMo preset, as on OpenAI's (added after
the live run): api.xiaomimimo.com is a fixed hosted endpoint with no gateway
of the user's in front, and a token typed for another server would otherwise
travel with every MiMo request. That is issue #52 in general — the tester
found the profile's Cloudflare Access token for the Chatterbox gateway about
to go to Xiaomi with the first probe, and blanked it for the run — and the
`uses` flip closes only the MiMo case of it.

## The Server dropdown's memory covers the credentials too (2026-09-06 01:47, issue #52)

Found by the tester during #50's live run: the profile's Extra headers held
the Cloudflare Access token of the Chatterbox gateway, and with the dropdown
on *Xiaomi MiMo* the first probe would have carried it to api.xiaomimimo.com
(the tester blanked the pref for the run). The API key, Voices and Extra
headers were one set of fields shared by every server; #34 had given each
server a memory of its address and model only, in `openai.presetValues`.
`switchPreset` now files and restores all five fields, and a server never
visited starts with an empty key, empty Voices and empty headers — nothing
typed for one server is ever sent to another. The copies live in the same
pref as before, in plain text like the fields themselves and in the settings
backup with them; what changed is where a credential goes, not where it is
stored. Two consequences to know: a key is rotated on the server that is
selected, and the copy filed under another server stays until that server
is visited again, when it comes back into the field and can be replaced;
and a profile upgraded from 1.10.9 files whatever the three fields hold under
the server selected at its first switch, while the other servers start
blank — someone who alternated between two servers before types the second
server's key once more.

## A typo of a hosted server's address is named before the key goes anywhere (2026-09-06 01:59, issue #54)

The worry after #52: `https://api.xiaomimim.com`, one letter short, fails as
"Cannot reach …" and the eye skips the missing letter; if the mistyped
domain is registered, the first probe hands it the key. The two hosted
presets now carry their server's hostname (`host` on the spec), and
`addressHint` compares the typed hostname with it by edit distance: within
two edits is a typo — refused by Test connection and Enable before any
request, `Not tested: … looks like a typo of …` — and anything else a
different address, tested as before with `… is not …: a mirror or a proxy?`
appended to the result. The same sentence lands in the status line on every
`input` of the Base URL field, and the field's placeholder is the preset's
default address, so clearing it shows the right value. Locking the field was
rejected: OpenAI mirrors are the common case for users in China, a proxy in
front of MiMo needs the address editable, and *Other* cannot replace the
MiMo preset since only the preset speaks the chat route. Real mirrors are
whole other domains, so the two-edit window catches typos and nothing
legitimate; a preset without a fixed host (Chatterbox, Other) gets no hint,
a LAN address being no typo of anything.

## The player's language dropdown resolved against the previous language's entry, so the pick hook now hands it the right one first (2026-09-06 02:46, issue #49)

Issue #49 is the record of the bug; this is what was learned fixing it.
Zotero 10.0.2-beta.7 on macOS for the line numbers (the issue cites
beta.5 on Windows; the code is the same, the numbers shifted).

- **Zotero's `setLanguage` never re-reads the entry.** `_persistedVoices`
  has one writer, `applyPersistedVoices` (reader.js 82354-82361), which
  only `_syncPersistedVoicesToManager` calls (84160-84170) — for
  `manager.lang` at that moment. The player's language dropdown goes
  `handleLangChange` (38594-38600) → `setLanguage(base, { region,
  persist: true })` (82317-82334): `_voiceID` cleared, `_pendingSetVoice`
  raised, `_resolveVoice` at once (82396-82448) → `_findFallbackVoice`
  (82450-82492) reading `_persistedVoices` as it stands, the entry of the
  language the manager *was* on. Branches 1 and 2 test that entry's
  voices against the new language's pool and fail; branch 3 (82484-82490)
  takes the first voice of `this._region || persistedRegion ||
  getPreferredRegion()`, and `_resolveVoice` takes `voicesForLang[0]` when
  even that is null. Because `_pendingSetVoice` is up, `_persistCurrentVoice`
  (82377-82394) then writes that voice into the *new* language's entry
  through `_setReadAloudVoice` (84274-84318), over what the user had
  there. Zotero's, with or without the plugin: two clicks, English →
  Multiple languages → English, turned Andrew into AIGenerate1 on
  2026-09-05, and the profile still carried that fingerprint on
  2026-09-06 (memory and the `en` entry both on AIGenerate1).
- **What the plugin added** was making the tab's mistake the default
  everywhere: the pref observer learned the persisted fallback as a pick
  and spread it, and the `setLanguage` pick hook (2026-08-27) learned it
  when the pref had not changed. The 2026-08-31 note on #36 had already
  seen `setLanguage` resolve "against the previous lane's entry" for the
  plugin's own moves and replaced those with field writes; the user's
  dropdown path was left as it was, and this is that path.
- **The fix is the same prototype hook, before the original.** With
  `persist` (only the dropdown passes it — Zotero's own calls and the
  sync's lane moves pass none), `stageLanguagePick` loads the pref's
  entry for the language chosen — `resolveVoiceLang` (#26); the pref,
  not the reader's copy, which may lag (refreshVoices) — `cloneInto` the
  reader's compartment, since `_findFallbackVoice` destructures it, and
  assigns it to the waived manager's `_persistedVoices`: what `stage()`
  (#37) already did for the list about to land, now one helper,
  `loadEntry`. The manager reaches the hook as `this`, behind an Xray; the
  reader it belongs to comes from a WeakMap filled in `attach`
  (`readerOf`), with a scan of the open readers comparing raw and waived
  identities as the fallback, and a debug line (`the dropdown picked …
  on a manager no reader was attached with`) when neither finds it — that
  line never appeared live. Zotero's own resolution then lands on the
  entry's voice through branch 1 (`persistedTierVoices[targetTier]`),
  persists it unchanged (no observer fires), and `notePick` learns the
  entry's voice as the pick: the 2026-08-27 decision that a dropdown
  switch *is* a pick stands, only what it lands on changed. The log
  reads `staged Zotero's entry for the dropdown's <lang>: voice <id>`,
  once per click and nowhere else.
- **Zotero's region rule now works on the dropdown path.** `regionChanged`
  (`this._region && persistedRegion && this._region !== persistedRegion`,
  82473) compared the region chosen against the *old* language's entry
  before; against the right one, "English (United Kingdom)" on an `en`
  entry with region `US` skips the entry's voice for the first en-GB voice
  of the pool (Abbi) and rewrites the entry with region `GB` — Zotero's
  design for an explicit region, and the plugin learns that voice as the
  pick like any other.
- **The test fake was cheating.** Its `setLanguage` with persist read the
  pref's entry for the new language directly — exactly what Zotero does
  not do — which is why 67 tests passed over this bug. It resolves from
  `_persistedVoices` now, with `isLanguageSupported`'s region filter,
  `regionChanged` and the region branch in miniature; the round trip, the
  region rule and a language with no entry are pinned. The pre-fix run
  failed four tests: the three new ones and the 2026-08-27 "learns a
  language switch that re-persists what the entry already holds", whose
  Ada had been reached through the cheat.
- **Live, 2026-09-06 02:12-02:24, 1.10.10-beta, through the bridge.** Two
  fixtures paused on Andrew at 2.1×; the pools as on 2026-09-05 (787
  Local voices, 87 for `mul` with Masaru first, 80 en-US with AIGenerate1
  first, 29 en-GB with Abbi first). To Multiple languages:
  `_persistedVoices` the `mul` entry (AlloyTurbo) at 0 and 500 ms,
  `selectedVoiceID` AlloyTurbo, both entries byte-identical, the memory
  AlloyTurbo (`mul`), the other tab moved to it and still paused; the log
  `staged … mul`, `read-aloud memory (a pick the pref did not show)`,
  `applied read-aloud memory: en -> mul` (the other tab's lane move),
  `spread … en: resynced`. Back to English (United States): the `en`
  entry, Andrew, the memory Andrew (`en`), the other tab back on Andrew.
  Five clicks, five `staged` lines, none on a popup open, a spread, a
  pref restore or `_prepareReadAloud()`; `patches()` identical before and
  after; no dead objects, no plugin errors. Zotero logs one
  `TypeError: can't access property "collapsed", selectionRanges[0] is
  undefined` (`_getAnnotationFromSelectionRanges`, 78185-78186) per
  dropdown click — the controller recreated with nothing selected,
  nothing of ours in the stack; the rulebook's `selectionRanges` noise.
- **Two driving pitfalls, now in the rulebook.** A player opened through
  the API in a background tab never mounts its DOM — `popupOpen` true,
  the manager `active`, `.read-aloud-popup` absent even after the tab is
  selected — so the dropdown is driven in the selected tab. And
  `Zotero.Debug.get()` is async: read bare, it hands back a promise whose
  string has no `[zotero-tts]` line, and the store looks empty.
- **Left open, on purpose.** A language never used has no entry to load:
  Zotero's fallback, with `_selectedTier` null (every restore clears it),
  takes the first regional match across every tier in list order, a
  Standard voice while signed in — Zotero's own behavior for a fresh
  language, unchanged here; whether the plugin should start it on a Local
  voice the way #35 does for a voice the list lacks is a separate
  decision. The stale entry itself is Zotero's bug, reportable upstream;
  the fix here stands either way.

## A permanently deleted document's bookmark now leaves the shared file: tombstones stay on the machine, never in the file (2026-09-06 11:02, issue #51)

Issue #51, from the 1.10.9 bug hunt: the deletion observer cleared only
the database row, the sampler's in-memory map kept the entry and fed it to
every sync, and the shared file's union kept it forever. The fix is two
local halves and no change to the file: the sampler learned `remove()`,
and the store learned tombstones — a `deletions (libraryID, key, ts)`
table, schema 2 — which the transport honors at merge. Kept here: the
Zotero facts the design rests on, and the reasoning the issue's plan
comment holds only in summary.

- **Every deletion, local or sync-driven, is the same notification.**
  `_finalizeErase` queues `('delete', 'item', ids, notifierData)` with
  `notifierData[id] = { libraryID, key }` (`data/dataObject.js:1448-1452`,
  `:1470-1478`); a deletion arriving through Zotero sync erases through
  `objectsClass.erase(toDelete, { skipEditCheck, skipDeleteLog })`
  (`sync/syncLocal.js:464-469`) and lands in the same place. So every
  machine that holds the document hears its deletion itself, and a
  per-machine tombstone is enough: nothing about a deletion has to travel
  in the positions file. `skipDeleteLog` only keeps the sync event
  listener from writing Zotero's own `syncDeleteLog`
  (`sync/syncEventListeners.js:54`).
- **Removing a library from this machine fires no item deletions.**
  `Library._eraseData` deletes the rows straight from SQL
  (`data/library.js:667-700`); nothing per item is queued. So a group the
  user stops syncing on one machine never writes tombstones, and its
  bookmarks stay in the file for the machines that keep the group — the
  union #40 designed. The startup sweep matches: a row whose library is
  gone is swept without a tombstone; only "library here, item not" is a
  deletion.
- **Zotero's own delete log cannot serve as the tombstone source.**
  `syncDeleteLog` is read for the upload and cleared once the deletion
  reaches zotero.org (`sync/syncLocal.js:475-476`), and never written for
  items that do not sync (`data/item.js:5610-5612`).
- **Order at an erase with the tab open.** `Zotero.Reader` registers its
  notifier observer at init with no priority (`xpcom/reader.js:2671`);
  the plugin's registers later with none either, and `_getObserverOrder`
  keeps insertion order among equals (`notifier.js:281-298`, a stable
  sort over defaults of 100). The reader's `notify` closes the tab first
  (`reader.js:2831`, `ReaderTab.close` → `Zotero_Tabs.close`
  synchronously, `:2078`), so the close capture's save is queued before
  the observer's remove. And `Items.unload` is a *temporary* commit
  callback of the erasing transaction (`dataObject.js:1466-1468`), which
  `db.js:523-525` runs before the permanent ones, where the notifier's
  commit lives (`zotero.js:544`): by the time any observer runs,
  `Zotero.Items.get(reader.itemID)` is already false, so a late capture
  cannot even name the attachment. The sampler still marks the key erased
  for the session — belt and suspenders against a lingering reader.
- **The tombstone's stamp and the drop rule.** A tombstone is stamped
  `max(now, held.ts)` and drops every merged entry with `ts <= tombstone`;
  the sweep stamps `max(now, row.ts)`. The `max` is the same lesson as the
  sampler's `max(now, previous.ts + 1)` (#40): an entry adopted from a
  machine with a fast clock is stamped in this machine's future, and a
  tombstone at plain `now` would never beat it. The `<=` leaves room for a
  document restored from a database backup and read again: its new
  position is stamped after the deletion and passes.
- **Why the tombstone is local and the file stays version 1.** A tombstone
  inside the file would change the format; an older build filters it out
  as malformed, still holds the position, and re-uploads it — the
  tombstone would be gone. Local tombstones need no other machine to
  understand anything: the entry leaves the file at the first sync of any
  machine that heard the deletion, and only a machine that still holds
  it locally can re-add it, which is exactly a machine that has not heard
  the deletion yet and will tombstone when it does. Convergence, with
  ping-pong of at most one re-add per machine that lags.
- **What the tombstones table never holds.** The `delete` notification
  covers every item — notes, annotations, parent items — so a tombstone
  is written only when the sampler's map actually held the key; the table
  stays one row per attachment that was ever read aloud and then erased.
  A tombstone whose key later gets a newer position is inert and is not
  revived away: not worth a write per sentence.
- **The eight orphans already in the file** predate any tombstone — their
  rows were swept long ago — and leave only by one hand-clean, which now
  sticks because nothing holds them in memory any more.
- **Verified live on 1.10.12-beta** (macOS, Zotero 10.0.2-beta.7, the real
  WebDAV folder, `test/zotero-dev.md` section 6 item 4): the schema went
  1 → 2 in place (`swept 0, deletions 0`); a fixture read, closed and
  erased left the map and the store at once and the erase's own sync
  logged `position sync (delete): 54 remote, 53 merged, 0 adopted,
  1 dropped, uploaded`, the file back to the 53 keys it started with; the
  entry put back into the file by hand was dropped again by the next
  reader-open sync (`1 dropped, uploaded`) and never entered the store —
  the very shape of sync that on 1.10.9 put it back; the switch-on
  trigger that resurrected the fixture on 1.10.9 now uploads nothing;
  erasing an attachment never read aloud wrote no tombstone and poked no
  sync; a plugin restart loaded the two fixture tombstones from disk.
- **The notifier yields between observers.** `Zotero.Notifier.trigger`
  awaits each observer (`notifier.js:167`, `await Promise.resolve(
  ref.notify(...))`), so a microtask continuation can run between
  `Zotero.Reader`'s observer and ours: with the fixture's tab open at the
  erase, the reader observer closed the tab and its close poke started a
  sync, whose download continuation read `local()` in that gap — before
  our `remove()` — and uploaded the entry (`reader-close: 53 remote, 54
  merged, 0 dropped, uploaded`); the deletion's own poke, the trailing
  sync, took it straight back out (`delete: 54 remote, 53 merged,
  1 dropped, uploaded`). The end state is right either way, which is why
  the observer pokes on every held removal rather than trusting the close.

## A provider that hangs at the popup's open dropped every provider's voices, so each is bounded on its own now (2026-09-06 11:16, issue #55)

Issue #55 holds the evidence (macOS, this morning: Kokoro and Chatterbox
behind Cloudflare not answering while Azure did, and Read Aloud starting on
`a6ac2542-en-US`, a Premium voice); this is what was learned fixing it.

- **Where the bound was.** The plugin's voices were listed under one cap,
  `ownCatalog`'s 30 s around the whole `listCatalog()`
  (`read-aloud/remote-interface.ts`, added 2026-08-22), and no provider's
  listing request had a bound of its own. `collectCatalog`'s
  `Promise.allSettled` keeps a provider that *fails* from hiding the
  others — that was its whole point — but it settles when the slowest
  settles, so a provider that neither answers nor fails held the union
  past the cap, the cap rejected, and `getVoices` handed Zotero its own
  Standard and Premium voices with an empty plugin catalog: the providers
  that had answered were dropped with the one that had not. From there
  it is issue #35's "no Local voice at all" branch, written for a user
  with no working provider, firing for one whose providers all work:
  `pickSubstitute` finds nothing, Zotero's `_findFallbackVoice` widens its
  pool to every tier and `_resolveVoice` takes `voicesForLang[0]`
  (10.0.2-beta.7, the build the live run below used: `loadVoices`
  reader.js 82300-82312, the fallback 82436, `_findFallbackVoice`
  82450-82492 with the pool widened at 82465-82468, `_prepareReadAloud`
  84260), and with the popup open `_onReadAloudEngineStateChanged`
  (83860-83865) activates the manager on that voice at once. The credits
  are spent before anything could correct it, which is why the fix had to
  be in the listing, not after.
- **Where it is now.** The bound moved to where the independence is:
  `collectCatalog` (`read-aloud/catalog.ts`) wraps each provider's
  `listVoices()` in its own `withTimeout` — `PROVIDER_LISTING_TIMEOUT_MS`,
  15 s, the bound Test connection puts on a provider's list, so the pane
  and the popup agree on how long is too long — and a provider that has
  not answered goes the way a failing one goes: one `Zotero.logError`
  line, `local: listing voices failed: no voice list within 15 s`, its
  voices alone missing. Whatever answered is kept. The request is
  cancelled as well: `TTSProvider.listVoices` takes an optional
  `{ signal }`, the three network providers pass it to their fetch, and
  the catalog aborts a controller it gets from a chrome window
  (`Zotero.getMainWindow()` in `index.ts`, the pane's own window in
  `prefs-pane.ts`) — the sandbox has none. The 30 s cap stays as the
  last resort and cannot fire for a hung provider any more; the pane's
  and the diagnostics' 15 s caps around the whole listing moved to
  `CATALOG_CAP_MS`, 20 s, because equal timers would tie with the inner
  bound and the order they were set in is nothing to rely on.
- **Two things left as they are, on purpose.** With every provider
  failing or hanging at once the plugin's catalog is empty and Zotero
  picks a paid voice for the document's language, the toast saying so —
  issue #35's decision, put to the user again today and kept: Read Aloud
  starts on Zotero's voices rather than stopping with an error, and a
  user who wants no such fallback switches the provider off. And the
  pane's status line does not name a provider that timed out: a provider
  that fails has never appeared there either, only in the log, and Test
  connection per section is where a provider's trouble is reported.
- **Reading the log.** The line that proves the bound fired is
  `local: listing voices failed: no voice list within 15 s` (or `azure:`,
  `openai:`), with its prefix: the system-voice migration's own error
  ends in the same `no voice list within 15 s`. The old cap's line,
  `Listing the plugin's voices took longer than 30 s`, must not appear
  for a hung provider any more; if it does, something other than a
  provider held the union.
- **Not settled.** The issue's second open, on macOS, returned in 402 ms
  with an empty plugin catalog — every provider failing at once, a
  transient network failure inside Zotero, not a hang. That is the
  all-providers-down case above; this fix does not change what it lands
  on, and why that outage happened stays open.
- **Live, 2026-09-06 11:20–11:45, 1.10.12-beta on 10.0.2-beta.7, through
  the bridge** (Zotero applied a staged update at the restart the run
  needed; the morning's unpack was beta.5. The test build was named
  before 1.10.12 went out from another worktree the same morning, so
  this fix ships as 1.10.13). Three providers answering —
  Azure 691 voices, Chatterbox 28, the remote Kokoro 68, 2267 with
  Zotero's 1480 — then `local.baseURL` at a listener that accepts and
  never answers: the list landed as 2199 (1480 + 691 + 28, no `local::`
  id) with the manager still on `azure::en-US-AndrewNeural` and never a
  Zotero id at any sample; `diagnostics.defaultVoice()` settled at
  15065 ms with `problems: []` and the pane's status line at 15326 ms;
  the error `local: listing voices failed: no voice list within 15 s`
  at +14663 ms of the listing, seven of them for seven listings, no
  30 s line; and the listener saw every connection closed by the peer
  at 15.00–15.50 s — an AbortController taken from the main window does
  reach the sandbox's `fetch` and the socket. With the memory on
  `local::am_puck` the substitute was `azure::en-US-AndrewNeural`, the
  first en-US favorite by label, the toast read from the chrome document
  `Zotero-TTS: local::am_puck is not offered here. Reading with
  Azure-Andrew instead.` — the id, not `Kokoro-am_puck`, since no listed
  voice carries the label once the whole provider is skipped — and the
  memory unchanged. Prefs byte-identical afterwards; no dead objects
  across the in-place upgrade from 1.10.9.
- **Three driving facts for the rulebook.** A 5 s toast cannot be
  screenshotted through the bridge — its round trip ran 15–20 s in this
  session and one eval caps at ~8 s — so a transient is read from the
  DOM instead: a `setInterval` watcher installed in one script and read
  in the next catches a status-line transition to the millisecond (the
  pane's 15326 ms). The toast's document depends on the tab: `toastDoc`
  (`index.ts`) draws it in the reader iframe's document while the tab is
  selected and in the chrome window's while it is hidden, so a watcher
  on one of them misses a toast drawn in the other — the tester's
  "substitution line without a toast" for a second memory write was
  that, the fixture tab selected and the watcher on the chrome
  document. And 28 × 250 ms of polling in one eval already trips the
  cap; 20 × 250 ms was reliable.

## Zotero collapses button margins on macOS, and a plugin's pane sheet cannot ask which platform it is on (2026-09-06 11:54, issue #56)

The settings pane's side-by-side buttons touched on macOS and stood 10 px
apart on Windows. Both halves of that, and the detour the fix took, are
Zotero and Gecko facts worth keeping.

- **Zotero's `preferences.css` gives every XUL button `max-height: 25px;
  margin: 0 -2px -1px` on macOS only** — `scss/components/_button.scss`
  34–39 ("Prevent ugly non-native button styles on macOS"), compiled into
  `chrome://zotero/skin/preferences.css` under `@media (-moz-platform:
  macos)`. It replaces the toolkit's Aqua `margin: 5px 6px 3px` (osx
  `button.css`: "there should be 12 pixels between two buttons"). On
  Windows the same sheet sets only `margin-block: 4px`, and the toolkit's
  `margin: 1px 5px 2px` stands: 5 px after a button, 10 px between two.
  The 2026-08-28 entry met this rule in the minified sheet and guessed at a
  flattened parent scope; the scope is that media query.
- **The native face is drawn about 2 px inside the button's box.** The
  −2 px puts the face's edge on the box's edge, which is what lines a
  lone button up with the text column; two buttons in a row then overlap
  by 4 px (measured: `Clear`.left − key.right = −4) and render as faces
  just touching. Zotero's own pairs sit in `hbox.preferences-button-group`
  (`gap: 6px; margin-top: 4px`) and never show it.
- **`-moz-platform` is parsed in chrome and UA sheets only, and a
  plugin's pane sheet is neither.** `PreferencePanes.register` resolves
  the sheet to the xpi's `jar:file:…!/content/preferences.css`
  (`xpcom/preferencePanes.js:155`) and the window takes it as an
  `xml-stylesheet` instruction (`preferences/preferences.js:323-330`), an
  author sheet with a non-chrome URL. A `@media (-moz-platform: macos)`
  block there survives in the CSSOM — `conditionText` round-trips
  verbatim, like `-moz-bool-pref` — as a Media Queries "general enclosed"
  condition that never matches. Isolated live on the open pane: a plain
  rule inserted into that sheet applies; the same rule inside the media
  block does not; `@media (min-width: 1px)` in the same sheet applies; the
  identical block in a `<style>` element of the document applies. Rule:
  **no `-moz-` media feature in `preferences.css`, ever; the platform
  goes on the markup as a class** — `ui/platform-class.ts` puts `ztts-mac`
  on the root `.ztts-pane` from `onPaneLoad` when `Zotero.isMac`, and
  `test/ui/pane-css.test.ts` pins both halves.
- **Specificity, not sheet order, decides against Zotero's rule.** The
  plugin's sheet is inserted at `document.firstChild`, before Zotero's,
  yet `.ztts-pane.ztts-mac hbox > button + button` (0,2,3) beats `button`
  (0,0,1); `getMatchingCSSRules` lists it last, highest precedence.
- The fix: `margin-inline-start: 8px` on a button after a button, `5px`
  on a `?` after a button, both under the class. Measured on
  1.10.13-beta2: the second button of every pair opens 6 px after the
  first (was −4), the `?` 3 px after `Clear` (was −2), the `?` after a
  checkbox still 4 px, the first buttons and the lone Restore buttons
  still `-2px`; with the 2 px inset that is 10 px and 5 px between the
  faces, Windows' distances. Checklist: `test/zotero-dev.md` §1.2.
- Tooling: `InspectorUtils.getCSSStyleRules` is gone in Firefox 140 —
  `getMatchingCSSRules(el)`, increasing precedence, each rule with
  `parentStyleSheet.href` and `parentRule.conditionText`. And
  `doc.styleSheets` gains a plugin pane's sheet a beat after
  `navigateToPane` returns (absent at 40 ms, present on the next read):
  poll for it.

## The sample player's `<audio>` reports a failure after `play()` has resolved, and the voice browser now says so (2026-09-06 13:07, issue #48)

Issue #48: a sample that broke off after it started — a machine with no
audio output, a stream Gecko starts and cannot finish — looked exactly
like one that played: `▶` → `…` → `■` → `▶`, the status line's default
line intact, nothing heard. The fix is in `src/ui/voice-browser-rows.ts`
(`createSamplePlayer`, `onPlay`) and `diagnostics.sampleSpeed()`; the
issue holds the evidence and the plan. What is worth keeping about the
element itself:

- **`HTMLMediaElement.play()` settles when playback starts, and a
  failure after that rejects nothing.** It is the `error` event alone,
  and the element keeps the reason in `el.error`, a `MediaError` with
  `code` (1 aborted, 2 network, 3 decode, 4 source not supported) and
  Gecko's own `message` — `OnMediaSinkAudioError` under code 3 for an
  output device it could not open (2026-09-05), `Failed to open media`
  under code 4 for a source swapped mid-play (today). `ended` and
  `pause` follow the `error` a few ms later, so the finish is one-shot
  or the caller hears twice. The player's `onDone` now carries
  `Error | null`: null on `ended` and on a stop, the described
  `MediaError` on a failure after the start.
- **A failure before the start is delivered twice, in one task.** The
  media element's "dedicated media source failure steps" fire `error`
  first and then reject the pending play promises
  (`NotSupportedError`), so a listener hears of it before
  `await el.play()` throws — measured today: `play-rejected` and
  `error` at the same millisecond. The player separates the two with a
  `started` flag set right after the await: the promise continuation is
  a microtask and runs before any later task can dispatch `error`, so
  the flag is exact — a pre-start `error` leaves the report to the
  rejection (the caller's `catch`, the old `Sample failed: <reason>`
  text, `describeMediaError` never called), a post-start one goes to
  the callback. The rejection also drops the callback (`done = null`):
  a replay of the same voice used to run the stale callback through the
  next `stop()` and put `▶` back on the new sample.
- **A stopped element can still report.** `removeAttribute('src')`
  aborts its load, and a late `ended`/`error` from it must not end the
  sample that replaced it — the listeners check `el === current`.
- **Every read of `MediaError.message` logs a `privacy.resistFingerprinting`
  warning on the error console, at the reader's line** (Gecko's
  `MediaError::GetMessage`) — two lines signed `zotero-tts.js` per
  failed sample until `describeMediaError` read it once. A warning, not
  an error, and only when a sample fails; Gecko adds its own `Media
  resource … could not be decoded` beside it.
- **`diagnostics.sampleSpeed()` is now the sink probe for the pane's
  path:** it waits for its 100 ms silence to end or fail (3 s cap) and
  reports `outcome` — `ended`, `error: decoding or output failed
  (OnMediaSinkAudioError)`, or `neither ended nor failed within 3 s`
  (a stall, never seen). Read Aloud's own AudioContext path
  ([2026-09-05](NOTES_2026-09-05.md)) is still probed on the
  controller. Checklist: `test/zotero-dev.md` §2.6.
- **The pane's detached `<audio>` is reachable from chrome scope** for
  a test: a wrapper on the pref window's `HTMLMediaElement.prototype.play`
  sees it (the element's prototype is that window's, DOM or not), which
  is how the tester timed its events and swapped its source mid-play.
- Verified on 1.10.15-beta through the bridge (Zotero
  10.0.2-beta.7+a5b4b4d20, Firefox 140, Windows), with an output device
  present the whole run: `sampleSpeed().outcome` `ended` three times
  over seven minutes; a Kokoro and a Zotero sample ended on `ended`
  (1944 ms and 1308 ms of playback at 1.7×, the durations divided by the
  speed) with the default line intact; a stop by hand fired neither
  `error` nor `ended`; a replay made no request to the Kokoro server
  (`http-on-modify-request` observer, zero new entries); a source
  swapped for an undecodable one 400 ms after `play()` resolved fired
  `abort`, `emptied`, `error` (code 4) and put
  `Sample failed: the audio arrived, but playback stopped: format not
  supported (Failed to open media)` on the line, once, `▶` back; the
  same swap before `play()` gave the old `NotSupportedError` text and
  nothing more. The no-sink branch (`OnMediaSinkAudioError`) is the
  unit tests' and 2026-09-05's measurement; it did not recur today. The
  System voice was not sampled — `system.enabled` is off in this
  profile — and the path does not branch on the provider. Known and
  left: a `Sample failed:` line stays until the next repaint of the
  status line (a heart, a pick, the slider, a switch), as it always has.
