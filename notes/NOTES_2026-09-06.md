## Xiaomi MiMo's TTS is a chat completion, and the plugin's OpenAI section learned that route (2026-09-06 01:12, issue #50)

A user could not connect Xiaomi's MiMo-V2.5-TTS through *Other
OpenAI-compatible server*: Test connection said "Connected, but synthesis
failed: OpenAI speech: HTTP 404". Probed live against
`https://api.xiaomimimo.com/v1` with the user's key before anything was
written; what the API actually does, kept here so the next session need
not probe again:

- `/v1/models` answers (401 without a key, 200 with one) and lists
  `mimo-v2.5`, `mimo-v2.5-asr`, `mimo-v2.5-pro`, `mimo-v2.5-tts`,
  `mimo-v2.5-tts-voiceclone`, `mimo-v2.5-tts-voicedesign`. **`/v1/audio/speech`
  and `/v1/audio/voices` are 404 at the gateway** (an openresty HTML page),
  key or no key. That is the whole report: the model list passed
  ("Connected"), the two-character probe on the speech route failed
  ("synthesis failed: HTTP 404").
- Speech is `POST /v1/chat/completions` with the text in an **`assistant`**
  message — `{ model, messages: [{ role: "assistant", content }],
  audio: { format, voice } }`; a `user` message is an optional style
  instruction, left out. The reply is an ordinary chat completion whose
  `choices[0].message` has `content: ""` and `audio: { id, data: <base64>,
  expires_at: null, transcript: null }` — the shape OpenAI gave its audio
  chat models. Formats: `wav` (24 kHz, 16-bit mono), `mp3` (64 kbps; 45 KB
  for 5.7 s where the wav is 269 KB), `pcm`, `pcm16`; anything else is a
  400 whose `param` names those four. A sentence took 2.5–2.9 s.
  `stream: true` works (pcm16 pieces under `choices[0].delta.audio.data`)
  and is not used: Read Aloud takes one blob per segment.
- **No timestamps of any kind.** `transcript` is null in every reply,
  streaming chunks carry only audio, and `timestamps`, `word_timestamps`
  and `return_timestamps` in the request are ignored without an error. So
  sentence highlighting, exactly as on OpenAI's speech route.
- Voice ids are the documented names, the Chinese ones as they are
  (`冰糖` worked verbatim): `mimo_default`, `冰糖`, `茉莉`, `苏打`, `白桦`,
  `Mia`, `Chloe`, `Milo`, `Dean`. A wrong one is a 400 in OpenAI's error
  shape with the detail in **`param`**, not `message` — `{ "error": {
  "code": "400", "message": "Param Incorrect", "param": "Unknown voice:
  alloy. Available voices: [mimo_default, 冰糖, …]", "type": "" } }` —
  where OpenAI puts the detail in `message` and the field name in
  `param`; the provider's `serverReason` therefore quotes the longer of
  the two after the status, so the pane says which voices exist.
  `Authorization: Bearer` is accepted (the docs also offer an `api-key`
  header). The platform calls the TTS models "free for a limited time".

What it became: a **Xiaomi MiMo** entry in the OpenAI section's Server
dropdown. `core/server-presets.ts` gives every preset a `synthesis` route
(`speech`, OpenAI's `/v1/audio/speech`, for the three that existed; `chat`
for MiMo), MiMo the documented voices as its fallback list (there is no
list to ask for) and `voiceName: 'MiMo'`, so the player and the voice
browser say `MiMo-冰糖` rather than `OpenAI-冰糖`
(`read-aloud/catalog.ts`). `providers/openai.ts` folds `synthesize` and
`checkSynthesis` into one `speak()` that posts on the configured route,
decodes the base64 mp3 into an `audio/mpeg` Blob and treats a reply
without audio — a chat model in the Model field — as a `SynthesisError`
at Test connection and while reading alike. The result carries
`note: 'audio through /v1/chat/completions'`, which the per-segment debug
line shows when there are no timestamps — the proof the chat route
answered, since the speech route cannot on this server. Weighed and
rejected, on the issue: a provider section of its own, an automatic
fallback to the chat route on a 404, the voiceclone/voicedesign models,
streaming.

Extra headers are disabled on the MiMo preset, as on OpenAI's (added after
the live run): api.xiaomimimo.com is a fixed hosted endpoint with no gateway
of the user's in front, and a token typed for another server would otherwise
travel with every MiMo request. That is issue #52 in general — the tester
found the profile's Cloudflare Access token for the Chatterbox gateway about
to go to Xiaomi with the first probe, and blanked it for the run — and the
`uses` flip closes only the MiMo case of it.

## The Server dropdown's memory covers the credentials too (2026-09-06 01:47, issue #52)

Found by the tester during #50's live run: the profile's Extra headers held
the Cloudflare Access token of the Chatterbox gateway, and with the dropdown
on *Xiaomi MiMo* the first probe would have carried it to api.xiaomimimo.com
(the tester blanked the pref for the run). The API key, Voices and Extra
headers were one set of fields shared by every server; #34 had given each
server a memory of its address and model only, in `openai.presetValues`.
`switchPreset` now files and restores all five fields, and a server never
visited starts with an empty key, empty Voices and empty headers — nothing
typed for one server is ever sent to another. The copies live in the same
pref as before, in plain text like the fields themselves and in the settings
backup with them; what changed is where a credential goes, not where it is
stored. Two consequences to know: a key is rotated on the server that is
selected, and the copy filed under another server stays until that server
is visited again, when it comes back into the field and can be replaced;
and a profile upgraded from 1.10.9 files whatever the three fields hold under
the server selected at its first switch, while the other servers start
blank — someone who alternated between two servers before types the second
server's key once more.

## A typo of a hosted server's address is named before the key goes anywhere (2026-09-06 01:59, issue #54)

The worry after #52: `https://api.xiaomimim.com`, one letter short, fails as
"Cannot reach …" and the eye skips the missing letter; if the mistyped
domain is registered, the first probe hands it the key. The two hosted
presets now carry their server's hostname (`host` on the spec), and
`addressHint` compares the typed hostname with it by edit distance: within
two edits is a typo — refused by Test connection and Enable before any
request, `Not tested: … looks like a typo of …` — and anything else a
different address, tested as before with `… is not …: a mirror or a proxy?`
appended to the result. The same sentence lands in the status line on every
`input` of the Base URL field, and the field's placeholder is the preset's
default address, so clearing it shows the right value. Locking the field was
rejected: OpenAI mirrors are the common case for users in China, a proxy in
front of MiMo needs the address editable, and *Other* cannot replace the
MiMo preset since only the preset speaks the chat route. Real mirrors are
whole other domains, so the two-edit window catches typos and nothing
legitimate; a preset without a fixed host (Chatterbox, Other) gets no hint,
a LAN address being no typo of anything.

## The player's language dropdown resolved against the previous language's entry, so the pick hook now hands it the right one first (2026-09-06 02:46, issue #49)

Issue #49 is the record of the bug; this is what was learned fixing it.
Zotero 10.0.2-beta.7 on macOS for the line numbers (the issue cites
beta.5 on Windows; the code is the same, the numbers shifted).

- **Zotero's `setLanguage` never re-reads the entry.** `_persistedVoices`
  has one writer, `applyPersistedVoices` (reader.js 82354-82361), which
  only `_syncPersistedVoicesToManager` calls (84160-84170) — for
  `manager.lang` at that moment. The player's language dropdown goes
  `handleLangChange` (38594-38600) → `setLanguage(base, { region,
  persist: true })` (82317-82334): `_voiceID` cleared, `_pendingSetVoice`
  raised, `_resolveVoice` at once (82396-82448) → `_findFallbackVoice`
  (82450-82492) reading `_persistedVoices` as it stands, the entry of the
  language the manager *was* on. Branches 1 and 2 test that entry's
  voices against the new language's pool and fail; branch 3 (82484-82490)
  takes the first voice of `this._region || persistedRegion ||
  getPreferredRegion()`, and `_resolveVoice` takes `voicesForLang[0]` when
  even that is null. Because `_pendingSetVoice` is up, `_persistCurrentVoice`
  (82377-82394) then writes that voice into the *new* language's entry
  through `_setReadAloudVoice` (84274-84318), over what the user had
  there. Zotero's, with or without the plugin: two clicks, English →
  Multiple languages → English, turned Andrew into AIGenerate1 on
  2026-09-05, and the profile still carried that fingerprint on
  2026-09-06 (memory and the `en` entry both on AIGenerate1).
- **What the plugin added** was making the tab's mistake the default
  everywhere: the pref observer learned the persisted fallback as a pick
  and spread it, and the `setLanguage` pick hook (2026-08-27) learned it
  when the pref had not changed. The 2026-08-31 note on #36 had already
  seen `setLanguage` resolve "against the previous lane's entry" for the
  plugin's own moves and replaced those with field writes; the user's
  dropdown path was left as it was, and this is that path.
- **The fix is the same prototype hook, before the original.** With
  `persist` (only the dropdown passes it — Zotero's own calls and the
  sync's lane moves pass none), `stageLanguagePick` loads the pref's
  entry for the language chosen — `resolveVoiceLang` (#26); the pref,
  not the reader's copy, which may lag (refreshVoices) — `cloneInto` the
  reader's compartment, since `_findFallbackVoice` destructures it, and
  assigns it to the waived manager's `_persistedVoices`: what `stage()`
  (#37) already did for the list about to land, now one helper,
  `loadEntry`. The manager reaches the hook as `this`, behind an Xray; the
  reader it belongs to comes from a WeakMap filled in `attach`
  (`readerOf`), with a scan of the open readers comparing raw and waived
  identities as the fallback, and a debug line (`the dropdown picked …
  on a manager no reader was attached with`) when neither finds it — that
  line never appeared live. Zotero's own resolution then lands on the
  entry's voice through branch 1 (`persistedTierVoices[targetTier]`),
  persists it unchanged (no observer fires), and `notePick` learns the
  entry's voice as the pick: the 2026-08-27 decision that a dropdown
  switch *is* a pick stands, only what it lands on changed. The log
  reads `staged Zotero's entry for the dropdown's <lang>: voice <id>`,
  once per click and nowhere else.
- **Zotero's region rule now works on the dropdown path.** `regionChanged`
  (`this._region && persistedRegion && this._region !== persistedRegion`,
  82473) compared the region chosen against the *old* language's entry
  before; against the right one, "English (United Kingdom)" on an `en`
  entry with region `US` skips the entry's voice for the first en-GB voice
  of the pool (Abbi) and rewrites the entry with region `GB` — Zotero's
  design for an explicit region, and the plugin learns that voice as the
  pick like any other.
- **The test fake was cheating.** Its `setLanguage` with persist read the
  pref's entry for the new language directly — exactly what Zotero does
  not do — which is why 67 tests passed over this bug. It resolves from
  `_persistedVoices` now, with `isLanguageSupported`'s region filter,
  `regionChanged` and the region branch in miniature; the round trip, the
  region rule and a language with no entry are pinned. The pre-fix run
  failed four tests: the three new ones and the 2026-08-27 "learns a
  language switch that re-persists what the entry already holds", whose
  Ada had been reached through the cheat.
- **Live, 2026-09-06 02:12-02:24, 1.10.10-beta, through the bridge.** Two
  fixtures paused on Andrew at 2.1×; the pools as on 2026-09-05 (787
  Local voices, 87 for `mul` with Masaru first, 80 en-US with AIGenerate1
  first, 29 en-GB with Abbi first). To Multiple languages:
  `_persistedVoices` the `mul` entry (AlloyTurbo) at 0 and 500 ms,
  `selectedVoiceID` AlloyTurbo, both entries byte-identical, the memory
  AlloyTurbo (`mul`), the other tab moved to it and still paused; the log
  `staged … mul`, `read-aloud memory (a pick the pref did not show)`,
  `applied read-aloud memory: en -> mul` (the other tab's lane move),
  `spread … en: resynced`. Back to English (United States): the `en`
  entry, Andrew, the memory Andrew (`en`), the other tab back on Andrew.
  Five clicks, five `staged` lines, none on a popup open, a spread, a
  pref restore or `_prepareReadAloud()`; `patches()` identical before and
  after; no dead objects, no plugin errors. Zotero logs one
  `TypeError: can't access property "collapsed", selectionRanges[0] is
  undefined` (`_getAnnotationFromSelectionRanges`, 78185-78186) per
  dropdown click — the controller recreated with nothing selected,
  nothing of ours in the stack; the rulebook's `selectionRanges` noise.
- **Two driving pitfalls, now in the rulebook.** A player opened through
  the API in a background tab never mounts its DOM — `popupOpen` true,
  the manager `active`, `.read-aloud-popup` absent even after the tab is
  selected — so the dropdown is driven in the selected tab. And
  `Zotero.Debug.get()` is async: read bare, it hands back a promise whose
  string has no `[zotero-tts]` line, and the store looks empty.
- **Left open, on purpose.** A language never used has no entry to load:
  Zotero's fallback, with `_selectedTier` null (every restore clears it),
  takes the first regional match across every tier in list order, a
  Standard voice while signed in — Zotero's own behavior for a fresh
  language, unchanged here; whether the plugin should start it on a Local
  voice the way #35 does for a voice the list lacks is a separate
  decision. The stale entry itself is Zotero's bug, reportable upstream;
  the fix here stands either way.
