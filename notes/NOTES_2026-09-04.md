## The pane speaks Zotero's language: Fluent files Zotero registers and translates itself (2026-09-04 10:02, issue #30)

Every string of the settings pane moved out of `preferences.xhtml` and into
`addon/locale/en-US/zotero-tts.ftl` and `addon/locale/zh-CN/zotero-tts.ftl`
(step ① of #30; the strings TypeScript writes follow in step ②). What was
verified in Zotero's source and then live, in a 1.10.7-beta through the
bridge, and is worth keeping:

- **Zotero registers a plugin's Fluent files on its own.** `registerLocales`
  (`xpcom/plugins.js:439-508`) reads `[plugin root]/locale/<locale>/*.ftl`
  at every startup, install, enable and upgrade — always *before* the
  plugin's `startup` (`:82-83`, `:748-751`, `:762-763`, `:809-810`) — and
  drops the old instance's files at `onInstalling` (`:721`). All plugins'
  files are folded into one `L10nFileSource` named `zotero-plugins`, so
  the **file name is a global name** (ours is `zotero-tts.ftl`) and every
  message id shares the document's namespace with Zotero's and every other
  plugin's (hence `ztts-`). For a Zotero locale a plugin does not ship,
  the pick is per file: exact → same language → `en*` → the first
  available (`:494-498`); Zotero ships both `zh-CN` and `zh-TW`. Seen
  live: after the install `Services.locale.appLocalesAsBCP47` came back
  in a different tail order (`en-US, en-GB, en-AU, en-CA, en-NZ` where it
  had been `en-US, en-AU, en-GB, en-NZ, en-CA`) — a renegotiation when the
  source was registered; en-US stays first, nothing of substance moves.
- **The pane is translated by Zotero's own pass, given a `<linkset>`.** The
  issue assumed `onPaneLoad` would have to `insertFTLIfNeeded` and re-run
  `translateFragment`. Not so: plugin panes are parsed as XUL
  (`xpcom/preferencePanes.js:157`, `defaultXUL: true`), so the markup can
  carry `<linkset><html:link rel="localization" href="zotero-tts.ftl"/></linkset>`
  (the pattern Zotero's plugin docs give); `_loadPane` appends the
  fragment — which binds the link and adds the resource to `document.l10n`
  — and then runs `document.l10n.translateFragment(pane.container)` itself
  (`preferences/preferences.js:345-355`) before dispatching `load`
  (`:617-622`). Proof by mechanism: with the pane open,
  `diagnostics.l10n().pane` reported all 92 `data-l10n-id` elements filled
  (`blank: []`), and each of the 18 `?` icons' `help` attribute was
  exactly the byte length of its message's `.help` in the ftl (214, 238,
  99, … under en-US; 134, 89, 44, … under zh-CN) — the text can only have
  come from the file. Everything `onPaneLoad` runs (`bold-labels`,
  `help-tips`, the engine heading) reads translated attributes.
- **Fluent strips the localizable attributes a translation leaves out**
  (`dom/l10n/L10nOverlays.cpp`, `OverlayAttributes`; for a XUL `label`
  that includes `value`). A `?` icon is `<label value="?" help="…">`, so
  its message must say `.value = ?` beside `.help`, or the `?` vanishes.
  Custom attributes (`help`, `bold`) are written only when
  `data-l10n-attrs` names them. `test/l10n.test.ts` pins both. A message
  with only attributes leaves the element's children alone; a message
  with a value replaces them — and inline `<span data-l10n-name="…">`
  markup in the value reuses the markup's own spans (cloned shallowly,
  ids and styles kept), which is how the highlight preview's painted spans
  survive translation with their ids.
- **The sandbox has `Localization`.** Beside the `wantGlobalProperties`
  whitelist, `_loadScope` hands the scope `Localization` (and
  `ChromeWorker`, `Worker`, `XMLSerializer`; `plugins.js:169`). A sync
  instance over our one file — `new Localization(['zotero-tts.ftl'], true)`,
  `formatValueSync(id, args)` — formats without a window or a promise,
  returns `null` for an id the file lacks (`t()` hands back the id), and
  follows the app locales live: after
  `Services.locale.requestedLocales = ['zh-CN']` its `sample` was Chinese
  with no rebuild. It is the `strings` startup step, first in the list.
- **A live locale switch is a test convenience, not a user path.** Setting
  `requestedLocales` retranslated the open pane in 172 ms (Fluent's
  DOMLocalization re-translates its roots) and `Zotero.locale` did not
  move — it is computed once, in `Zotero.Intl.init`. What does not follow
  until the pane is reopened: whatever TypeScript painted after the
  translation — the provider switches' `Enable`/`Disable` and the bold run
  of *Offer only favorite voices* (Fluent rewrites the checkbox's `label`,
  MozCheckbox copies it into `.checkbox-label` as plain text, and nothing
  re-runs `initBoldLabels`). A user changes the language in Settings →
  General and is asked to restart, so this stays as it is, recorded in
  `test/zotero-dev.md` 1.12. Each switch also logs one
  `uncaught exception: undefined` — Zotero's own: reproduced with no
  settings window open and nothing of ours in the trace.
- **A ? tooltip's `state` is a property**, not an attribute: with
  `#ztts-help-tip` open, `getAttribute('state')` is `null` and `tip.state`
  is `open`. The rulebook (`.claude/agents/zotero-tester.md`, step 7) now
  says so.
- **Tools → Plugins' description has a mechanism after all** — Mozilla's,
  not Zotero's: `XPIInstall.sys.mjs:567-568` resolves WebExtension
  `_locales/<lang>/messages.json` for `name` and `description`. Rejected
  for now: a `default_locale` that disagrees with the directory refuses
  the whole install (`Extension.sys.mjs:2590-2598`), and anything reading
  the manifest raw — the zotero-chinese store scrapes it — would show
  `__MSG_description__`.
- **Tests render the file.** `@fluent/bundle` and `@fluent/syntax`
  (Mozilla's reference implementation, no transitive dependencies, dev
  only): `test/setup.ts` installs an en-US rendering into `t()` for every
  test file, with `useIsolating: false` as Gecko's own bundles have it, so
  the UI tests keep asserting the sentence a user reads; `test/l10n.test.ts`
  parses both files — no junk, the same ids, attributes and variable
  references, every `data-l10n-id` and every literal `t('…')` present, no
  orphan, `.value = ?` on every `.help`, every `.bold` inside its `.label`.
  Five markup tests that had pinned the English in `preferences.xhtml`
  now read it from the file through the same rendering.

## The pause between sentences is catalog data, and the gap is one number handed to a timer (2026-09-04 17:08, issue #44)

Two settings in the Reading group — *Pause between sentences* (on, 0 ms)
and *Extra pause between paragraphs* (on, 200 ms) — now set the gap before
the next sentence for every voice in the player, Zotero's Standard and
Premium included, at 1× and shrinking with the speed; a switch off leaves
that part to Zotero. The owner chose the defaults knowing they depart from
Zotero's own pacing (a fresh install drops the Premium voices' 300 ms);
Zotero's is one switch away. What was verified in the source and live, in
1.10.8-beta on 10.0.2-beta.5 through the bridge:

- **The gap is computed in one place and read from the voice each time.**
  `_handleSegmentEnd` advances `_position`, takes `this.voice.sentenceDelay`,
  adds `DELAY_PARAGRAPH` (200, `reader.js:39296`) when the *upcoming*
  segment carries `anchor: 'paragraphStart'` (the segmenter marks a
  chain's first segment so, `:71231`), and hands the sum to
  `_scheduleSpeak(delay)` — a bare `setTimeout` (`:39503-39507`, `:39404`;
  that is its only caller). Nothing divides by the speed, while the audio
  itself is time-stretched (`:40379`): at 2× the sentence halves and the
  gap does not. `sentenceDelay` is a prototype getter over `impl`
  (`:40464`, `impl.sentenceDelay ?? 0`), and `impl` is a row of the voices
  response flattened by `parseVoicesResponse` (`:40537`) — server data.
  Measured live in the fixture's `_allVoices`: `Premium Voice 1-3`
  (`a6ac2542-`, `5c8d9d0d-`, `d072a0bf-en-US`) carry 300, Premium 4-5 and
  Standard 1-3 carry 0, the plugin's voices 0 (voice-catalog.ts publishes
  it). So out of 2267 listed voices exactly three paused, and nothing in
  Zotero could change it.
- **The hook is on the number, not the voice.** The first plan — shadow the
  `sentenceDelay` getter, as #9 once did for `label` — cannot reach the
  paragraph extra, added after the getter is read; rewriting the field in
  the composite `getVoices` freezes it into each tab's list, cannot follow
  the speed, and never reaches a running controller (it holds the old
  voice object). So `read-aloud/pauses.ts` shadows `_scheduleSpeak` on
  `ReadAloudController.prototype` and recomputes what it receives:
  sentence part = setting ÷ speed when on, else the voice's own; paragraph
  part (only when `_currentSegment.anchor === 'paragraphStart'`, read after
  Zotero advanced the position) = setting ÷ speed when on, else
  `delay − native`, which is what Zotero added. Both off, the number goes
  through untouched. The settings are read on every boundary, so the pane
  applies at the next sentence in an open session and the voice list is
  never rebuilt — the reading guard of #11 has no part here. The
  controller class is private to the bundle and exists only during a
  session, so the prototype is reached through the manager's
  `_createController` (`:82366`), shadowed per tab from `watchReader` at
  open; a controller already running at attach (an upgrade under a
  session) is patched at attach.
- **Verified live**, fixture-a (paragraph starts 0/5/9/12/15), Azure
  voice, memory speed 1.6, `diagnostics.pauses()` polled per second:

  | state | `gaps` | boundaries (`scheduled` → `delay`) |
  |---|---|---|
  | defaults, 1.6× | `{0, 125}` | into 5: 200 → 125, `paragraph: true`; elsewhere 0 → 0 |
  | sentence 1000, paragraph 400, 2×, written while paused | `{500, 700}` | 0 → 500; into 15: 200 → 700; `_allVoices` 2267 throughout, session `active` |
  | both off, 2× | `{0, 200}` | 0 → 0; into 9: 200 → 200 |
  | Premium Voice 1, defaults, 2× | `{0, 100}` | 300 → 0, `nativeSentence: 300` |
  | Premium Voice 1, both off | `{300, 500}` | 300 → 300 |
  | in-place reinstall under the paused session | `patched` both true, `count` 0 | next: 200 → 100 |

  `patches().pauses` counts one entry per open tab (the manager) plus one
  per tab with a session (the controller): `{4, 4}` right after the first
  install with one session running, `{6, 6}` after the reinstall with two,
  `{6, 4}` once the fixture tab closed. The pane: both rows bound, writes
  through the number field and the checkbox reach the prefs, no
  `#ztts-notice`, the `?` tooltips open. Log lines: `pauses attached` per
  tab per instance, `pause scheduling attached to a controller` per
  session per instance.
- **A metered voice costs a bridge round trip per sentence.** The Premium
  check was capped at four sentences and ran about thirteen: the resume
  after `selectVoice` did not start until a fresh
  `notifyUserGestureActivation()`, and while that was being diagnosed
  across calls the session played on. `premiumCreditsRemaining` (822) did
  not move in the provider object — it is not refreshed live — so the
  cost is estimated from the audio, roughly five credits. Resume and pause
  go in the *same* script whenever the selected id has no `::`.
- **Reaching a Zotero-tier voice from chrome.** `selectVoice(id)` alone
  leaves `_voice` null with no controller when the manager sits on the
  Local tier: `get voices()` filters `_allVoices` by `_selectedTier`
  (`:81994-81996`) and `_applyVoice` drops an id outside it and destroys
  the controller, silently. `selectTier('premium')` first. Two more
  chrome-side facts: `Array.prototype.filter` over a reader-compartment
  array returns `[]` (an index loop over the same array counted 1452
  premium voices), and a voice's fields are all prototype getters —
  `Object.keys(voice)` is `impl, provider`. The rulebook has all three.
- **Seen, not caused here, left open.** (1) The user's own tab was
  *speaking* at the first in-place install; after the #38 redelivery
  (`redelivered the Read Aloud interface to 3 open reader(s); rebuilt 1
  voice list(s)`) it took one more boundary and then sat `active, paused`.
  #38 verified an upgrade under a *paused* session; a voice-list rebuild
  re-runs `_applyVoice`, which destroys and recreates the controller, so a
  playing session may not survive it — unproven, the user may have
  pressed pause. (2) One stackless `can't access dead object` in the error
  ring at the second install (none at the first, no burst, nothing of
  `zotero-tts.js` in it); the two `uncaught exception: undefined` per
  install are Zotero's own, as recorded above. (3) The Reading group's
  number fields start after their own labels, so they do not line up in a
  column — the Prefetch row's flow, kept for consistency.
