## Before you start

- Build and bridge: `zotero_ping`, `zotero_plugin_list` for the installed version (expect the release unless a beta from this build is already there), install the xpi, `zotero_plugin_list` again, then `133-00`.
- WebDAV isolation (workflow "Test WebDAV first") runs once per zotero-dev session, outside this kit, before installing.
- Fixtures: `fixture-a.pdf` (17 segments, paragraph starts 0/5/9/12/15) and `fixture-b.pdf` (6 segments); `133-01` imports both.
- Items 13 and 23 need a local fake Kokoro-shaped HTTP server (routes `GET /v1/audio/voices`, `POST /dev/captioned_speech`; a `mode` file toggled between `ok` (small real WAV + word timestamps) and `garbage` (200 OK, undecodable bytes); "network" is simulated by pointing `local.baseURL` at a closed port, not a mode — a server that accepts the connection and only closes it without answering is not a fast, definite failure and produced unreliable timing in the first attempt). No such server is checked into the repo; write one ad hoc under the scratch directory before running `133-11`/`133-12`, and stop it afterward.
- Items 20/21 touch `zotero-standard.enabled`, `zotero-premium.enabled` and `readAloud.sameForAllDocuments` (memory-sync's spreadVoice) — `133-16` restores all three.
- A run that leaves the plugin sandbox in an unusual state (a `selectVoice` to a voice outside the manager's currently selected tier destroys the controller with no error, a known Zotero behavior — driving notes §3) recovers with `selectTier(<the voice's own tier>)` before `selectVoice`.
- Item 24 (a plugin update pauses the reading) is a real in-place `zotero_plugin_install` of the same xpi while a fixture is genuinely playing; check `diagnostics.startup()` and the fixture's `diagnostics.engine()` entry immediately after.
- Cleanup order: pause and close every player before erasing fixtures; restore prefs (mute last is wrong here — WebDAV's `readAloud.memory` is last, per the workflow); only then restore WebDAV sync switches.

## Limits

- Long real-time waits (natural sentence-to-sentence playback, the 5s/20s pause-resume thresholds, several 15-30s polls) make single scripts run 30-90s; some single `zotero_execute_js` calls returned a bare `undefined` (the bridge's own 30s window, not a throw — confirmed via `zotero_read_errors` each time) while the script kept running under `Zotero.ZoteroTTSRun.state` regardless. Prefer the kit runner's background execution and a `sleep` wait over a bare call for anything with a real-time wait inside.
- A first attempt at the read-ahead/cache sampling loop (item 4/5) polled `diagnostics.engine()` in a tight `while` loop with no `await sleep(...)` between iterations: 41,066 samples in 4.5s, all reading the same in-flight fetch, because the loop never yielded to the macrotask queue where `fetch()`'s own completion runs — the one real request never got a turn to resolve until the loop (and the script) ended. Always yield a few ms between diagnostic polls.
- The en-only pause/resume word-boundary rewind (item 11, 5s/20s) was not confirmed on this profile: its persisted voice for English resolves to a Fish `mul`-tagged voice even after picking an explicit `fish::en/...` id while idle (the manager's own `_syncPersistedVoicesToManager` overwrites an idle pick on reactivation) — picking a voice for a specific test needs it done while the manager is ACTIVE (through the handoff), not idle.
- Item 23(c)'s Retry *recovering* after a decode failure was not cleanly reproduced against the fake server (three attempts, including with `cacheAudio` off to rule out the plugin's own provider-level cache serving the same bad bytes again); the failure detection itself (`error: unknown`) and the retry mechanism firing again (`store.requests` and `notices.failed` both rise) are confirmed. See the case row and the report.
- Items 19 (OS media keys) and 20 (the negative half — `engine.owns` false has no dedicated diagnostic) are evidenced by source and a structural/shape check, not a full live reproduction; see the case row.
