## Before you start

- Build and bridge: `zotero_ping`, `zotero_plugin_list` for the installed version, install the xpi, `zotero_plugin_list` again, then `133-00`.
- WebDAV isolation (workflow "Test WebDAV first") runs once per zotero-dev session, outside this kit, before installing.
- Fixtures: `fixture-a.pdf` (17 segments, paragraph starts 0/5/9/12/15) and `fixture-b.pdf` (6 segments); `133-01` imports both. A third (`133-27`) is worth its own item for fault tests once fixture A/B's fake voices have read most of the document already (see Limits).
- Items 13/23 (and, from run 2, 17's fault-adjacent sub-items, 12, 14) need a local fake Kokoro-shaped HTTP server (`GET /v1/audio/voices`, `POST /dev/captioned_speech`; a `mode` file read fresh per request: `ok`, `no-timings`, `garbage`, `slow` (1-2s), `error` (500), `fail-once` (the first request for a given exact text fails, every later one for the same text succeeds); "network" is a closed port, not a mode). No such server is checked into the repo; write one ad hoc under the scratch directory, give it several voice ids (never one starting with a/b/z/j/e/f/h/i/p, kokoro.ts's own locale-prefix map), and stop it afterward.
- Item 21 touches `zotero-standard.enabled`/`zotero-premium.enabled`; item 17(i) touches `zotero-standard.enabled` alone. Both kinds of script restore what they set.
- A run that leaves the plugin sandbox in an unusual state (a `selectVoice` to a voice outside the manager's currently selected tier destroys the controller with no error) recovers with `selectTier(<the voice's own tier>)` before `selectVoice`. A fake voice added to the server's own list is invisible to an ALREADY-OPEN reader's catalog until that reader's own `manager.loadVoices(true)` runs (and settles, ~1-1.5s) -- skipping this makes the next `selectVoice` a silent no-op onto whatever voice was already selected.
- Item 24 (a plugin update pauses the reading) is a real in-place `zotero_plugin_install` of the same xpi; the playing variant is `stats.adopted` 1 with `session.paused` becoming true; the paused variant (run 2) is the same without the pause transition, and with no sound at all before Play.
- Cleanup order: pause and close every player before erasing fixtures; restore prefs (`133-31`; `readAloud.memory` last of all, per the workflow); only then restore WebDAV sync switches.

## Limits

- Long real-time waits make single scripts run 30-90s (some over 100s: item 17(g)'s full `HANDOFF_SWITCH_MS` deadline is 120s alone). Some single `zotero_execute_js` calls returned a bare `undefined` (the bridge's own 30s window) while the script kept running under `Zotero.ZoteroTTSRun.state` regardless. Prefer the kit runner's background execution over a bare call for anything with a real-time wait inside; poll the run's own `run.json` `done` flag from a backgrounded Bash wait rather than a fixed sleep.
- Always yield a few ms between diagnostic polls (a tight loop starves the macrotask queue `fetch()` resolves on).
- **A picked voice while the manager is merely PAUSED still goes through the Handoff for a plain `selectVoice`** (item 17(f)'s own mechanism) -- it is not a free, instant "utility" switch the way `selectTier`/`setLanguage` are while paused. Using it that way left a reader with a `stage: 'failed'` handoff and no bound controller more than once this run (recovered by closing and reopening the tab). Prefer `selectTier` while paused for a plain setup switch, or expect a real (if silent) handoff and wait for its `stage: 'committed'`.
- **The Engine's own read-ahead (3 segments) and a chosen fake-server MODE interact**: a segment fetched under one mode while an earlier one was still "current" is cached under that mode's answer, so a later, deliberately-failing mode change has nothing left to bite if the target was already read ahead. Set the mode before the segment two-or-more-back from the target ever starts playing, or use a segment/voice pairing neither has touched yet (this run went through five fake voice ids for exactly this reason -- af/bf/cf/df/gf_fake).
- Item 14's plugin-side warm chain's own `prefetch: local: stopped, the reader is gone` line was not independently observed in three live attempts (the Engine's own `late audio dropped` line and the absence of dead-object errors were, cleanly, twice) -- plausibly because the warm chain's single request had not yet been dispatched (queued behind the Engine's own pair) at the narrow point this run closed the tab.
- Items 8, 19, 20 (negative half), 22 remain evidenced by source/structure only (no Windows machine, no OS-key simulation, no `engine.owns` diagnostic, no Bluetooth output) — unchanged from run 1.
