## Scrolling stays smooth while the player is open (issue #125, 1.13.1)

With the Read Aloud player open — playing or paused — the document scrolls
as smoothly as it does with the player closed. Before the fix it did not:
scrolling dropped to 13 fps against 114 with the player closed, 91% of
frames over 50 ms, and the main thread was blocked 83 ms per frame.
Mechanism: the tier of a voice id is read through a factory the walk opens
once (`voiceTiers()`), so the local engine's name — which costs a whole
`loadSettings` over 66 preferences — is read once per walk of the voice
list instead of once per voice. The walks are `scan()` in
`src/read-aloud/provider-tiers.ts`, in front of every `_resolveVoice`, and
the list walk in `src/read-aloud/live-voice-list.ts`. Until #134 `scan()`
also ran every time the reader re-rendered Zotero's own player's first
dropdown, since Zotero repositions the open popup once per scroll frame
(`reader.js` `_handleScroll` 55160 → `_repositionPopups` 53973); that
per-frame walk is what this case measured, and #134 removed it with the
dropdown's rewrite.

Run the baseline first. Fixture:
`test/fixtures/scroll-performance/scroll-performance.epub` — 400
paragraphs, about 34 viewports, regenerated by `make.py` beside it. The
other EPUB fixtures are one viewport tall and cannot absorb a scroll.
**It opens paginated**: call `view.setFlowMode('scrolled')` and wait for
`scrollHeight` to exceed the viewport before measuring, since the fault is
on the scrolled DOM view and a paginated or PDF view may pass vacuously.
Flow mode is per attachment, not a global preference, so this does not
disturb any other tab.

The player is opened muted (`readAloud.volume` 0 for the run) and paused at
once. **Do not open a player on the owner's own document, and do not scroll
it**; if its paused player blocks a settings change, close it with
`toggleReadAloudPopup(false)`, note the tab, and never reopen it.

**Items 2-4 need a restored, non-minimized window**: `requestAnimationFrame`
in the reader stops while Zotero is minimized, and a minimized run returns
no frames with no error. Minimize again afterwards.

State it may touch: `readAloud.volume`, the fixture item, its tab and scroll
position, and its player's open state. Cleanup erases the item, closes the
tab, and restores the volume to its exact prior value and user-value state.

Values below were measured on 2026-09-18 with 1.13.1-beta on macOS, Zotero
10.0.3-beta.3, a 120 Hz display and 1,819 listed voices; scale the frame
numbers to the display in use and say so.

### 1. The build and its patches

`zotero_plugin_list` reports `1.13.1-beta`, and
`Zotero.ZoteroTTS.diagnostics.startup()` reports every step `ok` with
`failed` empty. Measured: 30 steps `ok`, `failed` `[]`.

### 2. Preference reads per walk (the mechanism)

Wrap `Zotero.Prefs.get` with a counter — the plugin's backend is
`(key) => Zotero.Prefs.get(key, true)`, looked up on `Zotero.Prefs` at call
time, so a chrome wrapper does see the sandbox's reads. Open the player on
the fixture, drive a 60-frame scroll, report the count beside
`manager._allVoices.length`.

Expected: the count does not scale with the voice list. Measured 11,423
reads over 60 frames with 1,819 voices — about 190 per frame, which is the
66 keys `loadSettings` covers read once for `voiceTiers()` and once for
`labels()` per render of the dropdown. With the player closed: 194 over the
same pass. **The number to compare against is 1,819 × 66 ≈ 120,054, which
is what a single walk cost before the fix** — the whole 60-frame pass is
now under a tenth of one old walk. A count in the tens of thousands per
frame means the fix did not take and everything below is moot. Since #134
no walk runs per render: expect the player-open pass near the
player-closed one.

### 3. Frame rate, player open against closed

The same scroll run twice from the same start position, one step per frame
(`win.scrollBy(0, 14)` inside a `requestAnimationFrame` loop — a single
`behavior: 'smooth'` call does not reposition the popup every frame).

Expected: both at or above 90 fps on a 120 Hz display, within roughly 10%
of each other, no frame over 50 ms in either. Measured: 121.8 fps closed
against 119.8 fps open, longest frame 9.3 ms and 9.4 ms, 0% over 50 ms in
both. Before the fix: 114.4 fps against 12.8 fps, 91.2% over 50 ms.

### 4. The main thread is not blocked

A 0 ms timer chain running during the pass of item 3 — the cheap way to
tell a blocked main thread from paint cost.

Expected: a median at or under 15 ms, in the range of the player-closed
run. Measured: 7.5 ms open against 6.4 ms closed, longest 16.2 ms. Before
the fix: 82.7 ms against 8.8 ms.

### 5. A settings change still reaches the next walk

The contract the hoist must not break: the engine's name is read afresh per
walk, never cached across walks. With the player open, change the local
engine and force a walk (`manager._resolveVoice()`); the tier the local
voices carry follows the new engine.

**NOT TESTABLE on a profile without local voices.** On 2026-09-18 the local
provider was off (`zotero-tts.local.enabled` false) and the 1,819 voices
were 1,452 Zotero premium, 28 standard and 339 Fish Audio — no `local::`
id, and `localEngine` reaches nothing else, so changing it moved no
observable value. Run this item only where the Kokoro provider is on and
listing voices. Meanwhile the contract is covered by the unit test
`test/read-aloud/provider-tiers.test.ts`, "is idempotent across rebuilds and
re-reads the engine's name on every resolve", which mutates the engine
between resolves and asserts the tier follows; and item 2's count shows the
settings are re-read on every walk rather than cached once.

### 6. The dropdown and the live list are unchanged

`Zotero.ZoteroTTS.diagnostics.providerTiers()` and
`.liveVoiceList()`. Expected: every reader reports `resolveShadow` and
`tierMemoryHook` true; `tiers` one entry per provider with voices beside
Zotero's; `retagged` counting the plugin voices the walk re-tagged; the
fixture's `pluginPlayer()` `state.providers` sorted by displayed label.

Measured before #134, with the dropdown's rewrite and its `options`: all
three patches true on both readers; `tiers`
`['premium','standard','fish']`; `retagged` `{fish: 339}`; `options`
`fish=Fish Audio`, `premium=Zotero Premium`, `standard=Zotero Standard`;
`liveVoiceList` `applied: 1` on the fixture with `retained: 0`. The fuller
behaviors stay in their own cases —
[`cases/provider-tiers.md`](provider-tiers.md) and
[`cases/reader-voice-list.md`](reader-voice-list.md) — since this change
edits the dependency both of them walk through.
